## 2. 「抄代码」与「同一个原理」在法律上是两件事

这是你问题的核心，先把它讲清楚：

| | 受版权保护？ | 说明 |
|---|---|---|
| **具体的代码表达** | ✅ **受保护** | 你逐行复制别人的 `.java` ⇒ 需要遵守对方许可 |
| **思想 / 原理 / 机制 / 算法 / 系统架构** | ❌ **不受保护** | 「用 capability 记录输入状态来驱动状态机」「自备一个 `onUseTick` 空实现的 `IWand`」——**这些是思路，任何人都可以独立实现** |
| **API 签名 / 协议 / 数据格式** | ❌ 基本不受保护（且有判例支持互操作性） | 调用 `Spell.mobSpellResult(...)` 不是侵权 |
| **美术、音效、模型等资源** | ✅ 受保护（且常单独授权） | 见 §1.1 第 3 条 |

⇒ **所以你说的"只是根据同一个原理"，是明确安全的，而且是软件工程的常规做法。**
**读别人的代码理解机制、然后自己写实现**——这叫参考（reference），不叫抄袭（plagiarism）。

> 📌 **一条实用判据**：问自己「我能不能在不看对方代码的情况下，把这件事描述给另一个工程师听？」
> 能 ⇒ 那是原理，安全。不能（必须逐行对着改）⇒ 那是在复制表达，要走许可。

## 3. 但还有一个容易忽略的陷阱：**"抄了"不等于"能维护"**

即使法律允许（MIT），抄万法皆通的代码还有三个**工程**上的代价——这才是真正该拒绝的原因：

| # | 代价 | 说明 |
|---|---|---|
| 1 | **抄来一个更差的实现** | **你自己说了它"很保守、很多聚晶直接无法使用"**。抄一个已知更弱的实现，图什么？ |
| 2 | **把它的抽象带进来** | 万法皆通的核心抽象是 `ISpellBookProvider<T, S>`——"**从一个法术书里收集法术**"。而本项目的核心抽象是"**以玩家操作为粒度的原子动作**"。**两者的切分方式不同**。强行混入会让你的数据模型被它的形状绑架。 |
| 3 | **升级会断** | 抄来的代码不会跟着上游修 bug。调律师的文档里记录了**几十轮**踩坑修复（见 §5.2），抄一份冻结的副本等于放弃这些修复。 |

## 4. 我建议的处置：**不要抄万法皆通，去复用你自己的调律师**

理由很直接——**你已经有一个更好的实现了，而且它是你自己的。**

| | 万法皆通 | **调律师（`goety-tuner`）** |
|---|---|---|
| 许可 | MIT（可抄但需署名） | **MIT，且你是版权人 ⇒ 零障碍** |
| Goety 施法覆盖 | **保守**（你的原话：很多聚晶无法使用） | **基本解决了大部分聚晶**（你的原话） |
| mob 侧通道类法术 | 未解决（因此保守） | ✅ `CastChannel.tickChannel` + 自备 `TunerWand` 解决 |
| 施法者身份 | `Player` 与 `mob` 两条路 | ✅ **`spell.mobSpellResult` 走 mob 专用入口** |
| 玩法定位 | 女仆施法（面向玩家体验） | 一个会指挥聚晶的 Boss + 一个可被指挥的仆从 |

⇒ **结论**：
- **法律上**：抄万法皆通是允许的（MIT + 署名）。
- **工程上**：**不抄**。它的抽象与本项目不匹配，而且实现更弱。
- **实践上**：**从调律师里提取共用机制**。这是唯一一条同时做到「零法律风险 + 零重复劳动 + 复用已验证的坑位修复」的路。

> 🎯 **一句话**：你不是在"抄万法皆通"，你是在**把自己的成熟实现**从"Boss 与仆从的施法通道"泛化成"通用操作层 + 行为架构"。

## 5. 具体有哪些东西值得从调律师搬过来

> 完整机制清单（25 项 + 文档≠代码不一致表 10 条）见 [`_research/tuner-reference.md`](../_research/tuner-reference.md)，全部带 `file:line`。
> 本节只摘出**对本项目最关键**的部分。

### 5.0 一句话总览

调律师需要复用的**不是它的玩法**（Boss 音乐/阶段），而是它那**一层"让 mob 施放任意聚晶"的通道**：

```
FocusPoolManager（枚举全部聚晶 + 分类 + 抽签 + 锁池 + 冷却）
        ↓
CastChannel（前摇 / 瞬发 / 通道路径；snapTowardTarget；异常自愈；松手保证）
        ↓
spell.SpellResult(level, caster, wand, stats)      ← 直调，不过物品
        +
caster.startUsingItem(MAIN_HAND)                   ← 自愈式维持，让光束类法术存活
        +
TunerWand（onUseTick 空实现）                        ← 让"正在使用法杖"成立而不触发白烟分支
```

### 5.1 可直接复用的机制（核心 6 项）

| 机制 | 解决什么问题 | 关键类与签名 |
|---|---|---|
| **`spell.SpellResult(ServerLevel, LivingEntity, ItemStack, SpellStat)`** | mob 施法的**唯一正确入口**（等价于 `Spell.mobSpellResult`，已核对 `Spell.java:49-61`） | `ISpell.java:243` |
| **`CastChannel`** 三段式调度 | 前摇 / 瞬发 / **通道路径**；呼叫顺序完全对齐玩家路径 | `entity/ai/CastChannel`（620 行） |
| ★ **`tickChannel` 里自愈式 `startUsingItem(MAIN_HAND)`** | 让 `AbstractBeam` 类法术**存活**（万法皆通缺失的正是这一条） | `CastChannel:308-310` |
| **两段预算公式** | 蓄力与持续分开算，否则 `castUp` 大的法术会把预算吃光只出一发 | `channelChargeTicks + max(5, channelMaxTicks)` |
| **自备 `TunerWand implements IWand`** | 让"正在使用法杖"成立，同时**不触发** `DarkWand` 的白烟+灭火音分支 | `focus/TunerWand`（145 行，`onUseTick` 空实现） |
| **`FocusPoolManager`** | 扫描**全部**已注册聚晶（含附属）+ 分类 + 轮盘赌 + 锁池 + 运行期自愈拉黑 | `focus/FocusPoolManager`（556 行） |

### 5.2 ★ 更值得搬的是「踩过的坑」——这些是钱买不到的

| 坑 | 现象 | 精确修法（源码位置） |
|---|---|---|
| ★★ **`Pose.CROUCHING` 被当成潜行** | 前摇摆蹲姿 ⇒ `isCrouching()` 为真 ⇒ Goety `Spell.isShifting` 为真 ⇒ **召唤类法术变成"召回已有仆从"** ⇒ 什么都召不出来。**42 个法术类**受影响（`SummonSpell` 全部子类继承该分支） | 在两个实体上覆写 **`isCrouching() { return false; }`**：`TunerBoss.java:368`、`TunerServant.java:300`。**安全**，因为蹲姿动画读的是 `hasPose(Pose.CROUCHING)`（`TunerModel.java:49`），与 `isCrouching()` 无关 |
| ★ **`AbstractBeam` 靠 `isUsingItem()` 存活** | `AbstractBeam.tick()` 里 `if (itemBase && !MobUtil.isSpellCasting(owner)) discard()`；而 `isSpellCasting = isUsingItem() && IWand && 有聚晶` ⇒ Mob 从不 `startUsingItem` ⇒ 光束刚生成就自毁 | `tickChannel` 里自愈式 `startUsingItem` + **5 处** `stopUsingItem`（缺一个光束就永不消失）+ 只在 `channeled` 时松手（避免误伤别的模组的引导物品） |
| ★★ **`DarkWand` 的"白烟 + 灭火音"链 ——四环，缺一不可** | ⚠️ **我最初只记述了后两环，不完整** ⇒ 会误以为"换一把 `TunerWand` 就够了"。实际上 `TunerWand` 单独**并没有解决**它，调律师在 0.0.21 又修了一次，方法完全不同 | **见下方专项** |
| **`snapTowardTarget` 必须在 `startSpell` 之前** | 瞬移走位瞬间改朝向，而 `LookControl` 每 tick 最多转 50° ⇒ `VoidRift`/`FlameStrike`/`AbyssalBeam`/`ChipRain` 在 `startSpell` 内就沿视线 rayTrace ⇒ **朝旧方向打偏** | 三处调用：前摇每 tick / **`startSpell` 之前** / 瞬发结算前；且两个实体都**不装** `LookAtPlayerGoal`/`RandomLookAroundGoal` |
| **第三人称附属的异常会崩服** | 只包 `startSpell` 不够；`conditionsMet`/`castDuration`/`CastingSound` 由第三方实现，抛异常会一路上冒到 `serverAiStep` | 三处 catch-all（`tryStartCast`/`tick`/`instantCast`）→ ERROR + **运行期拉黑** + 归还聚晶 + 复位 |

#### ★ 专项：「每 tick 冒 10~44 个白烟 + 灭火音」的完整四环链条

> 来源：调律师 **0.0.21（commit `36a3dc7` 追加8）** 的 `CastChannel#ensureInertWand` javadoc + 源码。

| 环 | 内容 |
|---|---|
| **① 谁会去"使用"杖** | `tickChannel` 要 `startUsingItem(MAIN_HAND)` —— 这是 `AbstractBeam` 那类"以法杖为基准"的光束实体存活的前提。**这一步让"手里那把杖"的 Item 层代码真正跑起来** |
| **② `DarkWand.getUseDuration` 读 NBT** | 它读 `stack.getTag().getInt("Cast Time")`。而 **Mob 的持有物永远不跑 `ItemStack#inventoryTick`**（1.20.1 里只有 `Inventory#tick` 调它 ⇒ 仅玩家物品栏）⇒ 这个键要么不存在（= 0）、要么是**玩家留下的陈旧值**。玩家持杖时 `setSpellConditions` 还会写 `Cooldown`，非玩家连这步都不会发生 |
| **③ 于是"使用"当场结束** | `LivingEntity#startUsingItem` 把 `getUseDuration()` 当 `useItemRemaining`；**为 0 时 `updateUsingItem` 连 `onUseTick` 都不会调**，直接 `completeUsingItem()` ⇒ `DarkWand#finishUsingItem` ⇒ `MagicResults(...)` |
| **④ `MagicResults` 对非玩家只冒烟** | 整段包在 `if (spell != null && caster instanceof Player)` 里，非玩家掉进 else：`failParticles(...)`（`IWand` 的 default 实现 = `for (i < random.nextInt(35) + 10)` 反复 `CLOUD` ⇒ **恰好 10~44 个白烟**）+ `FIRE_EXTINGUISH` 音效，**法术一个都不放** |

**叠加 `tickChannel` 的"每 tick 自愈" ⇒ 这条链每 tick 触发一次**（不是"每冷却 tick"——因为第 ③ 环已把 `useDuration` 变成 0，`onUseTick` 那条按 `Cooldown` 节流的路径根本走不到）。

**0.0.21 的修法（与"换把杖"完全不同）**：新增 `CastChannel#ensureInertWand` + **两道闸，顺序关键**——
因为主手这把杖有**四个来源**（构造函数 / 旧档 NBT / **仪式召唤**（0.0.20 及以前会把**玩家那把杖**塞进 Boss 主手）/
指令、数据包、其它附属的任意 `IWand`）：

1. **闸 A**：手里"正在使用"的东西**不是**惰性法杖 ⇒ **立刻 `stopUsingItem()`**；
2. **闸 B**：主手不是惰性法杖 ⇒ **先换成 `tuner_wand`（用 `BossWandHelper#inertCarrier` 保留原杖 NBT）再 `startUsingItem`**；
3. 换杖后**必须把当前聚晶重新装进去**（否则 `isSpellCasting` 的"杖里有聚晶"不成立，光束照样活不下来）。

> 📌 **教训（第 6 条，与 [01](01-操作清单.md) §9.1 的五条并列）**：
> **"提供了一个自备物品" ≠ "保证它一定在手上"。**
> 主手物品可能来自旧档、仪式、指令、其它模组 ⇒ **约束必须在行为发生的那一刻校验并按需替换**，
> 而不是指望类型系统。这类坑在跨模组集成里非常常见。

> 💡 **这六条恰好都是"从物品/输入/姿态路径走不通"的同类问题**——与拔刀剑那边
> `InputCommandEvent` 写死 `ServerPlayer`、`SuperSlashArts.releaseSSA(ServerPlayer)` 是**同一个性质**。
> 这印证了本项目的主线判断：**女仆必须绕过物品与输入，直调 API**；
> 而且**已经有验证过的绕法**，不必自己从零试错。

#### ★★ 这六条我们各自落在了哪里（2026-10-01 第九轮对账）

调律师的这六条不是"参考资料"，**每一条都在我们的代码里有一个落点**（没落的会被这一节暴露出来）：

| 调律师的坑 | 我们的落点 | 备注 |
|---|---|---|
| ① `Pose.CROUCHING` ⇒ `isShifting` ⇒ 法术走另一套分支 | `GoetyChannel#clearShifting`（**我们改不了 TLM 的实体** ⇒ 只能施法前清 + 复核） | 第九轮**收紧为硬规则**：复核仍潜行就**一概不施法**（`SNEAK_BRANCH_RISK`）—— 清除是专门动作的职责 |
| ② `AbstractBeam` 靠 `isUsingItem()` 存活 | `GoetyChannel#tryStartUsing`（**自愈式**：每 tick 掉了就补）+ `stopUsing` **只在确实在用物品时松手** | 通道期间每 tick 调用 |
| ③ `snapTowardTarget` 必须在 `startSpell` **之前** | `AimHelper.faceTarget`：`begin()` 里调一次，**每 tick 再调** | 因为 `VoidRift`/`FlameStrike` 在 `startSpell` 内部就 rayTrace |
| ④ 附属异常会崩服 | 所有第三方调用点 catch-all ⇒ **ERROR + 运行期拉黑该法术** + 收尾复位 | `GoetyChannel#blacklist`（进程内）+ `BLACKLIST` 诊断出口 |
| ⑤ `getUseDuration` 读 NBT ⇒ Mob 的杖不跑 `inventoryTick` ⇒ 使用当场结束 | ★ **我们整条绕开了它**：不依赖"使用物品"来施法，而是**自己调 `startSpell`/`useSpell`/`SpellResult`** | ⇒ **不需要自备惰性 `IWand`**（W35 因此只对"光束类依赖 `isUsingItem` 的实体"仍需留意，而 ② 已用自愈式 `startUsingItem` 覆盖） |
| ⑥ `MagicResults` 对非玩家只冒白烟 | ★ 同上：**我们从不用 `MagicResults`**；蓄力类"每一发"直接调 `ISpell#SpellResult` | 见 [12 §9.1](12-项目参考.md) |

> ★ 判据：**"抄了人家的教训"要能说出"抄到了哪一行"** —— 否则那只是引用，不是复用。

### 6.1 一个必须澄清的常见误解

> 「用了 GPL 模组的**API**，我也要 GPL 吗？」

**不需要。** 通过**独立的、可选加载的**代码去调用一个 GPL 程序的 API（尤其是经由反射或纯接口声明，且不复制其实现），一般**不构成衍生作品**。
但这条边界在司法上有争议 ⇒ **保守做法**：对 `sbr_core` **完全不引用**（本项目本来也不需要它——我们的拔刀剑能力来自 `slashblade` 本体）。

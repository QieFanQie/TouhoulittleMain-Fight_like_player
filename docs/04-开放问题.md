| 选项 | 内容 | 我的评估 |
|---|---|---|
| **A** 扩展万法皆通 | 给它补上缺的块（仆从管理、施法变体、数据驱动行为层） | 工作量最小，但受它架构约束，且要动它的核心才能数据驱动 |

### Q2 ✅ **已解决 + 已定义** · "处死仆从"是哪几条操作？

**你的回复**：「处死仆从包括**潜行左键指定处死一个**，也有**按下「，」键（或是别的）处死所有临时仆从**。这两个做成**两个独立功能**。」

⇒ **采纳，并明确为两条独立原子动作。** 与我的勘测精确对应（路径 ① 与路径 ②）：

| 动作 id（拟） | 玩家操作 | Goety 实现链 | Goety 里对应什么键 | reach |
|---|---|---|---|---|
| **`execute_servant`**（处死**指定**一个仆从） | **潜行 + 左键攻击自己的某个仆从** | `DarkWand.java:215-227` → `IServant.tryKill(player)` → `Summoned.java:517-519` `hurt(DISMISSED, Float.MAX_VALUE)`。14 个重型仆从有**两段确认**（「你确定要消灭%s?」，**60 tick 窗口**） | 无独立键（就是潜行左键） | **R-A**（等价物：`IOwned.dismiss()` / `hurt(goety:dismissed, MAX)`） |
| **`dismiss_temporary_servants`**（处死**所有临时**仆从） | **按一个绑定键** | `ClientEvents.java:1342-1344` → `CDismissServantsPacket.java:23-41` → 遍历全服筛 `getTrueOwner()==player && isLimitedLife()` 且不在坚守白名单 → `IOwned.dismiss()` | ⚠️ **`key.goety.dismiss`**，中文「**消灭临时仆从**」。**我实测的默认绑定是小键盘 `.`（numpad dot）**，不是 `,` | **R-B**（复刻包里的循环即可；`dismiss()` 本身不吃 `Player`） |

**关于你说的「，」键**：Goety 的键**名**确定是 `key.goety.dismiss`（`zh_cn.json:3257` = 「消灭临时仆从」），
但 `lang` **不含默认键位**（键位在代码里设定）。你的记忆是「，」，我读到的是**小键盘 `.`** ——
**两者都是"右下角的标点键"，很可能就是同一个键的不同称呼**（numpad `.` 在许多键盘上印作 `Del`/`.`）。
⇒ 建议按**功能语义**（"消灭所有临时仆从"）记录，**不写死键位**；具体默认键以游戏内键位设置页为准。

**两条动作的语义差异（这是"独立功能"的实质，不只是两个入口）**：

| | `execute_servant` | `dismiss_temporary_servants` |
|---|---|---|
| **作用域** | **单个**、由女仆**指定**目标 | **批量**、全部符合条件的己方临时仆从 |
| **筛选条件** | 女仆主动选中 | `getTrueOwner()==自己` **且 `isLimitedLife()`**（**只消灭"临时"仆从**） |
| **是否有确认** | 重型仆从有（60 tick 窗口） | 无（一次性） |
| **是否受白名单保护** | — | **受**：`SEHelper.getGroundedEntities/Types`（坚守之书）里的仆从**免疫** |
| **决策层需要的参数** | `target`（哪个仆从） | 无（或"保留哪些"） |

> ⚠️ **决策层必须把它们当两条**：一条是**单体定向**动作（要选目标），一条是**群体无参**动作（会连带牺牲，且受白名单约束）。
> 合成一条会导致"想处死一个却全杀了"这类不可逆事故。**已在 [01](01-操作清单.md) §4.4 拆成 G10 / G11 两条。**

**仍然保留的细节问题（不阻塞）**：`isLimitedLife()` 的具体判定（"临时"vs"常加载"），留给实现时读 `IOwned` 确认。

### Q3 ★★ 清单交付成"文档"还是"数据文件"？

现在清单是 Markdown 表格（人读友好）。但你最终要的是**可被程序消费**的东西。

| 选项 | 形式 | 优点 | 缺点 |
|---|---|---|---|
| 文档式（现状） | Markdown 表格 | 人读、评审方便 | 程序读不了；改一处要同步多处 |
| **数据式** | JSON / YAML 文件 + 规范文档 | 可直接生成注册代码；可校验；可数据包驱动 | 需要先定 schema |
| 代码式 | Java `enum`/`record` 注册表 | 类型安全 | 改动要重编译——**这正是万法皆通的局限** |

**我的倾向：数据式（YAML/JSON），并用文档解释 schema。**
理由：你第二步要的是"**可便捷搭建**的行为逻辑架构"，如果操作层还是 Java 硬编码，第二步无从谈起。
但**现在还不急着定**——先把清单内容补全，schema 随内容收敛。

> **你的决定原文**：「资源消耗：**暂时是白嫖，以后做也不会按照玩家的来**」。
>
> ⇒ **结论与影响**：
> - **现在**：什么都不做。女仆不消耗灵魂能量、不受聚晶冷却、可突破召唤上限——**接受现状**。

> - ⇒ **这一条砍掉了三项原本要做的额外工作量**：不需要补 `DarkWand` 的扣费、不需要给女仆加聚晶冷却、

勘测发现：**如果什么都不做，女仆会自动获得三种"白嫖"能力。** 这不是设计选择，而是现状的副作用。

| 白嫖项 | 机制 | 证据 |
|---|---|---|
| **Goety：不消耗灵魂能量** | `DarkWand` 的扣费在 `caster instanceof Player` 分支内；直调 API 绕过 | `DarkWand.java:762-845` |
| **Goety：不受聚晶冷却** | `IWand.isOnCooldown` 对非 `Player` **恒返回 false** | `IWand.java:88-95` |
| **Goety：可突破召唤上限** | `SummonSpell.java:73` 潜行时跳过 `summonLimit`（默认 64）检查 | `SummonSpell.java:62-81` |
| **拔刀剑：SA 与幻影剑消耗耀魂值** | 耀魂值存在**刀的 capability** 里 ⇒ **天然与主人共享**，谈不上"女仆自己攒" | `SlashArts.getProudSoulCost()` |
| **拔刀剑：格挡消耗耐久、受评价影响** | `RankPointHandler` 的判据是"主手有刀"的**任意实体**，不限于 Player ⇒ **女仆也会累积评价** | `RankPointHandler#onLivingDeathEvent` |

⚠️ **注意最后一条是好消息**：女仆**会**累积评价，所以"高评价免耐久格挡"这个机制对女仆**天然可用**。

**三种做法**：

| 方案 | 内容 | 代价 |
|---|---|---|
| **① 同规则** | 女仆共用刀上的耀魂值；主动补齐 Goety 的冷却与扣费 | 最"类玩家"、平衡最好；但要**主动写代码去补**（默认是白嫖的） |

**我的倾向：① + 允许在配置里切 ③。** 理由：你的核心诉求是"**类玩家**"，而"无限的资源"恰恰最不类玩家。
但请注意 **①需要额外工作量**——默认行为是 ③，这一点容易在后期才发现。

### Q8 ✅ **已决定：走位进动作层；换武器不做成动作；新增「撤退&脱战」** · 非攻击战术操作

**你的回复（三段，分别处理）**：

> 「后撤、突进这样的**技能式走位**放入动作层；**换武器直接体现在使用武器上**（即执行对应物品对应的动作时，若不是该物品则切换为该物品）；直接**增加一个技能：撤退&脱战**，其内容就是跑离对女仆有仇恨的目标，**优先玩家方向**。」

**⇒ 采纳。三段的处理方式不同，逐条明确：**

#### ① 走位（后撤 / 突进）⇒ **进动作层**（推翻我原来的"排除"倾向）

我原倾向"不进第一步清单"。**你否掉了它，理由是这些是"技能式走位"——它们来自操作映射，不是行为观察。**

| 新增动作 | 载体 | 说明 |
|---|---|---|
| `maid:retreat`（后撤） | `maid:body` | 向后位移，拉开与目标距离 |
| `maid:charge`（突进） | `maid:body` | 向目标方向位移 |

⇒ **它们不是 L3「战术级」**，而是 **L1/L2 的走位动作**。
[00](00-需求专业化重述.md) §1.1 里"L3 不含走位"那条**需要修订**：**区分「位移动作」（进动作层）与「走位策略」（属决策层）**。

#### ② 换武器 ⇒ **不做成动作，做成执行器的前置步骤**

**这条很关键，它简化了架构**：换武器不是"女仆可以选的一个动作"，而是**执行任何动作时的隐含前置**：

```
执行动作 x：
  1. 解析 x 需要的物品 i（见 [09] §4.5「W 项问题」）
  2. if (女仆主手 != i) → 先切换到 i        ← 换武器发生在这里
  3. 执行 x
```

⇒ **清单里不存在「换武器」这个条目**；它体现在**每个动作的 `carrier` 解析结果**上。
这与"类玩家"一致：玩家也不会"先按切换武器键，再按攻击键"——**他直接攻击，游戏自己换**。

> ⚠️ **由此产生一条 M2 的硬要求**：动作必须带**可解析的"需要的物品"**，
> 否则执行器无法知道要不要先换手。见 [09](09-动作空间与评分体系.md) §4.5。

#### ③ 新增动作「撤退 & 脱战」

| 字段 | 值 |
|---|---|
| **动作 id** | `maid:disengage` |
| **中文名** | 撤退 & 脱战 |
| **载体** | `maid:body`（**无需物品** ⇒ 无 W 项问题，永远可用） |
| **语义** | **跑离"对女仆有仇恨"的目标**，且**优先朝玩家方向** |
| **触发需求轴** | `SELF_SURVIVAL`（高）+ `MOBILITY`（高）⇒ 由弹簧自然选中 |
| **effects** | `DISPLACE`（位移）+ `SET_AI_STATE`（脱战） |
| **duration** | `CHANNEL`（持续逃跑，直到脱离仇恨或玩家改变局势） |

> ★ **这个动作与弹簧体系的契合度极高，值得说明**：
> 「残血时撤」正是 [09](09-动作空间与评分体系.md) §5.2 里 `自身血量 < 40% ⇒ SELF_SURVIVAL +0.6` 的直接后果 ——
> **不需要写"如果血少了就逃跑"这条规则**，弹簧会在生存需求升高时自动选中它。
> **这是把你的设计意图与既有评分体系连接起来的一条实证路径。**

> 📌 **「优先玩家方向」的实现要点（M4 时确认）**：需要一个"主人位置"的取向量
> （TLM 的 `EntityMaid` 有跟随/待命相关状态）。**逃跑方向 = 远离仇恨源 + 朝主人方向的加权合成**，
> 而不是单纯"远离"。具体权重留实现时定。

### Q9 ✅ **已决定：modid 用 `fight_like_player`** · 模组命名

### Q10 ★★ 「万法皆通对 Goety 保守」具体保守在哪？

你指出：万法皆通里**很多聚晶直接无法使用**，而你的 **调律师（`goety-tuner`）基本解决了大部分聚晶的施法问题**。

#### 已查明的差异（详见 [03](03-既有实现勘测.md) §5.5）

万法皆通的 `GoetyProvider` **确实**处理了 `IChargingSpell`（`handleChargingLogic` / `executeChargingShot` / `resetChargingCounters`），
也**确实**直接调 `spell.SpellResult(...)`（**不**用 `mobSpellResult`）。所以它的保守另有原因。

**字节码常量池引用计数（实测，最硬的证据）**：

| 符号 | 出现次数 | 含义 |
|---|---|---|
| `startUsingItem` | **0** | ★ **从不进入"使用中"状态** |
| `isUsingItem` | **0** | 同上 |
| `stopUsingItem` | **0** | 同上 |
| `mobSpellResult` | 0 | 直接调 `SpellResult` |
| `isSpellOnCooldown` | **1** | ★ **强制聚晶冷却** |
| `typeStaff` | **0** | ⚠️ **不做法杖学派匹配** |
| `getSpellTypes` | 0 | 同上 |

| # | 限制 | 证据 | 后果 | 等级 |
|---|---|---|---|---|
| 1 | ★ **从不 `startUsingItem`** | 上表三处均为 **0** 引用；而调律师实证 `AbstractBeam.tick()` 要求 `MobUtil.isSpellCasting(owner)`（= `isUsingItem() && 使用物是 IWand && 法杖里有聚晶`） | **所有"以光束实体为载体"的法术下一 tick 自毁**（腐化光束/震撼/炼狱一类） | ✅ **已查证** |
| 2 | **强制聚晶冷却** | `isSpellOnCooldown` 引用 1 处 + `setCooldown(...)` + `requiredCooldown` | 输出被节流 | ✅ **已查证** |
| 3 | **必须持有可用法杖** | `findSpellStaff(maid, data, spell)` / `getCurrentStaff` / `isUsableStaff(stack)` | 法杖缺失或不可用时**放不出来** | ✅ **已查证** |
| 4 | **可用聚晶限于聚晶包** | `isSpellBook(ItemStack)` 判 `instanceof FocusBag`；收集走 `FocusBagItemHandler` | 女仆只能放包里的聚晶 | ✅ **已查证** |

> ### ⚠️ 一处我的推断被推翻（记录在案）
>
> 我最初**推断**"万法皆通按学派限制法杖（`typeStaff`）导致大量聚晶不可用"。
> **实测反证**：`GoetyProvider` 常量池里 `typeStaff` 与 `getSpellTypes` 的出现次数**都是 0**。
> ⇒ 它**不做**学派匹配。这条推断**已删除**。

> **方法名"看起来该有"不等于真有。** 看到 `findSpellStaff` 就假设它做学派校验，是过度推断；
> **引用计数是比方法名更强的证据。**

#### ★★ 重要补充：要分成"Goety 侧"与"铁魔法侧"两件事看

后续对 `Closing Song` 实例的审计发现——**"万法皆通很保守"这个判断需要限定在 Goety 侧**：

| 侧 | 结论 | 原因 |

| 4 | 每法术冷却；CONTINUOUS 法术放完也吃整条 CD | — |

| **不在范围内** | `SEHelper` 的 `onSoulEnergyGain/Loss`（面向 `Player`）——按已定的**白嫖**决策**不补**，两者可分开处理 |

#### 我查到的东西（那次"全绿却不工作"共有四处独立缺陷）

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| 1 | **45 / 56 个 choice 动作的承诺时长 = 0**（漏字段 / 键名写错） | `catalog/data/maid_native.json` 10 条里只有 `melee_swing` 有 `duration`；`slash_art` 写 `chargeTicks: 9`，而旧 `commitOf` 只在 CHANNEL 分支读它 | 门控失效（每 5 tick 重选重执行）+ `finish()` 永不触发（弓永不松手） |
| 2 | ★ **走位被建成"可消费的需求"** | `charge` 的 `MOBILITY +0.8` / `retreat` 的 `MOBILITY −0.8`，而 `commit()` 执行后会 `subtract(u)` | **两个动作互相偿还对方 ⇒ 永久震荡**（"到处跑"） |
| 3 | 走位被**两处同时写** | brain 的 `SetWalkTargetFromAttackTargetIfTargetOutOfReach`（每 tick）+ 我们自己的 `navigate()` | 后退退不掉：一边想撤、一边被拉向敌人 |
| 4 | 我们的任务不是 `IRangedAttackTask` | `EntityMaid.java:1207-1217` 的方法体全在 `if (maidTask instanceof IRangedAttackTask)` 里 | **`performRangedAttack` 是空操作 ⇒ 箭永远射不出去** |

（另有一处数据级的"静默不可达"：13/54 个动作声明了 `custom` / `spellConditionsMet` 前置，
而游戏侧喂的是空表 ⇒ 包括「通用近战」在内全都拿不到 —— 见 [12](12-项目参考.md) §7。）

#### 为什么"走位是原子动作"这句话本身是错的

> **位移不是「可消费的需求」，而是「伺服误差」。**

「放一个 AoE ⇒ 群伤需求被满足了」是消费；
但「往敌人走 8 格 ⇒ 靠近需求被满足了」**是错的** —— 你走到之后，**下一步仍然需要继续靠近**。
⇒ 在"执行后扣减向量"的弹簧语义下，`charge` 与 `retreat` 会**互相偿还**，
形成无论注入什么向量都摆脱不掉的震荡。

★ **区分标准（本项目判据）**：
> **「这一步走完，我还需要再走一步吗？」**
> 需要 ⇒ 那是**步法**（持续意图）；不需要 ⇒ 那是**动作**（一次性、有明确代价的位移，如瞬步/传送）。

#### 委托方拍板的方案（A）与落地形态

| 项 | 决定 |
|---|---|
| **单位** | **步法（gait）＝ 并发槽位**：与手上的动作**同时进行**（可以边走边拉弓）；不进候选集、不参与评分、**不发布扣减影响器** |
| **驱动** | 由 `NeedAxis.MOBILITY`（唯一有向轴）的**符号**驱动方向；无强需求时**伺服在"站位"上** |
| **站位从哪来** | ★ **载体的属性**（`catalog/carriers.json` 的 `preferredRange`）⇒ 「手里拿什么就站什么距离」：弓 12 格、拔刀剑 3 格、法术 9 格、通用近战 2.5 格 |
| **导航写入者** | ★ **唯一**：已从 brain 移除 vanilla 的接近行为（它的"接近"职责由步法的伺服规则接替） |
| **接管规则** | 动作若自己需要导航（目前只有"撤退&脱战"），会**接管**导航，步法让位（且让位时连 `stop()` 都不能调） |
| **`charge` / `retreat`** | ❌ **从动作层降级**：它们不再作为动作存在，其语义变成步法的取值（方向 × 距离档） |
| **`disengage`** | ✅ **保留为动作**：它含**一次性决策**（`SET_AI_STATE` = 脱战、清空仇恨目标）；位移部分改为复用步法执行器 |
| **承诺的权威来源** | 两条并存：清单 `ticks` 作**兜底** + **执行器回报完成**作权威（弓=放箭后、枪=冷却结束）；另加**冷却账本**（`CooldownTracker`）负责瞬时动作的节奏 |

#### 否决的备选

| 选项 | 做法 | 否决理由 |
|---|---|---|
| B | 走位仍是原子动作，改成参数化族 + 唯一导航写入者 | 改动最小，但**动作承诺期内女仆无法移动** ⇒ 与玩家不一致（玩家能边走边拉弓），而且仍保留了"位移 = 可消费"的错误语义 |
| C | 走位交回 vanilla brain，只在"反常移动"时占用动作 | 最省事，但走位**不再进评分体系** ⇒ 「类玩家」的位移决策空间缩小，且 brain 与动作层仍有两处写入者 |

★ 这条决策同时**修正了 Q8 的一半**：Q8 说"走位进动作层"（作为**可选项**）是对的，
但"进动作层"的**具体形态**从"原子动作"改成了"并发步法"。

### Q19 ✅ **已决定（委托方 2026-09-30）：补齐执行层的三处，潜行类操作不做**

#### 委托方提出的两件事（原文要点）

> ① 「女仆根本潜行不了，直接把**真的需要潜行**的部分 pass 掉。我们只需要把**比较好实现**的部分实现为动作，再用另一个逻辑指挥它们。并不需要刻意实现每个可行的点。」
> ② 「我发现女仆**不会像预想中的"切换物品"**，手上拿着啥就用啥 —— 这里体现了一个**逻辑层次**的问题：
> 我们应该是**按女仆拥有的道具（包括物品栏）决定循环，循环决定动作，如果动作的道具不在手上则切到手上**；
> 从测试来看我们的逻辑并非如此（决定顺序略有不同）。」
> ③ 「**完善所有执行逻辑**，以达到完整"只差感知/思维层/WIP 部分"的地步。」

#### 我的核对结论（② 是对的，第三环此前根本不存在）

| 环 | 委托方的预期 | 我们的实现（修前） |
|---|---|---|
| ① 按**拥有的道具**（含物品栏）决定循环 | ✅ | ✅ `LoopSplit.MAIN_SLOTS` = 主手 + 盔甲×4 + 背包 + 女仆背包 + Curios，逐件解析 |
| ② 循环决定动作 | ✅ | ✅ `DecisionCycle` 最近邻选解 |
| ③ **不在手上就切到手上** | ✅ | ❌ **完全缺失** —— 候选集来自背包，而**所有执行器只看主手** ⇒ 实测就是"手上拿着啥就用啥" |

⇒ 这解释了委托方的观察，也说明 `ActionExecutors#isMainHandReady`（当时定义了却**从未被调用**）正是这一环的残骸。

#### 决策

| # | 决定 | 落点 |
|---|---|---|
| **1** | ★ **「换手」是执行器的统一前置步骤，不是一条动作** | `ActionExecutors#ensureCarrierInHand`：① 用**载体的同一条规则**判断手上是否已就绪；② 未就绪 ⇒ `TaskEquipUtil.tryEquipFromBackpack(maid, predicate)`（TLM 自己的**同步**换手原语，`IAttackTask#onFunctionCallSwitch` 同款）；③ 规则的槽位不含主手 ⇒ **不换**（如盾只在副手）。<br>输入来自解析结果的 `Resolution#evidenceOf(actionId)`（"这个动作当初是哪件物品让它可用的"）—— **执行路径与候选集必须来自同一次解析**。 |
| **2** | ★ **执行器必须回报成败** | `DecisionCycle.ActionExecutor` 由 `void` 改为 `boolean`：**没做出来 ⇒ 不扣代价、不进承诺、不记 lastChosenId**。此前无论成败都扣 ⇒ 弹簧会被"**没发生的事**"推动（换手失败、无执行器、没目标都照扣）。 |
| **3** | ★ **潜行类操作不做**（`slashblade:guard` / `guard_just`） | 理由三条：① `IInputState` 的命令集**只由客户端输入产生**（`MoveInputHandler` 是 `@Mod.EventBusSubscriber(Dist.CLIENT)` + `TickEvent.ClientTickEvent`，读 `LocalPlayer` 的按键再发 `MoveCommandMessage`）；② TLM **从不写**女仆的输入状态（整个 `compat/slashblade` 只有一处 `AttackManager.doSlash`）；③ 它还有**荆棘 ≥ 1** 的硬门槛（`Guard.java:100`）。⇒ 要做得自己造「输入模拟」，**投入产出比低**。 |
| **4** | **弹反投射物（`ArrowReflector`）记录但不实现** | 它**对女仆更可达**（只要我们能驱动招式 + `startUsingItem`，不碰输入状态、不挑附魔），但属拔刀剑一族（被 S1 卡着），且委托方明确"不必刻意实现每个可行点" ⇒ 记为 **D7 待拍板**，暂不进清单主体。 |

#### 顺带澄清一个被混为一谈的问题：「挡投射物」是**两条不同的路**

| | **`Guard`（潜行格挡）** | **`ArrowReflector`（挥刀/蓄力弹反）** |
|---|---|---|
| 触发 | 刀未损坏 + **荆棘≥1** + **在地面** + **潜行且不按移动键** + 攻击来自**正面** | 主手刀 + ★ **正在使用物品**（`getTicksUsingItem() > 0`）+ 附近有投射物 |
| 效果 | **取消伤害**（`LivingAttackEvent` cancelled）；非 just 且非高 rank ⇒ 刀 −1 耐久 | **把投射物弹回去**（`doReflect`：速度 3.5、朝目标） |
| 附魔 | **荆棘必需** | **无要求** |
| 出处 | `Guard.java:100`（★ 1.9.65 与 1.8.60 逐字一致） | `ComboState.java:173`（**每个招式的默认 tickAction**）+ `ArrowReflector.doTicks` |

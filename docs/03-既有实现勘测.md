### 2.1 `ISpellBookProvider` —— 就是"操作提供者"抽象

【已查证，`javap` 实测签名】

```java
public abstract class ISpellBookProvider<T extends IMaidSpellData, S> {
    protected abstract List<S> collectSpellFromSingleSpellBook(ItemStack, EntityMaid);
    protected List<S> collectSpellFromAvailableSpellBooks(EntityMaid);
    public abstract boolean isSpellBook(ItemStack);
    protected abstract void initiateCasting(EntityMaid);
    public abstract void processContinuousCasting(EntityMaid);
    public abstract void stopCasting(EntityMaid);
    public void castSpell(EntityMaid);
    public void updateCooldown(EntityMaid);
    public void refundCooldowns(EntityMaid, double);
    public void setTarget(EntityMaid, LivingEntity);
    public LivingEntity getTarget(EntityMaid);
    public boolean shouldStopWhenTargetInvalid(EntityMaid);
    public boolean isCasting(EntityMaid);
    public void onMaidJoin(EntityMaid);
    // + 数据生命周期：getData / removeData / clearAllData / hasData
}
```

**读法**：泛型参数 `S` 是"该 provider 的操作类型"——
- `IronsSpellbooksProvider`：`S` = 法术
- `GoetyProvider`：`S` = `ItemStack`（**聚晶物品就是操作单元**）
- `SlashBladeProvider`：`S` = `ResourceLocation`（**刀的 ID / 招式 ID**）

⇒ 它已经建立了"**从一个物品/书里收集出一组可执行操作**"这个抽象。这正是 [00](00-需求专业化重述.md) §4 所描述的东西，只是它叫 `provider`。

### 2.2 与 TLM 的对接方式

它注册了两个 `IMaidTask`（`SpellCombatMeleeTask` / `SpellCombatFarTask`），任务内挂行为节点调用 `SimplifiedSpellCaster.melee_tick()` / `far_tick()`。

⇒ **它是"另起两个任务"，不是改造 `TaskAttack`。** 这是与 TLM 共存的正确姿势，也是本项目可以沿用的姿势。

### 3.4 它怎么做到服务端可达（关键技术）

【已查证】

1. `SlashBladeDirectSkills` 直接调用 **`mods.flammpfeil.slashblade.util.AttackManager`** 的静态方法，
   签名（从字节码常量池读出）：
   ```
   AttackManager.doSlash(LivingEntity, float, Vec3, boolean, boolean, double, KnockBacks)
       -> EntitySlashEffect
   ```
   ⇒ **R-A 级可达**：拔刀剑的核心招式在服务端有公开静态入口。TLM 自己的 `SlashBladeCompat` 用的也是它。

2. `SlashBladeDirectSkillHandler` 直接操作 **`mods.flammpfeil.slashblade.entity.EntitySlashEffect`** 与
   **`EntityAbstractSummonedSword`**（斩击特效实体与幻影剑实体）来后处理。
   ⇒ 组合招式靠"生成实体 + 改写实体参数"拼出来，属 R-B。

3. `SlashBladeProvider.lambda$performSlashBladeComboAttack$8(… ISlashBladeState, IInputState)` —— 引用
   **`mods.flammpfeil.slashblade.capability.inputstate.IInputState`**。
   ⇒ **【推断】**它通过**写入"输入状态"capability**去满足拔刀剑自己的连击状态机，从而复用原版连击判定，而不是重写一遍。
   这是"女仆无手指"这一约束下最优雅的解法，值得重点验证。**【待验证】具体写入时机与内容。**

**→ 这直接回答了 [00](00-需求专业化重述.md) §6.1 提出的可达性疑问：拔刀剑是可做的，且路子已经探明。**

## 5. 它的"决策层"长什么样 —— 这才是真正的缺口

这是本次勘测最有价值的判断。

【已查证】`SlashBladeProvider` 的决策逻辑全部是**硬编码的私有方法 + 随机**：

```java
chooseCombatAction(maid, data, target, boolean)   // 4 选 1
  ├─ shouldUseSlashArt(...)   → boolean 启发式
  ├─ shouldUseDirectSkill(...) → boolean 启发式
  └─ selectRandomSkill(maid)   → ★ 随机挑一个 DirectSkill
```

特征：
1. **动作选择是随机的**（`selectRandomSkill`、`RANDOM_JUMP_CHANCE`、以及 TLM 自身的 `roll = random.nextInt(60) - 30`）。
2. **优先级是不可配置的 `boolean` 判断**，写死在 Java 里。
3. **没有任何数据驱动的行为描述**（没有 JSON/数据包/编辑器）。
4. 想改行为 = **改代码 + 重新编译**。

⇒ **它解决了"女仆能做什么"（动作空间），但没有解决"女仆何时做什么"（可搭建的决策）。**

> 🎯 **这正好是你两步规划里第二步要填的坑，而且证明你的两步划分是对的。**
> 你的"第一步：操作清单"在这个模组里**已经存在**（31 个 `DirectSkill` + 8 个 provider）；
> 你的"第二步：可便捷搭建的行为逻辑架构"在这个模组里**完全空缺**。

## 5.5 ⚠️ 第二份既有实现（更关键）：调律师 `goety-tuner`

> 这一节是**你的反馈带来的重大修正**，请与 §4 对照阅读。

你指出：**万法皆通对 Goety 的用法很保守，很多聚晶直接无法使用**；
而**你自己的「调律师」（`goety-tuner`）基本解决了大部分聚晶的施法问题**。

⇒ 因此本项目存在**两份**既有实现，而且**不是同一水平**：

| | **万法皆通** `touhou_little_maid_spell` | **调律师** `goety-tuner` |
|---|---|---|
| 定位 | 给女仆加施法（面向玩家体验） | 一个指挥聚晶的 Boss + 一个可被指挥的仆从 |
| 许可 | MIT（DreamCat） | **MIT（`Copyright (c) 2026 QieFanQie`，你自己）** |
| 规模 | 382 个类 | **59 个 `.java`**、122 个 jar 条目、77 项配置 |
| **Goety 施法覆盖** | ⚠️ **保守**（很多聚晶不可用） | ✅ **基本解决大部分聚晶**（你的原话） |
| mob 施法入口 | 未走官方 mob 入口 | ✅ `spell.mobSpellResult` |
| **通道类（长按）法术** | ❌ 未解决 ⇒ 这是保守的根因之一 | ✅ `CastChannel.tickChannel` + 自备 `TunerWand` |
| 施法者身份 | `Player` / `mob` 两条路 | ✅ mob 专用路径 |
| 决策层 | `selectRandomSkill()` **随机** + 死写 `boolean` | **聚晶池 + 分类 + 轮盘赌 + 动态学习权重**（更成熟） |
| 可复用性 | 抽象（`ISpellBookProvider`）与本项目**不匹配** | ✅ **你自己的代码，零障碍** |

**⇒ 直接结论：Goety 侧的参考实现应当是调律师，而不是万法皆通。**
机制清单与"可复用机制 + 踩过的坑"见 [05-许可与代码复用](05-许可与代码复用.md) §5 与 §6。

> 📌 **这也解释了一个疑点**：§4.1 说"万法皆通未发现潜行变体与仆从管理"。
> 你的反馈印证了这个观察——它确实是保守的，不是我的检索遗漏。

## 7. 定位选项 ✅ **已决定：选项 B（独立模组）**

> **你的决定：新建独立模组。**
> 但请注意——结论里"工作量最大"这一句在本轮**被大幅削弱了**：

看清上面这张表之后，有三条路，代价与收益差别很大：

### 选项 A · 扩展万法皆通
在你的整合包里以附属/PR 形式，给它补上缺的那几块（召唤物管理操作、施法变体、数据驱动行为层）。
- ✅ 复用它的 8 个 provider、31 个 DirectSkill、全套状态管理，工作量最小
- ✅ 与现有存档/玩家配置零冲突
- ❌ 受它的架构约束（Java 枚举 + 手写 provider，要改数据驱动得动它的核心）
- ❌ 依赖第三方作者的意愿与节奏（除非你 fork）

### 选项 B · 新建独立模组，做"通用操作层 + 可搭建行为层"
即本项目：定义统一的**操作清单 schema** + **可达性分级** + **数据驱动的行为作者化**，并把万法皆通视为**已有的 provider 之一**（兼容/桥接，而非重写）。
- ✅ 与你的两步规划完全对齐；第二步（行为架构）是万法皆通明确没有的
- ✅ 不重复造拔刀剑/聚晶的轮子，而是**把它泛化**
- ✅ 与 `fight_feed_back`（观测层）形成完整闭环
- ❌ 工作量最大；需要先证明"通用 schema"确实能容纳异构模组

### 选项 C · 先只做清单与规范，不写代码（**即本次交付**）
把操作清单做成**与实现无关的规范文档 + 数据**，同时对既有实现做完整勘测（本文）。
- ✅ 成本最低；产出的规范对 A、B 两条路都有用
- ✅ 你说的第一步本来就是"操作列表"，而不是"写代码"
- ❌ 不产生可运行的东西

> **我的建议：C → B**。
> 先完成清单与规范（C，本次），再据此决定是 B（新建）还是 A（扩展）。
> 理由是：无论走哪条路，**"女仆侧有哪些原子动作"和"每个动作服务端可达性如何"这两份信息都是必需品**，
> 而且目前**没有任何地方**把它们集中写下来——它们散落在万法皆通的 382 个类里。

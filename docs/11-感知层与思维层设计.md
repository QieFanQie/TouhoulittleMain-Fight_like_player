## 3. 感知层：建议的数据结构

**建议做成一个独立的纯数据记录**（放在 `carrier` 包，**零 Minecraft 依赖** ⇒ 可离线断言）：

```java
public record Perception(
    // ── 战斗目标 ──
    int enemiesTotal, int enemiesFront, int enemiesOther,
    double nearestEnemyDist,
    double enemyHpSumPct, double enemyHpMinPct,     // 血量汇总 / 最虚弱的那个
    double threatFront, double threatOther,         // 前方 / 其余方向的威胁加权

    // ── 自身 ──
    double selfHpPct, double selfArmor, int selfFireTicks,

    // ── 环境 ──
    int standableBlocks,                            // 可站立方块数
    double dangerScore,                             // 环境危险度（岩浆/悬崖/着火…）

    // ── 仆从 ──
    int servantCount, double servantHpSumPct, int servantDownCount,

    // ── ★ 面向玩家的提示 ──
    List<Broadcast> broadcasts,                     // Boss 血条 / 模组播报
    long gameTime, int tickSpan                     // 这一包覆盖的时间窗
) {}
```

### 3.1 ★ 三个必须解决的问题

| # | 问题 | 建议 |
|---|---|---|
| **P1** | **频率与成本**：委托方说"1~1.5 秒一次"。但决策周期是 **5 tick (0.25s)** ⇒ 感知**比决策慢 4~6 倍** | 感知结果**缓存**，决策层读缓存（不重复扫描）。★ 但**"是否需要立刻重扫"要有触发条件** —— 例如"刚刚被打了""目标变了"⇒ 立即重扫（否则会出现"怪物已经贴脸了但感知还是 1 秒前的"） |
| **P2** | **N 个女仆 × 扫描频率** —— 20 个女仆各扫一遍是 O(N×范围²) | 用**按区块/按区域**的共享扫描：同一区域的女仆共用一次怪物枚举；并设**每 tick 扫描上限**（超了排队），避免卡服 |
| **P3** | **前方扇形的定义**：`facing` 与"前方"的夹角阈值？ | 建议 **±60°（共 120°）** + 距离加权（越近权重越高）。**不是**简单计数 —— 3 个怪在 20 格外与 3 个怪在 2 格外完全不是一回事 |

> ★ **P3 特别重要**：委托方举例是"前方扇形的怪物信息和除此之外的怪物信息"。
> 若只做**计数**，短周期思维拿到的信息会**丢掉距离**，而距离恰恰是"该突进还是该后撤"的关键。
> ⇒ 建议按**距离分档**（近/中/远）各自计数，或直接给"最近的 3 个怪的距离"。

## 4. ★★ 播报（Broadcast）：先收集原版有哪些方式

委托方问："先收集一下原版可能的方式。"

### 4.1 原版可用的"面向玩家的提示"通道

| 通道 | 服务端可读？ | 内容 | 本项目的用法 |
|---|---|---|---|
| ★ **`ServerBossEvent`** | ⚠️ **需要拦截** | Boss 血条：名称、进度、颜色、是否可见 | **只能"我们主动创建"** —— **读不到其它模组创建的 Boss 血条**（它是客户端 `BossEvent` 的注册表，服务端没有"列出所有 Boss 血条"的 API） |
| **`Level#getEntitiesOfClass`** | ✅ 直接可读 | 实体本身 | ★★ **最可靠的路子**：`EnderDragon` / `WitherBoss` / `Warden` 等**看实体就能判断**（Boss 有 `getPhase()`/血量阶段） |
| **`BossEvent` 的血量阶段** | ✅ 通过实体读 | 末影龙 `getPhase()`、凋灵的无敌帧、监守者的蓄力 | ★ **这才是"boss 正在使用大招"的原版对应物** —— 不是提示文本，而是**实体状态** |
| **`/title`、`/tellraw`、`actionbar`** | ❌ 只能发，不能收 | 文本 | 发得出去，**收不到别人发的** |
| **`ClientboundSetTitleTextPacket`** | ❌ 客户端包 | 标题 | 服务端不经过 |
| **聊天事件 `ServerChatEvent`** | ✅ **可监听** | 所有聊天消息 | ★ **唯一能"听到"玩家可见文本的服务端钩子** —— 但只覆盖**聊天频道** |
| **`Raid`（袭击）** | ✅ | `Level#getRaids()` | 原版的"事件进度"范例 |
| **`BossEvent` 的原版创建者** | —— | 末影龙 / 凋灵 / 袭击队长 | **原版只有这 3 个 Boss 会创建 Boss 血条** |

### 4.2 ★ 结论：**"读播报"这条路在原版基本走不通**

| 想读 | 能否 | 替代方案 |
|---|---|---|
| 别的模组的 **Boss 血条** | ❌ 服务端无枚举 API | 读**实体**（血量、阶段、是否 Boss） |
| 别的模组的**提示文本** | ❌ 发得出去、收不回来 | 监听 `ServerChatEvent`（**只覆盖聊天**）；或**每个模组单独适配**（见 WIP） |
| **"boss 正在放大招"** | ⚠️ 没有通用信号 | ★ **改成读实体状态**：蓄力动画帧、无敌帧、`getPhase()`、AI 目标切换。**比读文本更可靠、更实时** |

> ★★ **一个重要的设计建议**：
> **把"播报"从"文本"重新定义为"可观测的世界事件"**。
> 委托方要的其实是"**现在有没有值得我立刻反应的事**"，而：
> - 文本播报 → **滞后、易漏、需要逐模组适配**；
> - 世界事件 → **实时、通用、可离线断言**。
>
> ⇒ 建议感知层产出的是 **`List<ThreatSignal>`（威胁信号）**，而不是文本：
> ```java
> record ThreatSignal(Kind kind, double severity, ResourceLocation source, String hint) {}
> // Kind: BOSS_PHASE_CHANGED / BOSS_CHARGING / ALLY_DOWN / EXPLOSION_NEARBY /
> //       MOD_BROADCAST(文本类，尽力而为) / ...
> ```
> **文本播报只是 `Kind` 的一种**（且是可靠性最低的一种）。

### 4.3 逐模组播报适配（WIP · 以后收录）

登记为 **W26**：收集各联动模组的"播报"实现方式。已知的候选形态：

| 形态 | 例子 | 可读性 |
|---|---|---|
| 聊天消息 | 多数模组 | ✅ `ServerChatEvent` |
| 动作栏 / 标题 | 战斗类模组常见 | ⚠️ 需逐个找钩子 |

## 5. 思维层：澄清与决议

### 5.0 ★★ 先回答：「规则版」是什么？没有思维层，决策向量从哪来？

> 委托方的质疑：「不对啊，没有思维层，哪来的一开始的决策向量呢？
> 没有决策向量弹簧空间就不会震荡，进一步就不会残血就撤。」

**质疑的逻辑完全正确**：没有决策向量 ⇒ `p` 恒在原点 ⇒ 命中死区 ⇒ 只会走默认动作 ⇒ **不会残血就撤**。

**但"决策向量"确实有来源** —— 不是思维层，而是 **`ContextBias`（态势基线偏置）**：

| 项 | 说明 |
|---|---|
| **它是什么** | 一张**手写的规则表**（8 条），把"当前局势"翻译成 8 轴向量。实现在 `carrier/ContextBias.java`，规格见 [09 §5.2](09-动作空间与评分体系.md) |
| **它的来源** | [09 §2.2 修正 ⑥](09-动作空间与评分体系.md) —— 当时就写明：「思维层先不做 ⇒ `a = 0` ⇒ **弹簧永远停在原点**」是**致命问题**，所以必须先有规则版替代品 |
| **它的定位** | ★ **思维层接入前的替代品，接入后的兜底**（是设计的一部分，不是临时 hack） |

**规则表的核心几条**：

```
有目标且在射程内   ⇒ SINGLE_DAMAGE +0.3
附近敌人 ≥ 3 / ≥ 6 ⇒ AREA_DAMAGE +0.4 / +0.8（分档，不叠加）
自身血量 < 40%     ⇒ MITIGATION_SURVIVAL +0.6
自身血量 < 15%     ⇒ MITIGATION_SURVIVAL +1.0、SINGLE_DAMAGE −0.5
主人血量 < 50%     ⇒ ALLY_CARE +0.5
距离目标 > 8 格    ⇒ MOBILITY +0.3（正 = 想靠近）
附近无敌人         ⇒ 全 0 ⇒ 死区 ⇒ 默认动作
```

**★ 实测证据（不是推演）** —— `PipelineSelfTest` 走的是**真实的 `ContextBias` 规则**
（该测试**刻意不自己塞偏置**，就是为了能发现"实现为 0"这类问题）：

| 情境 | 规则产生的偏置 | 弹簧选中的动作 |
|---|---|---|
| 满血 100%、1 敌、4 格 | `[单点=0.300]` | `slashblade:slash_art`（攻击） |
| **残血 12%**、1 敌、4 格 | **`[免伤=1.000]`** | ★★ **`fight_like_player:disengage`（撤退&脱战）** |

> ⇒ **"残血就撤"完全由规则版产生**，链路上**没有任何模型**。它由三件事凑齐：
> ① 规则产生 `免伤 +1.0` 的决策向量；② 弹簧把它变成"免伤需求"；
> ③ `disengage` 的向量是 `免伤 0.8 + 位移 −0.9`，**离这个需求最近**。
>
> ★ **术语澄清**：我此前说"思维层不是前置"，准确说法应是
> **"模型（JEV/LLM）不是前置"**。若把"产生决策向量的东西"统称为思维层，
> 那么规则版**就是一层极简的、手写的思维层** —— 它没有推理能力，但**足以产生决策向量**。

**⚠️ 规则版的局限（说清边界，免得高估）**：

| 做不到 | 需要思维层 |
|---|---|
| "Boss 在放大招，先躲开"（要理解"大招"是什么） | ✅ |
| "这个敌人打不动，换个目标"（要评估收益） | ✅ |
| "主人要的是压制不是击杀"（要读意图/基调） | ✅ |
| **残血就撤 / 群怪就 AoE / 远了就靠近** | ❌ **规则版已能做** |

### 5.1 短周期的输出：**打分 → 决策向量**（P1 已定：按 8 轴直接打分）

| 项 | 决议 |
|---|---|
| **打分维度** | ★ **直接按 8 轴打分**（委托方 P1）—— 少一层失真，量纲天然对齐弹簧 |
| **量纲约束** | 遵守 [09 §3.1](09-动作空间与评分体系.md)：除 `MOBILITY` 双向 `[-1,1]` 外其余 `[0,1]`；**负值 = 代价** |
| **输出接口** | `SpringImpact.bias(...)` —— 与 `/flp bias` 命令**同一个接口** |
| **无上下文 ⇒ 抖动** | 每包独立 ⇒ 同一局势两次判断可能不同 ⇒ 调小 `SpringConfig.jitter`；由**长周期基调**做稳定项 |

### 5.1b ★★ 短周期**已实现**（2026-10-01）—— 落地形态与取证

> 委托方 2026-10-01：「关于思维层，调用 jev 的部分……**要写好 API 配置接口，做到在 MC 的模组配置界面配置**。
> **长线思维先不做。**」⇒ 本节就是这次落地的权威描述。

| 环节 | 落地物 | 关键决定（都有理由） |
|---|---|---|
| **接口客户端** | `decision/thinking/JevClient.java`（纯逻辑，**零第三方依赖**：JDK `java.net.http` + Gson） | ① 只走 `POST {base}/responses`，请求体固定 `model/input/state/questions`（`input` 是**占位符**，缺了报 `input is required`）；② **绝不用 `/chat/completions`**（永远路由不到渠道 + 计费口径不对）；③ ★★ **内置本地预校验** —— 网关会把"请求体不合法"统一伪装成「无可用渠道」，不本地拦住就永远看不到真原因 |
| **局势翻译** | `ThinkScene`（纯 record）+ `ThinkPrompt.state()` | ★ **英文提示词**（JEV 训练以英文为主）；★ **不喂弹簧点** —— 否则"她想 X → 模型说 X → 更想 X"是正反馈回路；★ 无目标时的 `Double.MAX_VALUE` 必须译成 `-1 + distance_is_valid=false`（**自测抓到的真 bug**） |
| **问题集** | `ThinkPrompt.questions()` —— **8 条轴各一问，全 `score` 5 档** | ★ 不问"选哪个动作"：动作清单会增删、模型也看不到 `v_x` ⇒ 那会造出**第二套不一致的评分标准**。★ 位移单独一套**有向**等级（`MOBILITY` 是唯一"负值有语义"的轴）。★ 取 `score` 的**连续分**而不是 argmax（JEV 的价值就在分布） |
| **答案→向量** | `ThinkPrompt.verdict()` | 无向轴 `v = score/4 ∈[0,1]`；位移 `v = (score−2)/2 ∈[−1,1]`；★ **缺轴记 0 并登记**（不猜默认值）；★ 越界**钳制**而不是丢整包；★ 置信度取**各轴最小值** |
| **调度器** | `Thinker.java`（纯逻辑，`Transport` 可替换） | ★★ **线程铁律：HTTP 回调里只写原子量**（结果由主线程 `poll()` 取走）—— 碰 `EntityMaid`/`SpringSpace` 就是崩服。★★ 在途用**代次**（`AtomicLong` + CAS）而不是计数器 ⇒ **迟到的旧结果无法清掉"新一代在途"状态**。★★ 失败**绝不传染**：UDP 式丢包，弹簧沿用旧值 |
| **配置** | `config/FlpConfig.java`（`ForgeConfigSpec`，COMMON）+ **自带配置界面** `compat/client/FlpConfigScreen.java` | ★★ **Forge 47.3.22 没有内置配置界面**（反汇编取证见下）；★ **默认关闭 + 不填 Key 不发任何请求**；★ 界面做**三页**（每页 ≤5 行 ⇒ 任何 GUI 缩放下都放得下，不必自己写滚动）；★ Key 用**掩码/明文切换**而不是 `EditBox` 的 formatter |
| **接线** | `compat/think/ThinkBridge.java` + `PlayerLikeCombat` 的 **1b 步** | 位置刻意在**主循环之前**：本 tick 取到的判定能在**同一个 tick** 被 drain。发布的就是 `SpringImpact.bias(vec, "think:jev", label)` |
| **诊断** | `/flp think` · `/flp think now <女仆>` · `/flp think last <女仆>` | 延续 [13 第 19 条](13-更正记录与教训.md)：**可预期的失败必须有用户可读的出口**（含把「无可用渠道」翻译成人话） |

**★★ 一条必须在文档里留痕的取证（否则下一个人会重犯）**：
我原以为"用 `ForgeConfigSpec` 注册配置，Forge 就会自动给一个配置界面"。反汇编
`forge-1.20.1-47.3.22-universal.jar` 后确认**这是错的** —— 整个 Forge 里与配置界面相关的类
**只有** `net.minecraftforge.client.ConfigScreenHandler`（一个**扩展点**）：
```java
static Optional<BiFunction<Minecraft, Screen, Screen>> getScreenFactoryFor(IModInfo)

### 5.1c ★★ LLM「实时调控」的可行性决议（委托方 2026-10-01 第 6 条设想）

**委托方的设想原文**：
> 「接入一个 LLM 实时调控机制：LLM 不直接决定战斗，但可以决定**风格**和**决策**；
> LLM 可以知道女仆的一些参数和日志情报，我们尽量从**统计结果**的方式输入以节省上下文；
> LLM 可以通过输出**指令**来调整我们这个体系的各个参数。就类似于**动态调试**。」

#### 结论：**可行，而且这个方向比「让 LLM 选动作」正确得多。**

理由是**影响面**：
<pre>
  LLM 选动作   → 单次判断错了 = 那一次战斗做蠢事（而且动作清单会变、模型看不到 v_x）
  LLM 调参数   → 单次判断错了 = 一组【有界】的旋钮偏了一点，最坏情况被钳制住
</pre>
⇒ **它把「模型可能犯错」的影响面从「一次战斗」缩小到「一组被钳制过的数字」。**
这是整条设想里最值钱的一点。

#### 关键：它是**第三层**，与前面两层的时间尺度不同

| 层 | 输入 | 时间尺度 | 它改什么 | 状态 |
|---|---|---|---|---|
| **决策层**（②③） | 当前需求 + 候选集 | 5 tick | 这一步做什么 | ✅ 已有 |
| **短周期思维**（④a） | 当前局势快照 | ~1.5 秒 | 弹簧点**这次**往哪推 | ✅ 已有（JEV） |
| ★ **调控层**（④b，本节的设想） | 一段时间的**行为统计** | **十秒 ~ 分钟** | 体系长期的**性格** | 🟡 **地基已落地** |

⇒ 三者互不替代。**调控层只动参数，永不直接产生动作** —— 这就是「不直接决定战斗」的精确含义。

#### 已落地的地基（`TuningBus`，2026-10-01）

设想的前提是「体系里有一组**有名有界、可读写**的旋钮」。⇒ 已实现
`decision/TuningBus` + `/flp tune` 命令（★ 刻意**先做不依赖 LLM 的入口**：
否则「调参」永远要先接模型才能试，就没法验证旋钮本身是否有效、是否安全）：

| 旋钮 | 范围 | 作用 |
|---|---|---|
| `satisfaction.all` | 0.1~2 | 动作扣减弹簧的**整体**倍率 |
| `satisfaction.damage` | 0.1~2 | 只作用于扣减时的**单点/群伤**分量 |
| `cooldown.scale` | 0.2~5 | 所有动作最小重复间隔的倍率（节奏） |
| `failure.backoff` | 1~16 | 连败退避上限（「选中却做不出来」的保险丝） |
| `bias.aggression` | 0~2 | 态势偏置里**进攻**分量的倍率（风格） |
| `bias.caution` | 0~2 | 态势偏置里**生存**分量的倍率（风格） |

**三条安全设计**（缺一条都不能让外部输入来写）：**白名单**（未登记的键被拒且原因可读）·
**硬钳制**（越界钳到边界而不是接受）· **可回退**（`/flp tune reset` 一键复原）。

#### ✅ 已实现（2026-10-01，第 7 轮）

委托方第 3 条「制作并完善 LLM 动态指挥机制」⇒ 上面那 5 步里的 **第 1~4 步已经做完**
（第 5 步「开关不劣化」的验收留待实机）：

| 环节 | 落地物 | 关键决定 |
|---|---|---|
| 统计聚合 | `decision/thinking/BehaviorStats` | 滑窗 200 tick；**统计项与旋钮一一对应**；上下文长度与战况复杂度脱钩 |
| 问题集 | `Advisor.questions()` | ★ **一个旋钮一个 `score` 问题**（不是「让模型写 JSON 补丁」）—— 见下 |
| 映射 | `Advisor.patch()` / `valueFor()` | ★ **中档 = 默认值**（严格相等）⇒「不动」是不动点；两端钳在 `[min,max]` |

**★★ 为什么是 `score` 而不是「自由 JSON 补丁」**（本节最重要的设计决定）：
JEV 是 System One 模型，**只回答 `noul`/`choice`/`score`，不会写自由文本**；
而自由文本补丁要面对「值不合法 / 键不存在 / 越界」的一整套校验 ——
**在 `score` 形态下这些由构造保证不可能发生**：答案是 0~4 的连续分，映射区间是我们写死的。
⇒ 这比「让模型输出一段 JSON 再解析」**同时更简单、更可控**。

**★ 映射为什么要以默认值为中档**：若线性铺满 `[min,max]`，「中间档」会落到 `(min+max)/2`，
而它**通常不是默认值**（`cooldown.scale` 默认 1.0、区间 0.2~5.0 ⇒ 中点 2.6）
⇒ 模型每答一次「中间」，体系就被推离默认一次，几十轮后漂到边界。
⇒ 分段线性 + **`score=2` 严格等于默认值**，并让「设成默认值」等价于「撤销覆盖」。
**这一条有断言**（「全答保持 ⇒ 总线仍是默认状态」）。

**★ 可调的 5 个旋钮**：`satisfaction.damage`（委托方第 5 条要的那个）· `satisfaction.all` ·
`cooldown.scale` · `bias.aggression` · `bias.caution`。
**`failure.backoff` 刻意不在其中** —— 它是保险丝，不该被「风格」改掉（也有断言）。

**⚠️ 已知限制（第九轮已解除）**：旋钮曾是**全局**的，而统计是**每女仆**的 ⇒ 两个女仆会抢同一组旋钮。
现已改为 **`TuningBus.independent()`**：每女仆一条**活的继承**总线（没单独调过就跟着全局走，
单独调过就只影响她）—— 见 [13 §32](13-更正记录与教训.md)。

★ **不要**把「当前局势」喂给调控 LLM —— 那是 ④a 的活，会重复而且贵。
调控层的输入应当是**聚合统计**（委托方自己提的「尽量从统计结果输入以节省上下文」，完全正确）：

```

### 6.1 「假打分」到底指什么（P5 澄清）

> 委托方问：「假打分是指？jev 实时打的是决策向量分，判断局势的。」

**我说的"假打分"不是伪造 `v_x`**，而是**把"产出决策向量"这一环换成人手**：

```java
// 真思维层：JEV 读一包感知信息 → 产出 8 轴决策向量 b
NeedVector b = JevClient.score(perceptionPack);   // ← 外部模型，不可离线验证

// "假的打分源"：手工注入同一个 b
/flp bias <女仆> 0.3 0.8 0 0 -0.5 0 0 0           // ← 走【同一个接口】SpringImpact.bias
```

⇒ **两者产出的是同一种东西（8 轴决策向量）**，只是一个来自模型、一个来自人手。
把模型那一环换成命令，就能**先验证"决策向量 → 行为"这一段**，再接模型 ——
出问题时能立刻判断是**架构错**还是**模型判断错**。

★ **已实现**：`/flp bias` · `/flp spring` · `/flp reset` · `/flp status` · `/flp axes`
（`compat/command/FlpCommands.java`）。注入走的是与真思维层**完全相同**的接口。

## 7. ⚠️ 一个必须提前想清的问题：**思维层的验收标准是什么？**

现在的每个里程碑都有**明确的、可断言的验收标准**（断言数、覆盖率、S0/S1 复测）。
但"思维层更聪明"**无法这样验**：

| 候选验收标准 | 问题 |
|---|---|
| "行为看起来更像玩家" | 主观，不可回归 |
| "打赢了更多场战斗" | 噪声大（怪物种类、装备、地形都在变） |
| "强制指令被正确执行" | ★ **这个可验**（机械通路） |
| "基调在残血时变保守" | ★ **这个可验**（给定感知 ⇒ 断言基调） |

> ⇒ **建议：把思维层拆成"可验的机械部分"与"不可验的判断部分"**：
> - **机械部分**（指令是否执行、基调是否影响偏置、异步是否不阻塞）⇒ **必须有断言**；
> - **判断部分**（JEV/LLM 判断得好不好）⇒ **只做"不劣化"验收**：
>   ★ **关掉思维层时行为不能变差**（即思维层是"增强"而非"必需"）。
>
> ★★ 这一条很重要：**如果思维层不能证明"比规则版更好"，那它就不该进主干。**
> 规则版（`ContextBias` + 弹簧）现在已经能产生"残血就撤"这类行为，
> 思维层的价值必须是**增量**，而不是重复。

### 8.3 ★ 一个被"更好的打分"暴露出来的语义 bug（已修）

子代理给 4 条 Goety 管理动作打了**全 0 分**（`execute_servant` / `dismiss_temporary_servants` /
`set_servant_stance` / `transfer_servant_ownership`），理由充分："它们确实没有战术价值"。

**但当时评分表统计出现"56 条里有 4 条不可评分"** ⇒ 暴露出 `hasVector()` 的实现是：

```java
return defaultVector != null && !defaultVector.equals(NeedVector.zeros());  // ❌
```

⇒ **"明确判为 0 分"被当成了"没打分"**，动作会被 `NO_VECTOR` 丢弃。

**修正**：判据只看 `!= null` —— **"零向量"与"缺失"是两件事**：
- `vector: {}` ⇒ 已评分，价值为 0（作者的判断）
- 没有 `vector` 键 ⇒ 未打分 ⇒ 丢弃

> ★ 修好之后，这 4 条动作**可用但永不被选中**（零向量离任何非原点需求都最远），
> **正是委托方要的"先留着"** —— 留给将来的**直接指令表**去点名调用。

### 8.4 ★ 一条关于"多样性"的实测经验（重要）

改成逐条重打的评分后，`PipelineSelfTest` 的旧断言"**恒定环境下应出现多个不同动作**"**失败了** ——
弹簧在恒定群怪环境下**连续 6 次选中同一个** `spiral_swords`。

**分析**：那次断言以前能过，是因为**启发式打分很粗糙**（拔刀剑全族 `SINGLE_DAMAGE 1.0`）
⇒ 那是「**噪声带来的假多样性**」，不是真行为。

★ **而收敛到同一个动作是正确的**：局势不变、需求不变 ⇒ 最优解不变 ⇒
反复用同一个最好的 AoE **正是玩家会做的事**。

⇒ **断言改成**：
- **局势变化 ⇒ 选择随之变化**（群怪→AoE、单敌→单体、濒死→撤退）；
- **恒定局势 ⇒ 收敛稳定**（不乱跳）。

**实测结果**：

| 局势 | 选中 | 是否符合直觉 |
|---|---|---|
| 群怪（6 敌） | `slashblade:spiral_swords`（幻剑阵，AoE） | ✅ |
| 单个敌人 | `slashblade:summoned_sword`（单发幻影剑） | ✅ |
| **濒死 12%** | **`fight_like_player:disengage`（撤退）** | ✅ |
| 恒定群怪 ×6 | 稳定同一动作 | ✅ |

> **教训（第 13 条）：粗糙的输入会制造"看起来对"的假象。**
> **打分变准之后，旧断言反而失败** —— 这正说明那些断言测的是噪声，不是行为。
> ⇒ 遇到"改进之后旧测试挂了"，先怀疑**测试的期望**，而不是新数据。

## 1. 原始需求（保留你的原话，便于日后复核）

> 我希望制作一个新的"**类玩家**"战斗模式：
> 即基于玩家的操作选择来重构女仆的逻辑：比如女仆使用拔刀剑时，由于拔刀剑面向玩家的操作有："左键/右键/长按右键/shift+……"等等操作，则对于该模式的女仆而言，这些不同操作对应的是不同可选项（**看作同一个东西**，对于玩家是某一套操作，对于女仆而言是某一个独立的技能，即**由玩家的操作视角来分割女仆技能使用**）。
> 比如对于聚晶，则是不同聚晶对应的右键操作、加上玩家主动的"处死仆从"等。
> 即**把玩家的操作对应的效果视作技能，作为女仆的操作**。
> 女仆角度：**一个操作列表中有所有目前可行的操作**。这是第一步，第二步是设计可便捷搭建的女仆行为逻辑架构。先不急。

**拆解为四个断言**：

| # | 断言 | 性质 |
|---|---|---|
| A1 | 女仆当前的动作空间，是玩家动作空间的一个**退化子集**——玩家有的操作，女仆大多没有 | 问题陈述 |
| A2 | 应当**以玩家操作为粒度**，把女仆的能力重新切分成一组可独立选择的动作 | 核心方法 |
| A3 | 切分依据是"**玩家视角的操作**"，而不是"模组内部的实现单位"（不是"一个物品""一个类"） | 切分准则 |
| A4 | 第一步交付 = **一张穷举的操作清单**；第二步才是行为决策架构 | 阶段划分 |

## 2. 核心重构：从"输入编码的选择"到"数据编码的选择"

这是整个需求最关键的一步抽象，后面所有设计都从它推导。

### 2.1 玩家侧：选择被**输入编码**

玩家持一把拔刀剑时，面前有 22 种以上不同的操作（见 [01-操作清单](01-操作清单.md) §3）。但玩家**从来没有把这些操作当成一个"列表"去看**——它们被编码进了手指的动作里：

```
玩家侧：   输入事件 ──(隐式解码)──▶ 选中的操作 ──▶ 效果
           左键连点4下              "连击A"          4 段伤害
           Shift                    "防御"           抵消远程攻击
           左键长按                 "次元斩"          蓄力斩击
           特殊行动键+前进+Shift      "隔空瞬步"        瞬移到敌人头顶
```

**"按什么键"本身就是"选哪个操作"**。选择空间是**隐式**的：它散落在按键、时机、朝向、地形状态里，没有任何一处用代码或数据把它列出来。玩家的大脑就是那个解码器。

### 2.2 女仆侧：选择必须被**显式化**

女仆没有手指，没有鼠标，没有客户端。它只拥有：

```
女仆侧：   决策 ──(显式选择)──▶ 原子动作 ──▶ 效果
           行为逻辑说"现在用次元斩"    "次元斩"     蓄力斩击
```

**选择必须从"输入里"搬到"数据里"**：变成一个可枚举、可判定前置条件、可计量代价、可评分优劣、可被决策层点名调用的**条目**。

### 2.3 由此得到的定义

> **"类玩家"战斗模式 ＝ 把玩家输入语法中隐含的选择空间，显式化为一张女仆可决策的动作表。**

由此立刻得到三条推论：

- **推论 1（这就是第一步）**：既然目标是"显式化一个选择空间"，那么第一件事必然是**把这个空间枚举出来** —— 即操作清单。清单不完整，后面的决策架构就是在残缺的动作空间上做规划，毫无意义。**这也解释了为什么第一步必须是清单而不能跳过。**
- **推论 2（"类玩家"的含义）**：所谓"类玩家"，是**效果层面的同构**，不是**输入层面的同构**。女仆不需要"假装有人按了左键"，它只需要"产生与那次左键完全相同的效果"。这两件事的工程难度差了一个数量级（见 §6 可达性）。
- **推论 3（不是新增内容）**：这不是往游戏里加新技能、新物品、新模组。这是**对既有内容按新粒度重新索引（re-indexing）**。玩家侧"一把刀 + 22 种输入"这个既有事实，在女仆侧变成"一把刀 + 22 个可选条目"。**内容总量不变，索引方式改变。**

这正是你说的"**看作同一个东西**"的精确含义：同一个对象（拔刀剑的招式集、聚晶系统），被**重新划分**了一次。你没有创造新东西，你只是换了一把切刀。

## 3. 术语表（本项目强制使用）

> ⚠️ **存在一个必须先解决的术语冲突**：TLM 自 1.5.1 起，**"Skill（技能）"一词已被占用**，专指女仆 AI 聊天用的 **Markdown 知识技能**（`ai/agent/skill/SkillInstance.java`，`skills/*.md` 带 `tlm-type: knowledge` 前言）。【已查证】
> 因此本项目**禁用"技能"一词**指代战斗动作，统一改用"**原子动作**"。这是硬性约定，不是偏好。

| 术语 | 英文 | 定义 | 反例（不是这个词的意思） |
|---|---|---|---|
| **操作** | Operation | 玩家为触发某效果而施加的**一次输入事件**：含输入通道、修饰键、时长、时机、前置状态 | 不是"一个物品"；也不是"一次攻击"（一次左键连点 4 下 = 1 个操作还是 4 个？见 §4.3） |
| **操作载体** | Operation Carrier | 决定"此刻有哪些操作可用"的东西：主手物品 / 副手物品 / 饰品 / 已激活模式 | 载体是**可用性来源**，不是动作本身 |
| **原子动作** | Atomic Action | 女仆侧**可被独立选中并执行**的最小完整动作，与某个玩家操作效果同构 | 不是"一次伤害结算"；也不是"一个 tick 的行为" |
| **动作族** | Action Family | 由同一载体提供、共享执行骨架、**仅参数不同**的一组原子动作 | 「施放聚晶」是族；「施放火球聚晶」是实例 |
| **动作实例** | Action Instance | 动作族被具体参数化后的单个动作 | — |
| **操作清单** | Operation Catalog | 全部原子动作及其元数据的显式枚举 ＝ **第一步交付物** | 不是文档目录；是有 schema 的数据集 |
| **触发语法** | Trigger Grammar | 玩家侧操作的输入编码（键序/时长/状态谓词）。**在女仆侧它被拆成两半**：状态谓词→前置条件，时序→执行模型 | 女仆**不复现**触发语法，只继承其中的约束 |
| **前置条件** | Precondition | 该动作此刻是否可用的**服务端可判定**谓词 | 不是"玩家有没有按对键" |
| **可达性** | Reachability | 该操作在**服务端、无客户端输入**条件下被复现的能力等级（R-A/R-B/R-C，见 §6） | 不是"能不能实现"，是"能完整到什么程度" |
| **决策** | Decision | 女仆侧取代玩家输入的选择行为，由行为逻辑层产出 | 第一步不涉及 |
| **类玩家** | Player-Like | **效果同构、输入不同构**：女仆产生与玩家操作相同的结果，但触发来自决策而非输入 | 不是"女仆模拟玩家账号" |

## 4. 概念模型

### 4.1 三轴坐标：任何一条操作记录都落在三个轴上

单说"一个操作"是不够精确的——同一个玩家操作在三个维度上都有位置，而这三个维度正是后面所有争论的来源。

| 轴 | 取值 | 说明 | 为什么重要 |
|---|---|---|---|
| **载体轴** | 物品 / 饰品 / 模式 | 操作由什么赋予 | 决定**可用性剪枝**：女仆手上没有刀，全族不可用 |
| **粒度轴** | 通道 → 操作 → 组合 → 战术 | 见 §4.2 | 决定**枚举的规模**：切太细会爆炸，切太粗会丢信息 |
| **原子性轴** | 原子 / 组合 | 动作能否被拆成更小的动作 | 决定**决策层的接口形态**：组合动作是"多 tick 承诺" |

### 4.2 粒度四级（本项目最重要的分层）

| 级 | 名称 | 例子（拔刀剑） | 女仆侧是否需要 |
|---|---|---|---|
| **L0** | 通道级 | 左键、Shift、跳跃、特殊行动键、召唤幻影剑键 | ❌ **不需要**。通道是玩家侧的物理约束，女仆无手指。通道只作为**枚举时的扫描维度** |
| **L1** | 操作级 | 连击A、防御、格挡、次元斩、幻影剑、隔空瞬步 | ✅ **这就是清单的主体** |
| **L2** | 组合级 | 连击A·绝（需力量/饥饿效果）、星旋天翔（需"迅冲斩后长按"）、御空刀舞B（需"停顿后重复"） | ✅ 需要，但必须标注其**合成依赖**（前置动作 + 时序窗口） |
| **L3** | 战术级 | 走位风筝、集火、拉开距离、换武器、脱战 | ⚠️ **不来自输入映射**。它源自玩家行为观察，属于第二步的决策层输入，不进本清单 |

> **判定规则**：一条操作是否进清单，看它是否**同时**满足：
> ① 由某个载体赋予；② 效果可被服务端观测（伤害/位移/状态/实体生成）；③ 能被独立选中。
> L3 不满足 ①，L0 不满足 ③（它只是通道，不是选择单元）。**只有 L1 和 L2 进清单。**

### 4.3 切分准则：什么样的两个操作算"两条"

A3 说切分依据是"玩家视角的操作"。但玩家视角有歧义，必须给出可操作的判定规则：

| 判定问题 | 若"是" | 若"否" |
|---|---|---|
| Q1 效果**实质不同**吗？（伤害类型/位移/状态/生成物不同） | 两条 | 可能是同一条的参数变体 |
| Q2 是**同一个目标的同一效果**，只是程度不同吗？（伤害高低、消耗多少） | 一条 + 参数 | 两条 |
| Q3 前置条件**互斥**吗？（地面 vs 滞空；持有刀 vs 未持刀） | 两条（各自独立可用） | 两条（需处理并发） |
| Q4 存在**硬性时序依赖**吗？（"上斩后长按左键"） | 组合动作，标注依赖 | 独立动作 |
| Q5 只是**输入通道不同**吗？（同一个效果换了个键） | **一条**（通道是玩家侧细节） | — |

**关键推论（Q2 + Q5）**：**120 个聚晶不是 120 条清单记录。**
它是「施放聚晶」这**一条动作族** + 一个 120 值域的**参数域**。同理，拔刀剑的"左键连点 2 下/3 下/4 下"如果只有伤害段数差异，应合并为一条带参数的动作。

> 这一点在勘测中得到了实证，而且比预期更彻底：
> **Goety 的 125 个法术共享同一套「变体语法」**——变体只有 **5 个维度**
> （潜行 / 瞄准 / 施法形态 / 作用对象 / 破坏地形），且其中**潜行维度只有 8 类语义**，
> 由基类 `Spell.isShifting(caster)` 统一判定。
> ⇒ 也就是说，**125 × 若干变体 的行为空间，可以用「1 族 + 5 维度 + 125 参数」精确表达**，
> 只有 4 个法术需要逐个特判。见 [01-操作清单](01-操作清单.md) §4.2。

> 但同时——**你说的"不同聚晶对应不同操作"并没有被否定**。清单同时记录**族**与**实例集**：
> - 决策层看到的是**族**（紧凑，避免组合爆炸）；
> - 校验/展示层看到的是**实例**（枚举，保证"所有目前可行的操作"都在表里）。
>
> 这是"穷举"与"不爆炸"之间唯一能同时成立的形式。这也是第二步（可便捷搭建的行为逻辑）能否成立的前提——如果第一步就展开成几千条平铺条目，第二步没有任何架构能驾驭。

### 4.4 元模型（清单每一条必须有的字段）

清单不是散文，是可校验的数据。每条记录（族或原子动作）必须携带：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| `id` | 稳定标识（命名空间 + 路径） | 决策层要能点名 |
| `carrier` | 载体（物品/饰品/模式 ID） | 可用性剪枝 |
| `sourceMod` | 提供方模组 ID | 是否有该模组决定清单是否含此项 |
| `preconditions` | **服务端可判定**的谓词集合 | 否则决策层无法判断可用性 |
| `stateRequirements` | 所需实体/世界状态（地面、滞空、朝向目标、已选中仆从…） | 从触发语法的"状态谓词"部分继承 |
| `cost` | 代价（耐久、耀魂值、弹药、冷却、召唤位、饥饿、经验） | 决策层要能算性价比 |
| `duration` | 时长（瞬时 / N tick 承诺 / 持续引导） | 决定动作能否被打断、能否并发 |
| `interruptibility` | 可被打断性 | 组合动作的必备信息 |
| `effects` | 可观测效果（伤害/位移/状态/生成实体/治疗） | **对接战报项目**（`fight_feed_back`）的接口 |
| `compositeDeps` | 若为 L2 组合动作，其依赖的前置动作与时序窗口 | 见 Q4 |
| `reachability` | R-A / R-B / R-C | 见 §6 |
| `evidence` | 证据出处（源码行/字节码/配置/lang） | 允许【已查证】与【推断】分级 |

## 5. 边界（非目标）

明确写下"不做什么"，避免范围失控：

| 非目标 | 理由 |
|---|---|
| ❌ 不让女仆"模拟玩家输入" | 女仆是服务端实体，没有客户端。模拟输入既不可靠也无必要（推论 2） |
| ❌ 不新增游戏内容（新物品/新招式） | 本模式是**重新索引**（推论 3） |
| ❌ 本期不设计决策架构、不做 GUI、不做动画 | 你说的"先不急" |
| ❌ 不覆盖非战斗操作（建造、整理、社交、耕作） | 本模式限定战斗；但**包含战斗中的召唤/位移/防护/控制/资源管理**，因为你举的"处死仆从"就属于召唤物管理 |
| ❌ 不追求 100% 覆盖所有模组 | 与 `fight_feed_back` 的分级策略一致：先做 L0/L1 级模组，其余保持观察 |
| ❌ 不使用"技能"一词指代战斗动作 | 术语冲突，见 §3 |

**边界的一个易混点**：你举的"处死仆从"不是攻击性操作，而是**对己方召唤物的管理操作**。它之所以要进清单，是因为：① 它有明确的玩家发起动作；② 它改变战斗状态（仆从消失、仇恨转移）。⇒ 清单的收录标准是"**玩家主动发起 + 有战斗相关效果**"，而不是"造成伤害"。

## 6. 关键技术约束（在写清单之前必须知道）

这四条约束直接改变了清单的形态，来自本机实测。

### 6.1 约束一：女仆是服务端实体 ⇒ 可达性必须分级

玩家的操作有一部分**只在客户端存在**（GUI 打开、按键轮盘、鼠标左键点实体）。一个服务端 mob 无法发起这些。【已查证：TLM 的 `EntityMaid` 是 `TamableAnimal` 派生；拔刀剑有独立的 `client/SlashBladeKeyMappings` 与 `capability/inputstate`】

因此清单必须给每条操作标注可达性：

| 等级 | 含义 | 处理 |
|---|---|---|
| **R-A** | 模组本身提供**服务端可调用入口**（public 方法/API），直接调用即可 | 优先；这类操作是清单的核心 |
| **R-B** | 无公开入口，但效果可由**更底层调用组合**出来（例如自己算轨迹 + 生成实体） | 可行但成本高，需标注工作量 |
| **R-C** | 效果**本质依赖客户端/UI/玩家身份**（如"打开聚晶圆环""左键点仆从保存到聚晶"） | **不进清单**（或标注为不可达，仅作记录） |

> 这一条是"类玩家"模式与"直接抄玩家逻辑"的分水岭。**能拿到 R-A 的操作，这个模式才立得住。**

### 6.2 约束二：TLM 现有任务模型没有"离散动作"这一层

【已查证】
- `IMaidTask` 的接口是 `List<Pair<Integer, BehaviorControl<? super EntityMaid>>> createBrainTasks(EntityMaid)`（`api/task/IMaidTask.java:60`）——**一个任务 = 一组行为树节点**，粒度是"节点"，不是"动作"。
- 内置攻击任务的实现全部退化为一个通用近战：`MaidMeleeAttack.create(20)`（`entity/task/TaskAttack.java:57`，20 tick 固定冷却）。
- 拔刀剑兼容只有**一次**通用斩击：`AttackManager.doSlash(maid, roll, Vec3.ZERO, false, false, 1.0, KnockBacks.smash)`（`compat/slashblade/SlashBladeCompat.java:27`），且只在 `TaskAttack` 下触发，`roll` 是**随机数**。

⇒ 结论：**TLM 目前丢弃了"是哪一招"这个信息**。从散落的 brain 节点里无法反推出动作集合，因此清单必须**新建**，不能从 TLM 现有结构中抽取。这正是这个项目存在的理由。

### 6.3 约束三：TLM 依赖的拔刀剑版本与实例版本存在代差

【已查证】

| 项 | 值 | 出处 |
|---|---|---|
| TLM 编译期依赖 | `slashblade-resharped:1.1.6-1.20.1` | `TouhouLittleMaid-1.20/build.gradle:216` |
| 实例实际安装 | `SlashBladeResharped-1.20.1-1.8.60` | `…\versions\诡厄使徒1.3.1\mods\` |

⇒ 从 1.1.6 到 1.8.60 是一个大跨度。TLM 的 `compat/slashblade` 只用到 `ItemSlashBlade` / `AttackManager.doSlash` / `CapabilitySlashBlade.BLADESTATE` 三个面，**不一定仍然稳定**。清单里每一项都必须标注**它是从哪个版本的哪条证据得到的**，否则会在版本升级中静默失效。

### 6.4 约束四：TLM 已经有一个"原子操作 + 知识 + 上下文"三层结构（重要的先例）

【已查证】TLM 1.5.1+ 为**女仆 AI 聊天**已经建立了完全同构的三层结构：

| 层 | TLM 的实现 | 文件 | 与本项目的关系 |
|---|---|---|---|
| **原子操作层** | `ITool`，javadoc 原文："Tool 用于向模型暴露一个**可执行的原子操作**" | `ai/agent/tool/ITool.java:19` | ★ **这就是"操作清单"在 AI 侧的对应物** |
| **触发/知识层** | `SkillInstance`（Markdown + frontmatter），`tlm-type: knowledge` | `ai/agent/skill/SkillInstance.java` | ⚠️ 占用了"Skill"一词，见 §3 |
| **上下文层** | `GameContextRegister` / `IMaidContext`，按分类懒加载 | `ai/agent/context/GameContextRegister.java` | 第二步决策层需要的"局势感知"的先例 |
| **注册入口** | `registerAITool(ToolRegister)` / `registerAIMaidContext(GameContextRegister)` | `api/ILittleMaid.java:126/146` | 附属模组可扩展的官方面 |

**这条约束是正面的**：它证明"把游戏内能力拆成一堆原子操作，再交给一个决策器去选"这件事在 TLM 的代码库里**已经被验证可行**。本项目要做的是把这个结构从"AI 聊天"搬到"战斗"，并且决策器从 LLM 换成行为逻辑。

同时它也给出一个**可直接复用的设计范式**：`ITool` 的字段（`id` / `summary` / `parameters` / `codec` / `trigger(maid, ctx)` 可用性判定 / `invocationSummary`）与本项目 §4.4 的元模型高度重合。**第二步应当优先考虑复用这套形态，而不是另起一套。**

## 8. 本步结论（给下一步的输入）

1. **"类玩家"的实质**：把玩家输入语法中隐含的**选择空间**，显式化为女仆可决策的**动作表**。（§2.3）
2. **第一步产物**：一张带元模型的**操作清单**，含**族 / 实例**两级表示、**L1/L2** 两级粒度、**R-A/R-B/R-C** 可达性标注。（§4）
3. **必须避开的三个坑**：
   - 术语坑：不能叫"技能"（与 TLM 的 LLM Skill 冲突）；
   - 规模坑：120 聚晶 ≠ 120 条，必须做参数化族；
   - 可达性坑：客户端操作进不了清单，必须先分级再枚举。
4. **下一步（不在本期）**：设计"可便捷搭建的行为逻辑架构"。它的输入正是本清单，它的形态应当优先复用 TLM `ITool` + `GameContextRegister` 的既有范式。

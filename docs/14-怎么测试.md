## 0. 三层验证，从便宜到贵

| 层 | 花多少 | 能验什么 | 不能验什么 |
|---|---|---|---|
| **① 离线自测** | 秒级、零成本 | 判据/映射/调度器/统计**逻辑**是否正确 | 游戏里真实的"物品/法术/朝向" |

> ★★ **顺序不能颠倒**：①② 都绿了再进游戏。否则一旦观感不对，
> 你分不清是"判据错"还是"游戏侧接线错"——这正是本项目前几轮反复吃亏的地方。

```powershell

$gson=(Get-ChildItem "$env:USERPROFILE\.gradle\caches\modules-2\files-2.1\com.google.code.gson\gson" -Recurse -Filter 'gson-*.jar' | Where-Object {$_.Name -notmatch 'sources|javadoc'} | Select-Object -First 1).FullName
java -Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -cp "build\classes\java\main;$gson" `
     com.touhoulittlemad.fightlikeplayer.decision.thinking.ThinkSelfTest --live
```

### 1.6 ★★ Goety 法术的三种生命期（本轮主修）

**背景**：Goety 的法术有三条**完全不同的生命期**，走错一条就会"什么都没发生但回报成功"
（实测：`炽燃升腾` = `FlameStrikeSpell`，活儿全在 `startSpell` 里）：

| 形态 | 判据 | 我们怎么驱动 |
|---|---|---|
| **瞬发 INSTANT** | `castDuration == 0` | 只调一次 `SpellResult` |
| **定长引导 CHANNEL** | `0 < castDuration ≤ 200` | `startSpell` → 每 tick `useSpell` → `stopSpell`（长度 = 法术自己的数） |
| **蓄力长按 CHARGING** | `IChargingSpell`（`castDuration` 恒为 **72000**，是"不松手就一直放"的**硬上限、不是时长**） | 前摇 `castUp` 过后**按 `Cooldown()` 的节奏反复 `SpellResult`**（长度我们自己定：`castUp+20`，夹在 20~60） |

**实机**：给女仆**炽燃升腾聚晶**（`flame_strike`）+ 法杖，让她打怪。

**看日志**（`-Dforge.logging.console.level=debug` 或 `logs/debug.log`）：
```
[FLP] goety 引导起手：FlameStrikeSpell（CHANNEL·60 tick·前摇 0）
[FLP] goety 引导收尾：FlameStrikeSpell（60 tick·0 发）
```
- ✅ **过**：怪脚下**真的升起火柱**（`FlameStrikeSpell` 不再"空转"），且**她不再反复选同一个法术**
- ✅ 判据②：**引导结束后她立刻做别的事**（不会"卡住其他行为"）
- ❌ 不过：日志出现 `goety 引导中断：法杖已不在主手` ⇒ 引导期间被换手了（该报 bug）
- ❌ 不过：出现 `★ goety 法术 XXX 出错 ⇒ 【本次进程内拉黑】` ⇒ 该法术抛异常，
  **她会跳过它继续用别的**（这是设计行为）；把那行贴给我即可

### 1.6b ★★ 第十轮修的四件事（都是你上轮报的）

| 你报的现象 | 现在的行为 | 怎么确认 |
|---|---|---|
| 「**熔岩炸弹**释放到一半被自己打断重新放」 | 定长引导类现在**在自然收尾时派发一次 `SpellResult`**（此前只在引导，不发射）⇒ 熔岩炸弹会真的飞出去；★ 看门狗也**不再在引导期间判卡死** | 看到 `goety 引导收尾：LavaballSpell（40 tick·0 发）` 之后**有火球飞出**（`0 发` 是正常的：它的"一发"发生在收尾那一刻） |
| 「**腐化/水蛭大量白烟**」 | **删掉了 `startUsingItem`**（白烟的根因：法杖使用时长为 0 ⇒ 当 tick 走完 ⇒ 非玩家分支 `failParticles` = 10~44 个 CLOUD）；改为给光束**松绑**（`itemBase=false`） | 施法时**不应再出现成团白烟**（法术自身的粒子仍在，那是设计） |
| 「**怪死了也不停止**」 | 收尾判据现在**覆盖所有形态**（此前只管蓄力类），目标一死就 `goety 引导收尾：目标已消失/死亡` | 目标死后**光束/持续效果立刻消失** |
| 「**换聚晶后先放旧的**（哪怕不在背包）」 | 每 tick 复核"杖里现在装的是哪颗"，一换就收尾旧法术 | `goety 引导收尾：杖内聚晶已被换成 XXX（起手时是 YYY）` |

> ★ 引导长度的旋钮（配置 `goety.sustainTicks`，默认 60 = 3 秒）：
> 太小 ⇒ 光束刚出来就收；太大 ⇒ 她站桩久（但目标一死就收）。

### 1.8 ★★ 枪械：以"一梭子"为单位（第十轮）

**实机准备**：给女仆一把 **TaCZ 冲锋枪/步枪** + **足够的备用弹药**（放在她的背包里）。

**预期的完整流程**：开始（若弹夹不满会自动换弹）→ 连续开火打空弹夹 → 自动换弹 → 继续打 → 打够发数后收枪。

**看日志**（debug 级）：
```
[FLP] 枪械：打满 30 发 ⇒ 收枪
[FLP] 枪械：连续 2 次换弹/上膛都没有打出子弹 ⇒ 提前收（多半没有备用弹药）
[FLP] 枪械：达到时长上限 200 tick ⇒ 收枪（打了 12 发）
```
- ✅ **过**：她**连续打完一梭子**（而不是"打两三发停一下"），且**中间会自己换弹**
- ✅ 判据②：**换弹期间不会切去干别的**（一次动作 = 一梭子，决策层在打完之前不重选）
- ❌ 不过：只打两三发就停 ⇒ 看上面三条日志哪一条在触发（把日志贴我）
- ⚙️ 两个旋钮：`gun.magazineShots`（默认 30，一梭子最多几发）· `gun.magazineTicks`（默认 200，最多打多久）
- ⓘ 只有 **TaCZ** 走"一梭子"；别的枪械包（卓越前线等）保持"一发"语义（它们的节奏口径不同，同一套推断会误判）

> ★ 想验证"蓄力长按类"（`箭雨`/`水刀`/`暴雪` 等）：它们**前摇一过每 tick 一发**，
> 因此观感应是"持续输出一小段（1~3 秒）后收手"，而**不是**站桩一分钟。
> 若她站桩不放超过 6 秒 ⇒ 看门狗会介入（见 §1.7），日志里能看到 `⚠ 看门狗`。

### 1.7 ★★ 卡死看门狗（本轮新增的鲁棒性机制）

**它解决什么**：有一种最坏的失败是「**回报成功、照扣代价，但世界里什么都没发生**」
（本轮实测的 `FlameStrikeSpell` 就是）。它**既不增加连败、也不抛异常** ⇒
此前三道保险丝（无执行器过滤 / 连败退避 / 法术拉黑）**全都不响**。

**判据**：她在**战斗中**，而**目标血量、距离、自己血量、位置**这四项在 **120 tick（6 秒）**内**毫无变化**。

**看日志**：
```
[FLP] ⚠ 看门狗：Neuro-sama（牛肉） 在 120 tick 内毫无可观测变化（目标 僵尸）⇒ 第 1 次判定卡住；
      已中止在途动作（有），并把 goety:cast_focus 停放 200 tick
      （停放走冷却通路，/flp why 里显示为 ON_COOLDOWN）
```
- ✅ **过**：出现这行之后，**她换了一个动作**（`/flp why` 里能看到主循环选了别的），
  且 `/flp whyfull` 的"丢弃"段里 `goety:cast_focus → ON_COOLDOWN`
- ✅ 判据②：**停放会过期**（200 tick 后那个动作又能被选中）—— 它是"临时让位"，不是"永久禁用"
- ❌ 不过：反复刷同一行、她始终不换动作 ⇒ 把所有候选都卡住了（把日志贴给我）

> ★ **脱战时不会误判**（站着不动是正常的）—— 这一条有断言钉住
> （`GameLoopSelfTest §16`：`isStalled(0, 100000, false) == false`）。

### 1.9 ★★ 副手：举盾是被动姿态 + 换手（第十一轮）

**委托方的模型**：「我们做的基本上都是**主动技能**，但是盾是**被动迎击**：
『举盾』动作实际上是『**确认副手上是否是盾并把盾放在副手上**』。」

**实机准备**：把**盾放在女仆的物品栏里**（不用手动放副手），给她一个敌人。

**看到的应该是**：
- 她**自己把盾换到副手**（日志 `[FLP] ★ 换手（副手）：(空手) → minecraft:shield`）；
- 敌人 8 格内时**一直举着**（日志 `[FLP] ★ 副手姿态：举盾（目标 5.2 格）`），
  **不是**"举 1 秒 → 收手 → 再举"；
- 敌人走远到 12 格外（或死了）才放下。

- ✅ 过：**举盾是连续的**，且她**不会再把它当成一个"动作"反复选择**
- ❌ 不过：`/flp whyfull` 里还能看到 `maid_native:shield_block → NOT_A_CHOICE`
  ⇒ 说明它还是被当动作（应该已被改成 `role=stance`）

> ★ 为什么它现在是"姿态"：动作的语义是"这一步做什么"（有承诺、做完扣代价），
> 而"举着盾"没有"做完"的时刻。**与步法（走位）同构**：都是"由持续条件驱动的并发伺服"。
> ⓘ 灭火器也已按同一族机制接上（**它在 TLM 里是主手物品**，所以实现是"需要时借主手、用完还回去"，
> 且**只在主循环空闲时借** —— 不会打断挥刀/引导/打枪）。

### 1.10 ★★ 铁魔法：前摇与冷却现在补上了（第十一轮）

**取证结论**（读 ISS 反编译）：此前**前摇与冷却都被跳过** ——
玩家侧 `attemptInitiateCast` 先等 `getEffectiveCastTime`，`castSpell` 再 `addCooldown(serverPlayer, ...)`
（形参是 `ServerPlayer`）；而我们直接调 `onCast`（**效果**钩子）。
★ 巫法那一半：前摇**在**（按 `castUp`/`castDuration` 引导），冷却此前**没有**（同样是 Player-only）。

**实机**：给女仆一本**装了 LONG 类法术**（例如火球/闪电链这类需要蓄力的）的书，看她打怪：
```
[FLP] 铁魔法起手 irons_spellbooks:xxx（前摇 20 tick）      ← 前摇现在看得见
[FLP] 铁魔法施放：irons_spellbooks:xxx（从 XXX书 第 2 槽）
```
- ✅ 过：**同一颗法术不会连绵不断地放**（它有自己的冷却了）；前摇期间她在**瞄准并转向**目标
- ⚙️ 冷却的数**来自法术自己**（ISS `getSpellCooldown()` / Goety `spellCooldown(caster)`），
  不是我们拍的

### 1.11 ★ 瞄准点：对着落脚处稍高（第十一轮）

委托方要求：「瞄准类的法术，女仆释放法术时请**对着怪物落脚部分的稍高处**瞄准
（比如对于两格生物，即下面那格的位置再稍稍偏低一点）」。

现在瞄点 = **脚底 + 目标高度 × 0.2**（夹在 0.25~0.5 格）：
两格生物 ⇒ **0.4 格**；一格生物 ⇒ 0.25 格；铁傀儡 ⇒ 0.5 格。
- ✅ 过：法术**擦着躯干命中**的概率明显变高（尤其是中远距离）
- ⓘ 原来是瞄**眼睛**（两格生物约 1.6 格高）⇒ 远距离容易从头顶飞过

## 2. 运行期旋钮速查（`/flp tune`）
| 命令 | 作用 |
|---|---|
| `/flp tune` | 列出全部旋钮 + 当前值 + **来源层** + 范围 + 中文含义 |
| `/flp tune <键> <值>` | 改**全局**（越界自动钳制并告知；未登记的键被拒并说明） |
| `/flp tune reset` | 全局一键复原 |
| `/flp tune maid <女仆>` | 看**这一个女仆**的旋钮（含"来自哪一层"） |
| `/flp tune maid <女仆> <键> <值>` | 只改她（不动别人） |
| `/flp tune maid <女仆> reset` | 只清她的覆盖 ⇒ 回到继承全局 |
| `/flp tune advisor [女仆]` | 顾问状态 + 该女仆的**行为统计** + **"它想怎么调"** |
| `/flp tune advisor now <女仆>` | ★ **立刻问一次顾问**（不等 30 秒） |

**最常用的两条**（委托方第 3/5 条的效果就在这两个旋钮上）：
```powershell
/flp tune satisfaction.damage 0.5   # 砍一刀"更不解渴" ⇒ 攻击需求要更多次攻击才满足
/flp tune cooldown.scale 0.5        # 出手更快（★ 想"打得更勤"必须调这个，光调满足度没用）
```

## 3. ★★ 调控顾问：怎么测（三步）

### 第 0 步（可选）：离线先看一眼

跑 `--live`（见 §0 的命令），末尾会打印：
```
---- 调控顾问（同一份 Key，另一次请求）----
行为统计   = 窗口 200 tick：出手 9 次（平均间隔 22.5）· 失败 2 次 · 受伤 1 次/共 13.0 · 最低血 62%
它想怎么调 = satisfaction.damage ↑ 1.00→1.02　cooldown.scale ↑ 1.00→1.10　bias.caution ↑ 1.00→1.15
```
这条**不写进任何总线**（与游戏的 `observe` 一致）—— 纯粹"看看它会不会回、回得像不像话"。

### 第 1 步：进游戏，打开顾问但**只观测**

模组配置界面 → 玩家拟人战法 → Config → `advisor` 段：

| 配置项 | 设成 | 为什么 |
|---|---|---|
| `thinking.apiKey` | 你的 Key | 顾问与短周期**共用**这一份 |
| `advisor.enabled` | **true** | 打开顾问 |
| `advisor.applyMode` | **observe**（默认） | ★ **先只看它想怎么调，不真的生效** |
| `advisor.intervalTicks` | 600（默认 30 秒） | 慢变量；调太勤会随模型抖动 |

### 第 2 步：让女仆打一架，然后立刻看

```powershell
/flp tune advisor now @e[type=touhou_little_maid,limit=1]   # 不等 30 秒
# 约 1~2 秒后
/flp tune advisor @e[type=touhou_little_maid,limit=1]
```
输出会包含：
```
  已提问 N 次　已生效 0 次　最近往返 1234 ms
  行为统计：窗口 200 tick：出手 12 次（平均间隔 18.3）· 失败 2 次 · 受伤 3 次/共 39.0 · 最低血 55%
  最近建议：satisfaction.damage ↑ 1.00→1.03　cooldown.scale ↑ 1.00→1.12　bias.caution ↑ 1.00→1.21
```
日志里对应：
```
[FLP][advisor] 顾问建议（仅观测，未生效）：…　★ 想让它真的生效：配置里把 advisor.applyMode 设为 apply
```

- ✅ **过**：`已提问 ≥ 1`、`行为统计`非空、`最近建议`里的方向**讲得通**
  （她老挨打 ⇒ `bias.caution` 升；她老是卡在同一个动作 ⇒ 有 `stuck_actions`）
- ❌ 不过：`⚠ 顾问提问失败：…` —— 那句里会写清原因
  （没配 Key / 401 / 网络 / 那句假的「无可用渠道」会被翻译成人话）

### 第 3 步：确认它合理之后，再放开

把 `advisor.applyMode` 改成 **`apply`**。之后：
```
[FLP][advisor] ★ 已按顾问建议调整：satisfaction.damage ↑ 1.00→1.03　…
```
⇒ 旋钮开始真的动，**且只动这一个女仆**（她有自己的总线）。
任何时候 `/flp tune reset`（全局）+ `/flp tune maid <女仆> reset`（她）可以一键复原。

> ⚠️ **三条安全边界**（都有断言，可以放心）：
> ① 顾问**只能调 5 个标量旋钮**（`failure.backoff` 是保险丝，刻意不给它）；
> ② 值**永远钳在各自区间内**，模型答得再离谱也推不出边界；
> ③ 答「保持」（中档）**严格等于当前默认值** ⇒ **长期不会漂移**（这条是自测抓出来的）。

## 3.0 ★★ 先做这一步：**在配置界面上把连接测通**（第十/十二轮）

模组配置界面 → 玩家拟人战法 → Config → **第 ① 页**（**标签在上、输入框在下**，不会再挤在一起）：

| 步骤 | 做什么 | 看到什么算过 |
|---|---|---|
| 0 | 先看**页眉下面那两行**：`已就绪：JEV 官方（/responses）` 与 `会 POST 到 https://api.new.bi/v1/responses` | ★ **这一行是"端点填对了没有"的唯一可视证据**（两家路径不同，见下表） |
| 1 | 若端点不对 ⇒ 点 **「用 JEV 官方」** 或 **「用 DMXAPI」** 预设按钮（别手打路径） | 上面那行立刻跟着变 |
| 2 | **填 API Key**：**直接点输入框打字**（聚焦即明文，不必先点「显示」） | 打字时看得见字符 |
| 3 | 点右上角 **「测试连接」** | 下方出现 `§a✅ 连接成功（1234 ms，模型 jev-1.13.0）` |
| 4 | 失败 ⇒ 那一行会写**人话**（401 / 超时 / DNS / 代理） | 照它说的改，再点一次 |
| 5 | 通过后：**打开总开关** → `保存并关闭` | 进游戏后 `/flp think` 应显示"已就绪" |

**★ 两家中转站的路径与请求体不同（填错就一直失败，而报错看不出是路径问题）**：

| 中转站 | 端点填什么 | 实际 POST 到 | 请求体 |
|---|---|---|---|
| **JEV 官方** | `https://api.new.bi/v1` | `{它}/responses` | `model/input/state/questions`（`input` 是占位符） |
| **DMXAPI** | `https://www.dmxapi.cn/typesafe/v1/systemone` | 原样使用 | `model/state/questions`（**不含** `input`） |

> ★ 实测：`api.new.bi/v1/responses` 对这个 key 返回 **HTTP 200**；`dmxapi.cn` 返回 **401**（说明 key 属于前者）。
> ★ **「测试连接」用的是当前草稿里的值**（不是上次保存的）⇒ 可以"先改端点/Key → 先测 → 再保存"。
> ★ 它在**后台线程**发请求（最长 20 秒），不会卡住界面。
> ★ 不必进游戏也能测：命令行版见 §0 的 `--live`（用 `JEV_API_KEY` 环境变量）。

### 3.4 ★★ 提示词可配置（第九轮新增，配置界面第 ④ 页）

模组配置界面 → 玩家拟人战法 → Config → **翻到第 ④ 页「提示词（可编辑）」**：

| 位置 | 填什么 | 说明 |
|---|---|---|
| 上框 **思维层问法覆写** | 每行 `<轴 id> = <问法>` | 轴 id 共 8 条：`single_damage` / `area_damage` / `heal_survival` / `mitigation_survival` / `control` / `mobility` / `reinforce` / `ally_care` |
| 下框 **顾问问法覆写** | 每行 `<旋钮名> = <问法>` | 5 条：`satisfaction.damage` / `satisfaction.all` / `cooldown.scale` / `bias.aggression` / `bias.caution` |

- **只改一条就只写一条** —— 没写的键沿用内置问法（不会"改一条坏七条"）。
- `#` 开头是注释；**留空 = 完全用内置**。
- 拿不准键名 ⇒ 点 **「填入模板（…）」** 按钮，它会把**合法键名清单**写进框里。
- 写错的键**不会静默失效**：`保存并关闭` 时会**当场拦住并指出是哪个键**；
  若绕过界面直接改 toml，日志里会打 `提示词覆写已更新：覆写 N 条；★ 丢弃了 M 个无法识别的键：…`。

> ⚠️ **能改的只有"问法"，不能改等级**：`score` 的档数（5 档）与 `→ 向量` 的映射是**代码里的算术**，
> 档数一变映射就错了 ⇒ 界面/覆写都**只换文本**（有断言：覆写后问题数、键集合、档数都不变）。

### 3.5 ★★ 「LLM 动态指挥到底有没有上下文？」——**默认没有会话历史，有三样"记忆"**

这是委托方明确问过的问题，答案分两半：

| | 有没有 | 说明 |
|---|---|---|
| **多轮对话历史** | ❌ **没有** | 每次请求都是**独立判定**。这不是偷懒：JEV 是 System One 的**打分模型**（只答 `noul`/`choice`/`score`），**它压根不接受消息历史**。要"多轮"就得换 chat 模型，那是另一套风险与成本 |
| **一段时间的行为** | ✅ **有** | 顾问拿到的 `recent_behaviour`：**200 tick 滑窗**（出手次数/平均间隔/失败次数/受伤/最低血/卡住的动作用于）—— **这才是真正的"历史"** |
| **当前旋钮值** | ✅ **有** | 含**它自己上次改出来的效果**（调过的显示为数值，没调过显示 `default`） |
| **上一轮的建议** | ✅ **有（本轮新增，只有一格）** | `previous_round`：上一轮它建议了什么 + **有没有被采纳**（区分"被采纳 / 你答了保持 / 配置还是 observe 只记录"） |

⇒ 一句话：**它记得"世界现在是什么样"，但不记得"我们聊过什么"。**
对本用途这反而更稳（不累积幻觉、不被自己前几轮的话带偏），而"上一轮"这一格刚好挡住最讨厌的情况：
**它反复提同一个建议却被忽略**（那说明建议与实际旋钮之间有断层，应当让它看见）。

**怎么验**：`/flp tune advisor` 看 `最近建议`；打开 `logDecisions` 后，
请求体里的 `previous_round` 会随日志一起出来（`[FLP][think]` 那几行）。

## 4. 失败了去哪看

| 现象 | 先看哪 |
|---|---|
| 她"选中了却没做出来" | `/flp whyfull <女仆>` —— 候选集 + 丢弃原因明细 + 最近 40 条结果 |
| 她为什么做这件事 | `/flp why <女仆>` —— 弹簧点 / 承诺 / 上次选中 / 步法 / 冷却 |
| 法术为什么没放出来 | 日志里搜 `施法失败` —— 会写明是"主手不是法杖 / 没有能用的聚晶 / 不是 Spell 子类" |
| **某个法术"放了但没效果"** | 日志搜 `goety 引导起手` / `引导收尾`（看形态判对没有）；6 秒无变化会打 `⚠ 看门狗` |
| **她被某个动作卡住** | 日志搜 `看门狗`（会写明"把哪个动作停放多久"）；`/flp whyfull` 里看 `ON_COOLDOWN` |
| 某个动作从不出现 | `/flp whyfull` 的"丢弃"段；或 `python tools\check_executors.py`（有没有执行器） |
| 短期判定/顾问没反应 | `/flp think`（Key/端点/开关）· `/flp tune advisor`（顾问开关与统计） |
| **改了提示词没效果** | 日志搜 `提示词覆写已更新`（会写明覆写几条、丢弃哪些键）；`/flp think` 看当前配置 |
| 想开详细日志 | 启动器加 `-Dforge.logging.console.level=debug`，或看 `logs/debug.log` |

> ★ 日志里的 `[FLP]` 前缀是这个模组的全部输出 —— 出问题先 `grep "[FLP]" logs/debug.log`。

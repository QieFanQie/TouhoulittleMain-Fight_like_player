## 1. 把你的两条要求写成规范

| # | 你的原话 | 规范化表述 |
|---|---|---|
| 1 | 建立**所有物品和动作层的关系**（拔刀剑-拔刀剑对应动作）；所有物品包括主手、副手、所有物品栏、身上盔甲；由此**通过所有物直接判断可行的动作** | **载体解析（Carrier Resolution）**：`持有物集合 → 候选动作集合 → 可用动作集合`。是"动作层"到"执行层"的**唯一入口** |
| 2 | 给动作列表中的**每个动作一个多维评分**，构成一个能描述语义的空间 | **动作向量化（Action Vectorization）** + **需求空间（Need Space）** + **最近邻选解** |

### 1.1 为什么这两件事必须一起做

单独看都不成立：

- **只有物品映射**：知道"能做什么"，但**不知道现在该做什么** ⇒ 就是现在的骨架（一个通用近战）。
- **只有评分体系**：有了一套打分，但**打分对象从哪来**是空的 ⇒ 无米之炊。

⇒ **完整链条**：
```
持有物 ──①载体解析──▶ 可用动作集合 ──②向量化+需求空间──▶ 选定动作 ──③执行器──▶ 效果
                                                              └── 反馈回需求空间
```
其中 **①是本文 §4**，**②是本文 §3/§5**，**③是执行层（N2/N3，见 [08](08-测试计划.md) §8.5）**。

## 2. 对【行为弹簧体系】的评审

### 2.1 先把它形式化（确保我们说的是同一件事）

| 你的说法 | 形式化 |
|---|---|
| "多维评分体系构成一个能描述语义的空间" | 动作 `x` ↦ 向量 `v_x ∈ ℝⁿ`；需求为点 `p ∈ ℝⁿ`（同维） |
| 思维层"决策出一个决策向量" | 偏置 `a ∈ ℝⁿ`（**当前不做**，先留接口） |
| "由原来的点朝决策向量方向偏移" | `p ← p + a` |
| "选择和弹簧空间当前点对应的位置向量最近似的向量" | `x* = argmin_{x ∈ 可用} d(p, v_x)` |
| "进行 b 后，对当前点坐标 A=(o+a) 进行 -b 的平移" | `p ← p − v_{x*}` |
| "忘却机制" | `p ← (1−λ)·p`（向原点回归） |
| "规整机制：不在原点时不断向原点缓慢回归；若离原点极近则算作原点" | `p ← 0 if ‖p‖ < ε` |
| "坐标应该没有负值" | `p ← max(0, p)` 逐分量 |
| "举例的负是向量的负" | `v_x[d] < 0` 表示**该动作制造** d 方面的需求（代价/暴露） |

> ✅ **内部一致性检查通过**。特别是**符号语义**这一处是关键设计：
> `p ← max(0, p − v_x)` 在 `v_x[d] < 0` 时**自动增大** `p[d]` ——
> 于是"吟唱 AoE 让生存需求上升"这件事**不需要任何额外机制**就成立了。
> **这个设计的优雅之处就在这里：收益与代价用同一个向量的正负号表达。**

### 2.2 结论：**合理，可以开发** —— 但必须修 7 处

我按"不修会怎样"排序：

| # | 问题 | 不修的后果 | 修正 |
|---|---|---|---|
| **①** ★★ | **各维度量纲不同 ⇒ 欧氏最近邻被大量纲维度支配** | 若"伤害"是 0~100 而"群攻"是 0~1，则**选解实际只看伤害**，整个空间退化成 1 维 | **全部维度归一化到 `[-1, 1]`**，并给每轴一个权重 `w_d`（见 §3.4） |
| **②** ★★ | **原点处的选解没有意义**：`p = 0` 时最近的动作是**幅值最小**的那个 ⇒ 女仆会一直挑"最弱的动作" | 无事可做时反复放最廉价的动作，观感是"发呆乱放" | **死区**：`‖p‖ < ε` ⇒ 不进最近邻，改走**默认动作集**（接近目标 / 保持警戒）；并且引入**态势基线偏置**（见 ⑥） |
| **③** ★ | **动作向量是静态的，但效果依赖情境** | "治疗"在满血时价值 0、"AoE"对单个敌人价值很低，但静态向量会说它们很划算 | 引入**契合度乘数** `m_x[d]`（**逐轴**），`u_x[d] = v_x[d]·m_x[d]`。**静态向量写在清单里，情境因子运行时算**（见 §3.5） |
| **④** ★ | **没有承诺/打断语义** | 弹簧每个决策周期都重选 ⇒ **引导类法术每 tick 被打断**，永远放不完 | 决策周期由动作的 `duration` 门控（`COMMIT`/`CHANNEL` 期间不重选）；打断时**按剩余比例退还**（见 §5.3） |
| **⑤** | **大动作会把状态清零**（`p[d]` 被减成负再钳到 0）⇒ 丢失上下文 | 放完一个大招后需求全被抹平，女仆"忘记"刚才在打什么 | 这其实是**正确行为**（大招确实解决了问题）；但要**显式化**为"减法即 `max(0, ·)`"，并给出 `P_MAX` 上限防止偏置累积溢出（见 §3.6） |
| **⑥** ★ | **"思维层先不做"⇒ `a = 0` ⇒ 弹簧永远停在原点** | 上一条被触发：一直挑最弱的动作 | 引入**态势基线偏置** `b_context`（规则产生，**不是**思维层）：有敌 ⇒ 偏输出；主人濒死 ⇒ 偏护友；自己低血 ⇒ 偏自保。**它同时是思维层接入前的占位与之后的兜底** |
| **⑦** | **平局/抖动**：两个动作距离相等时会 A→B→A→B | 观感是"反复横跳" | 平局带（`τ`）内**优先选最近最少使用的**（用一个衰减的 recency 惩罚），再带极小随机抖动（见 §5.4） |

> 📌 **另外两处"你的模型没提、但必须补"**：
> - **互斥占用**（清单里的 `exclusivity`，如"同时只能装 1 本法术书"）——
>   它是**硬约束**，必须在**过滤阶段**处理，**不能进评分**（一个互斥的动作不管你多想要都不能选）。
> - **回退路径**：可用动作集合为空时（裸手、无载体、全被过滤）必须有兜底动作。
>   **回退必须永远存在** —— 这是我们不劣于 TLM 的底线。

### 2.3 一句话评价

> **你的模型是对的，而且是"用最小机制换到最多行为多样性"的少见好设计。**
> 它的核心价值在于：**把"冷却/轮换/节奏"从手写规则变成了空间几何的自然结果** ——
> 放了 AoE 之后生存轴自然上移，于是下一次自然倾向防御。
> **这恰好就是玩家"打完一套补个防御"的行为外观，而它不需要任何一条"打完 AoE 就防御"的规则。**
>
> 需要补的是**工程外围**：量纲、死区、情境因子、承诺语义、基线偏置、平局。

### 2.4 ★ 动作的「单位」是什么（粒度对齐 ①）

**定义**：

> **动作的单位 = 决策层一次提交所对应的、不可再分的执行跨度。**

它由清单里的 **`duration.kind`** 刻画 —— **不是由"动作看起来多大"决定的**：

| `duration.kind` | 单位 | 决策层行为 | 玩家侧对应 |
|---|---|---|---|
| **`INSTANT`** | **一次调用** | 立即扣减 `p`，下一个决策周期重新决策 | **单击** |
| **`COMMIT`** | **一次不可打断的承诺**（`ticks`） | **承诺期内不重选**（[§5.3](#53-承诺与退还修正-)） | **一段连击 / 一次蓄力斩** |
| **`CHANNEL`** | **"持续"这件事本身** | **每个决策周期都可决定是否继续** | **按住不放** |

⇒ 判据是一句话：**"决策层能不能在半途停下它？"**
能停 = `CHANNEL`；不能停但有固定长度 = `COMMIT`；一提交就结束 = `INSTANT`。

#### 各载体的单位对照

| 动作 | 单位 | `duration` | 依据 |
|---|---|---|---|
| **释放一次 SA** | 一次 `doChargeAction(user, elapsed)`（**松手那一帧**结算） | `COMMIT`（`chargeTicks ≥ 9`） | 松手前随时可放弃 ⇒ 蓄力段是承诺、结算是一次 |
| **施放一个瞬发聚晶** | 一次 `Spell.mobSpellResult` | `INSTANT` | — |
| **施放一个长按聚晶** | **"按住引导"这件事** | `CHANNEL` | 光束实体靠 `isUsingItem()` 存活，中途松手即结束 |
| **开火（SEMI）** | **一次 `shoot()`** = 一发 | `INSTANT` | 见下 |
| **开火（BURST）** | **一次 `shoot()`** = **整轮三连发** | `COMMIT` | ★ 见下 |
| **开火（AUTO）** | **"持续射击"这件事** | **`CHANNEL`** | ★★ 见下 |
| **换弹** | 一次完整换弹流程 | `COMMIT` | 中途打断 = 没有换弹 |
| **近战挥击** | 一次 `doHurtTarget` | `COMMIT`（TLM 固定 20 tick 冷却） | — |

#### ★ 直接回答你的疑问：「步枪的单位是"打一梭子"吗？手枪是打一发还是一梭子？」

**都不是"一梭子"（弹匣），也不是笼统的"一发" —— 单位是「一次 `shoot()` 调用」，而这次调用的内容由 `fireMode` 决定。**

**证据（已查证）**：

| 事实 | 出处 |
|---|---|
| **一次 `shoot()` 会内部完成整轮连发** | `ModernKineticGunScriptAPI.shootOnce` 里 `CycleTaskHelper.addCycleTask(period, cycles = burstData.getCount())` |
| **AUTO 冷却 2 tick；SEMI / BURST 冷却 10+rand(5) tick** | `GunItemDataAccessor` 的 `GunFireMode` |

⇒ 所以：

| 枪 | 默认 `fireMode` | **一次动作的内容** |
|---|---|---|
| **步枪** | AUTO | **持续射击**（`CHANNEL`）—— 玩家按住不放 |
| **步枪**（切到 BURST） | BURST | **一轮三连发**（`COMMIT`） |
| **手枪** | SEMI | **一发**（`INSTANT`） |
| **手枪**（切到 BURST，若该枪支持） | BURST | **一轮三连发** |

> ★ **"一梭子（弹匣）"为什么不能是单位**：弹匣边界属于**换弹**动作，不属于开火。
> 玩家可以在弹匣打空**之前**任何时刻松手 —— 这正说明开火是 `CHANNEL`（可停），而不是"一个弹匣 = 一个动作"。

#### ★★ 由此发现并修掉了我自己的一个建模错误

我原来把 `tacz:shoot` 标成 `"duration": { "kind": "INSTANT" }`。**这是错的**，后果很具体：

```
决策周期 decisionInterval = 5 tick
若 AUTO 按 INSTANT 处理  ⇒ 女仆每 5 tick 打 1 发（0.2 发/tick）
玩家的实际表现          ⇒ 每 2 tick 打 1 发（0.5 发/tick）
                         ⇒ 女仆的火力只有玩家的 40%
```

⇒ **AUTO 必须建模成 `CHANNEL`**，否则"开火"这个动作在行为上就不是"类玩家"的。

**修法**：`duration` 也必须能**按参数覆写**（与 `vectorOverrides` 同构），
因为**同一个动作在不同 `fireMode` 下承诺形状确实不同**：

```jsonc
"duration": { "kind": "INSTANT" },                    // 族默认
"durationOverrides": {
  "SEMI":  { "kind": "INSTANT" },
  "BURST": { "kind": "COMMIT", "ticks": 12 },         // 一轮连发 ≈ 10+rand(5)
  "AUTO":  { "kind": "CHANNEL", "sustainTicks": 40 }  // ★ 持续射击，决策层每周期可停
}
```

> 📌 **`durationOverrides` 的使用边界（重要）**：它只用于**参数取值确实改变"承诺形状"**的场合。
> 一般的差异（伤害高低、射程远近）属于 **`vectorOverrides`**（定量）。
> **不要把定量差异写成 `durationOverrides`** —— 那会让决策层的承诺逻辑变得依赖数据、难以推理。
> 判据：**"决策层对待它的方式是否不同？"** 是 ⇒ `duration`；否 ⇒ `vector`。

#### ★★ 第二层粒度：**不是所有"动作"都是"选择"**（`role` 字段）

做 v_x 补齐时发现了一个更根本的粒度问题：**清单里有 11 条动作，根本不是决策层会"选"的东西。**

| `role` | 含义 | 例子 | 决策层怎么办 |
|---|---|---|---|
| **`choice`**（默认，67 条） | 战术选择 —— **玩家会为了它专门换一招** | 开火、连击、SA、施法、格挡、撤退 | **进候选集，参与评分** |
| **`maintenance`**（7 条） | **维护步骤** —— 弹匣空了不得不做，不是"选择" | `tacz:reload`（换弹）、`cancel_reload`、`bolt`（拉栓）、`draw`（拔枪）、`attachment`（配件）、`inspect`（检视）、`use_item_interact` | **执行器自动完成**，不进候选 |
| **`stance`**（4 条） | **姿态 / 配置** —— 是一个持续状态或设置，不是一招 | `tacz:aim`（ADS）、`fire_select`（切射击模式）、`zoom`（开镜）、`crawl`（匍匐） | **作为契合度乘数或状态**（如 ADS ⇒ `SINGLE_DAMAGE` 乘数↑），不进候选 |

**为什么必须分开**：
- 玩家**从不"选择"换弹** —— 他是弹匣空了不得不换。把它放进候选集，就是让决策层
  在一个**没有战术价值**的条目上做权衡，**污染评分空间**（还会让"换弹"和"开火"抢同一个决策周期）。
- ADS 同理：它是"提高精度的姿态"，不是一招。它的正确位置是 §3.5 的**契合度乘数**。

⇒ **实现的后果**：`role != choice` 的动作**不进候选集**，并被记为
`DropReason.NOT_A_CHOICE`（而不是静默消失）。**它们的向量字段为空是正常的**，不是缺漏。

> ★ **这一步是"粒度对齐"里最容易被忽略的一层**：
> 前一层（`duration`）回答"一个动作有多长"，这一层回答"**它到底算不算一个动作**"。
> 判据同样是一句话：**"玩家会为了它放弃别的选择吗？"**
> 会 ⇒ `choice`；不会 ⇒ `maintenance` 或 `stance`。

#### 单位定义的完整判据链（三问）

```
这个"动作"是决策层会主动选择的吗？
  ├─ 不会 ⇒ role = maintenance / stance      （不进候选集，不需要 v_x）
  └─ 会   ⇒ role = choice
              └─ 决策层能在半途停下它吗？
                   ├─ 能            ⇒ duration = CHANNEL   （按住不放）
                   ├─ 不能但有定量  ⇒ duration = COMMIT    （固定长度的承诺）
                   └─ 一提交就结束  ⇒ duration = INSTANT   （单击）
```

#### ★★ 逐载体的动作单位表（委托方指定）

## 3. 评分空间设计

### 3.1 需求轴（**8 轴**）—— 弹簧空间就是这个空间

> ★★★ **首先记住这一条：这些是「评分」，不是「归类」。**
> 每条轴都是**连续的分数维度**，**不是互斥的类别桶**。
> 一个动作可以同时在多条轴上有值（拔刀剑·防御 = 非回血生存 `+0.9`、单点 `−0.3`）。
> ⇒ **绝不要用轴去做动作分类**（分类是 `carrier` / `role` / `kind` 的事）。
> 轴只回答一个问题：**"这一招在多大程度上满足了这个方向的需求？"**

> **选轴准则**：每条轴必须同时满足 ① 由清单里的 `effects` **可推导**；② **玩家会为它专门选一个不同的操作**；③ **能为负**（有代价）。
> 不满足②的轴（如"施法距离"）不进需求空间，而进 §3.5 的契合度。

> ★ **为什么"回血"和"非回血"必须分开（而不是一条 `SURVIVAL`）**：
> 一条轴只能表达"我有多需要活下去"，**无法表达"我打算怎么活下去"**。

### 3.3 需求点 `p` 与"弹簧"

| 量 | 含义 |
|---|---|
| `p ∈ [0, P_MAX]⁷` | **未满足的需求**。原点 = 无事可做 |
| `o` | 原点（全 0） |
| `b_context` | **态势基线偏置**（规则产生；思维层接入后与它相加） |
| `λ_d` | 逐轴**忘却率**（回归速度） |
| `ε_d` | 逐轴**死区**（极近即视为 0） |
| `P_MAX` | 逐轴上限（防偏置累积溢出） |

**为什么"弹簧"这个比喻很准**：`p` 被偏置推离原点（受迫位移），动作把它拉回，
忘却机制是一根弱弹簧 —— **三者共同构成一个受迫阻尼振子**。§7 给出稳定条件。

### 3.4 距离度量（修正 ①）

```
d(p, u) = sqrt( Σ_d  w_d · (p_d − u_d)² )        // 加权欧氏
```

| 项 | 说明 |
|---|---|
| `u` | **有效向量** `u_x[d] = v_x[d] · m_x[d]`（见 §3.5） |
| `w_d` | 逐轴权重。**默认建议**：`SELF_SURVIVAL` 与 `ALLY_CARE` 取 `2.0`，其余 `1.0` |

**为什么不用余弦相似度**：余弦只看**方向**、忽略**大小** ⇒
"需要一点治疗"时会选中"巨型全体治疗"（方向对、大小离谱）。
**加权欧氏能同时惩罚"方向不对"和"超出需求太多"**，更适合"够用就好"的行为。

**为什么权重差异是必要的**：否则女仆会用**致命的自保**去换一点输出
（因为两轴同权时，0.3 的输出收益与 0.3 的自保代价等价）。
**自保必须比输出更"贵"。**

### 3.5 契合度乘数 `m_x[d]`（修正 ③）

**逐轴**乘数，运行时算，默认全 1.0：

| 轴 | 乘数来源 | 规则（示例） |
|---|---|---|
| `SINGLE_DAMAGE` | `rangeFit × targetPresent` | 距离超出射程 ⇒ →0；无目标 ⇒ →0 |
| `AREA_DAMAGE` | `rangeFit × targetPresent × clusterFit` | `clusterFit = clamp(附近敌人数 / 3, 0, 1)`；**对单个敌人 →0.3** |
| `SELF_SURVIVAL` | `deficitFit` | 满血时治疗类 →0.2；血量 <40% →1.0 |
| `ALLY_CARE` | `allyNeedFit` | 主人满血 →0.2；主人 <50% →1.0 |
| `CONTROL` | `targetPresent × (1 − targetAlreadyControlled)` | 已控目标 →0.3 |
| `MOBILITY` | `gapFit` | 距离 <2 格时远离类 →0.2 |
| `REINFORCE` | `slotFit` | 召唤位已满 ⇒ 该动作**直接过滤**（不进评分） |

> 📌 **乘数只作用在"该动作本来就有值"的轴上**（`v_x[d] = 0` 时乘什么都是 0）。
> ⇒ **作者只需写静态向量，情境适配是运行时统一的**，不必为每个情境手写一套分数。

### 3.6 规整机制（三件套，对应你的"规整机制"）

```
① 非负钳制：  p_d ← max(0, p_d)
② 上限钳制：  p_d ← min(P_MAX_d, p_d)
③ 死区：      if p_d < ε_d then p_d ← 0
```
**顺序很重要**：先减、再①②③（否则负值会在减法前被吃掉，代价语义失效）。

### 4.2 两级解析：动作载体 vs 修饰载体

| 类型 | 作用 | 例 |
|---|---|---|
| **动作载体**（Active Carrier） | **提供**动作 | 拔刀剑 → 31 条；法杖+聚晶 → 施放族；弓 → 射击 |
| **修饰载体**（Modifier Carrier） | **不提供**动作，只**改**已有动作的参数 | 盔甲（+法术强度）、饰品（−冷却）、火焰附加（+点燃） |

⇒ **修饰载体作用于向量与代价**：例如"法术强度 +50%"⇒ 攻击类轴 ×1.5（钳到 1.0）、
"冷却 −25%"⇒ `COMMITMENT` 乘数 ×0.75、`readyFit` 放宽。

### 4.3 载体规则的数据格式

清单里的 `carrier` 需要从"一个 ID"升级为"**一条匹配规则**"：

```json
{
  "carrier": "slashblade:blade",
  "match": {
    "slots": ["MAINHAND"],
    "itemTest": { "kind": "javaInstanceOf", "target": "mods.flammpfeil.slashblade.item.ItemSlashBlade" },
    "itemTag": null,
    "requiresMod": "slashblade"
  },
  "actions": ["slashblade:*"]
}
```

| 字段 | 说明 |
|---|---|
| `slots` | **该载体在哪些槽位有效**。弓只能主手；灭火器只能副手；法术书主/副/背包/Curios 皆可 |
| `itemTest` | 匹配方式，优先级：`itemTag`（纯数据，最稳） > `itemId` > `javaInstanceOf`（需反射，见 [05](05-许可与代码复用.md) 的零硬依赖原则） |
| `requiresMod` | `ModList.isLoaded` 守卫 —— 未装则整条规则不加载 |
| `actions` | 该载体提供的动作 id（支持 `*` 通配，指向族） |

### 4.4 解析流水线

```
输入：maid
────────────────────────────────────────────────
1. 枚举持有物
     possessed ← [(MAINHAND, s), (OFFHAND, s), 盔甲×4, 背包×N, 女仆背包×M, Curios×K]

2. 收集候选动作（载体命中）
     candidates ← ∅
     for (slot, stack) in possessed:
       for rule in CARRIER_RULES:                       // 只含 requiresMod 已满足的
         if rule.match.slots ∌ slot: continue
         if not rule.match.test(stack): continue
         candidates ∪= expand(rule.actions)              // 族 → 实例（按参数域）

3. 硬过滤（顺序不能换）
     ① 模组未装        → 丢弃（2 步已保证）
     ② reach == RC     → 丢弃（不可达，见清单）
     ③ preconditions   → 必须全部满足（服务端可判定）
     ④ stateReq        → 必须全部满足（地面/滞空/潜行/朝向…）
     ⑤ exclusivity     → 与其他已占用的互斥组冲突 ⇒ 丢弃
     ⑥ readyFit == 0   → 冷却中/无弹药/召唤位满 ⇒ 丢弃

4. 计算有效向量
     u_x ← v_x ⊙ m_x(context)                          // §3.5

5. 应用修饰载体
     u_x ← u_x ⊙ m_modifiers(possessed)                // §4.2

────────────────────────────────────────────────
输出：可用动作集合 A = {(x, u_x)}        // A 为空 ⇒ 走回退动作
```

> ★ **回退动作必须永远存在**：`A = ∅` 时使用内置的
> 「接近目标 + 通用近战」。这是"不劣于 TLM"的底线，
> 也是 [08 §8.2](08-测试计划.md) 那条"灭火器丢失"教训的直接对策 ——
> **任何能力丢失都必须有一条显式的回退，而不是静默什么都不做。**

> ★ **载体可以不存在**：`carrier = maid:body` 的动作**不需要任何物品**
> （空手近战、走位、撤退&脱战）。⇒ **解析流水线第 2 步必须允许"无物品命中"的规则**，
> 否则女仆空手时会得到 `A = ∅`，退化到回退动作。见 §4.6.3。

### 4.5 ★ 「同一动作 ↔ 多个物品」问题（W 项问题）

> 本节回答你的 M2 注记里的三个问题。**结论先行**：
> **首选机制是「参数化」，不是「随机取一个物品」**；随机取物只是参数化覆盖不到时的**兜底（WIP）**。

**你提出的三个问题**：

1. 我有 4 把拔刀剑，用「横斩」时该用哪把？
2. 不同拔刀剑的 SA 不同 ⇒ 在框架里它是「**SA**」还是「**SA-次元斩**」？
3. 背包里有**不同枪械**呢？（火箭筒 / 步枪 / 手枪）

#### 4.5.1 先回答第 2 问：**是「SA」+ 参数，不是「SA-次元斩」**

**关键事实（均已查证，出处见 [01 §3.7](01-操作清单.md) 与 [`_research/slashblade-operations.md`](../_research/slashblade-operations.md)）**：

| # | 事实 | 出处 |
|---|---|---|
| 1 | **SA 的种类是有界的：9 种** | `SlashArtsRegistry.SLASH_ARTS`（9 项），研究文档 line 232-246 |
| 2 | **SA 绑在「物品数据」上，不在「操作」上** | `named_blades/*.json` 的 `properties.slashArtsType`（`PropertiesDefinition.Builder#slashArtsType`），例：夜叉=`sakura_end`、结月=`drive_horizontal`、黑狐=`piercing` |
| 3 | ★ **SA 运行时可以改** | 露台/合成可复制替换，item tag **`can_copy_sa` / `can_change_sa`** |
| 4 | **触发方式是同一个操作** | 按住右键 → `ItemSlashBlade.releaseUsing` → `ISlashBladeState#doChargeAction(LivingEntity, int)`；差别只在 `elapsed` 落点 |

**⇒ 结论：动作身份 = 「SA」（1 条族），参数 = `slashArtsType`（9 个取值），`v_x` 按参数覆写。**

**三条理由**：

| # | 理由 |
|---|---|
| **① 操作同构** | 9 种 SA 的**玩家操作完全一样**（按住右键松手）。`elapsed` 的三种落点（Fail / Jackpot / Success）是**同一操作的三种判定**，清单里已用 `judgement_cut` / `judgement_cut_just` / `quick_charge` 分开记录 —— **这一层与"哪把刀"无关** |
| **② SA 可变 ⇒ 按刀写清单会立刻过期** ⚠️ | 清单是**静态数据**（初始化加载），而刀的 SA **能在运行时被复制/替换**。若清单里写死"结月 = 幻影刃"，玩家改一次 NBT，**清单就错了**，且**没有任何办法在加载时发现** |
| **③ 参数域有界 ⇒ 不爆炸** | 若按刀枚举：9 种 SA × N 把刀（附属可加几百把）；**按 SA 枚举：只有 9 条** |

> ★ **第 ② 条是最关键的一条，它决定了架构**：
> **任何"由物品数据决定、且运行时可变"的东西，都不能进清单的静态主体，必须走参数在运行时解析。**
> 这条原则同样适用于枪型（`IGun` 的枪型索引）、聚晶（`domain.ref` 闭包）、法术书的法术表。

#### 4.5.2 三档处理（按"机制"而不是"表象"分）

| 档 | 判据 | 处理 | 例 |
|---|---|---|---|
| **A · 参数化**（★ 首选） | 物品只改变**同一操作的参数**，参数域**有界**且**影响战术价值** | 动作 = **族**；参数**运行时从物品解析**；`v_x` **按参数覆写**（`vectorOverrides`） | **SA 种（9）**、**枪型（7）**、`fireMode`、聚晶（`domain.ref`） |
| **B · 不同动作族** | **操作本身不同**（不是"同一操作的不同参数"） | 由载体规则的 `actions` 区分 ⇒ **它们本来就是不同的条目** | **开火 / ADS / 换弹 / 拉栓 / 切射击模式 / 枪托近战**（guns.json 里已是 14 条独立条目）；拔刀剑的 连击 / SA / 幻影剑 |
| **C · 等价类内取物**（WIP） | 两个物品**同属同一个参数值** ⇒ **战术等价** | **物品池 + 执行时随机取一个** | 4 把**同型**刀做横斩；★ **两把不同的步枪开火** |

> ★★ **A 的参数粒度决定了 C 的边界** —— 这一条是本节最重要的结论：
> **C 不是"我们没做机制"，而是"参数粒度选在战术等价类上"的自然推论。**
> 只要 A 的参数选得对，同一参数值内的物品**在决策空间里本来就是同一个点**，
> 那么"选哪一个"就**不存在战术上正确的答案**，随机（或按耐久/弹药挑）都是合理的。

##### ★ 一次自我纠正：手枪 / 步枪 / 火箭筒**不是 B，是 A**

我在本表初版里把「手枪 / 步枪 / 火箭筒」判成了 **B（不同动作族）**，并写"你的判断正确"。
**这是错的**，实测证据如下：

| 事实 | 出处 |
|---|---|
| **开火对三种枪是同一个操作** | `IGunOperator.fromLivingEntity(e).shoot(() -> pitch, () -> yaw)` —— 手枪、步枪、火箭筒**走同一个 `shoot()`** |
| **枪型是 TaCZ 的一个真实字段，且 TLM 自己就按它分支** | `CommonGunIndex.getType()`；TLM 的 `TacInnerCompat.java:40-64` 里 `sniper → 64`、`shotgun/pistol/smg → 32`、`rifle/mg/rpg → 48` |

⇒ 所以它们是**同一个操作、同一个族（`tacz:shoot`）、不同的参数取值** ⇒ **A**。

> **你的原话"火箭筒、步枪、手枪自然是不同的技能"并没有错** ——
> 它正确的地方在于**它们的战术价值不同**（该用火箭筒的时候不该用手枪）。
> 而"战术价值不同"恰恰就是 **`v_x` 不同** ⇒ **A 档**。
> **我用错了"B"这个分类**：B 应该只留给**操作本身不同**的东西（开火 vs 换弹 vs ADS）。
>
> ⇒ **教训（第 9 条）："不同的招" ≠ "不同的操作"。分类要看「输入路由」而不是「观感」。**

##### ★ 直接回答你的追问：「不同的步枪」是 C 吗？

**是。** 而且理由很干净：

```
两把不同的步枪  →  它们的 getType() 都是 rifle
              →  映射到同一个参数值（gunType = rifle）
              →  命中同一组 vectorOverrides
              →  在决策空间里是【同一个点】
              ⇒  不存在"战术上更对"的那一把  ⇒  落到 C（随机取一个）
```

| 对比 | 参数值 | 归属 |
|---|---|---|
| 步枪 ↔ 步枪 | 都是 `rifle` | **C**（同一等价类，随机取一个） |
| 步枪 ↔ 手枪 | `rifle` vs `pistol` | **A**（不同参数值 ⇒ 不同 `v_x` ⇒ 弹簧会按局势选） |
| 步枪 ↔ 火箭筒 | `rifle` vs `rpg` | **A**（同上） |
| 开火 ↔ 换弹 | —— | **B**（不同操作，已是两条独立条目） |

> ⇒ **所以 C 的适用范围比"不同步枪"更窄也更清晰**：
> **只有当两个物品落进同一个 `gunType`/同一个 SA 种时，才轮到 C。**
> 这也意味着 **C 会随着 A 的参数粒度变细而自动缩小** —— 如果我们以后想区分"AK-47 vs M4A1"
> （比如 M4 更准、AK 更伤），只需给 `tacz:shoot` 加一个 `gunId` 层级的覆写，
> **C 的成员就自动少了两个**。**这是"用架构重构"而不是"打补丁"的直接体现。**

#### 4.5.3 `v_x` 的落点（★ 架构缺口的修补）

> ⚠️ **写本节时发现一个真实缺口**：`docs/09 §6` 一直宣称 `v_x` 由**清单**提供（"清单 → 本文：`v_x`（手写）"），
> **但 `operation.schema.json` 里根本没有放向量的字段** —— 也就是说 `v_x` 至今**没有家**。
> ⇒ **本次补上**：schema 新增可选字段 **`vector`**（族的默认向量 / 实例的向量）
> 与 **`vectorOverrides`**（按参数取值覆写）。

```jsonc
{
  "id": "slashblade:slash_art",
  "kind": "family",
  "params": {
    "slashArtsType": {
      "ref": "SlashArtsRegistry",              // ★ 闭包来源（Q14 原则）
      "count": 9,                              // ★ 实测快照，用于交叉校验
      "values": ["judgement_cut", "sakura_end", "circle_slash", "wave_edge",
                 "drive_vertical", "drive_horizontal", "void_slash",
                 "piercing", "..."],
      "note": { "zh_cn": "SA 只有 9 种，且可在运行时被复制/替换 ⇒ 必须运行时解析" }
    }
  },

  "vector": { "SINGLE_DAMAGE": 0.6, "AREA_DAMAGE": 0.3 },          // 族默认（兜底）

  "vectorOverrides": {                                             // ★ 按参数覆写
    "judgement_cut":   { "SINGLE_DAMAGE": 0.4, "AREA_DAMAGE": 0.9 }, // 次元斩：大范围
    "drive_horizontal":{ "SINGLE_DAMAGE": 0.7, "MOBILITY": 0.2 },    // 幻影刃：中距直线
    "sakura_end":      { "SINGLE_DAMAGE": 0.9, "AREA_DAMAGE": 0.5 },
    "piercing":        { "SINGLE_DAMAGE": 0.8, "CONTROL": 0.2 }
  }
}
```

**取值规则（M3 实现）**：

```
u_x 的基准向量 = vectorOverrides[当前参数值]  若存在
               = vector                     否则（族默认）
```

> ★ **这样写的三个好处**：
> 1. **清单不需要知道有哪把刀** —— 只声明"参数是 SA，共 9 种"；
> 2. **9 组向量是可控的作者工作量** —— 而不是"给几百把刀各写一份"；
> 3. **改了 NBT 也不会错** —— 参数在运行时解析，清单始终有效。

#### 4.5.4 W 项（C 档）的规格 —— 按要求标记 WIP

```
执行动作 x：
  pool ← { 女仆持有的、满足 x.carrier 匹配规则的物品 }        // 见 §4.4 流水线
  if pool == ∅            → 该动作不可用（在第 3 步已被硬过滤掉）
  if pool.size == 1       → item ← pool[0]
  else                    → item ← pool[random]              // ★ WIP：随机取一个
  if 女仆主手 != item     → 切换主手到 item                   // ★ 见 §4.6.2「换武器」
  item 执行 x
```

| 项 | 状态 |
|---|---|
| 物品池枚举 | ✅ 机制已定（§4.4 第 1-2 步） |
| **随机取一个** | ⚠️ **WIP** —— **具体机制没做**（按你的要求标记） |
| 长期替代 | **A 档参数化**（若该差异影响战术价值）；或**按物品覆写 `vector`**（若只是数值差异） |

> ⚠️ **WIP 的已知缺点（留档，不要忘）**：
> 1. **随机 ⇒ 决策不可复现** ⇒ **自测无法断言选了哪把**（`SpringSelfTest` 的确定性会被破坏）；
> 2. **随机 ⇒ 行为不可解释** ⇒ 玩家看到"这次用这把、那次用那把"会归因为 bug；
> 3. ⇒ **实现时应把随机源纳入 `SpringConfig` 的随机源**（现已是注入式 `Random`），**保证自测可关**。

### 4.6 全局动作表 → 女仆可行子集（两级模型）

> 你的 M2 注记：「动作层可能有的所有内容**在整合包初始化部分搞定**，
> 然后局内编辑女仆的时候会**判定"这个女仆可行的动作层内容"**」。
> ⇒ **模型正确，但需要拆成两级 + 一个澄清。**

#### 4.6.1 两级 + 一个澄清

| 级 | 名称 | 何时确定 | 输入 | 输出 |
|---|---|---|---|---|
| **Lv1** | **全域动作表** | **整合包初始化**（mod 构造期 / `reload`） | `catalog/*.json` + **已装模组集合**（`sourceMod` 剪枝）+ **闭包枚举**（Q14） | 本次游戏会话**可能存在的全部动作** |
| **Lv2** | **女仆可行子集** | **运行期**（每个决策周期） | Lv1 + **该女仆此刻持有的物品** + 状态/互斥/冷却 | **该女仆此刻可用的动作集合 A** |

> ⚠️ **需要澄清的一点（重要）**：你写的是"**局内编辑女仆的时候**判定可行内容"。
> 这对**配置层**成立，但对**可用性**不成立 —— 因为**女仆会在战斗中途捡起/切换物品**。
> ⇒ **必须分成两件事**：

| | **配置层**（编辑时，静态，存 NBT/配置） | **可用层**（运行期，动态，每周期重算） |
|---|---|---|
| 回答 | "**允许**这个女仆用哪些动作族" | "**此刻**这个女仆能做哪些动作" |
| 变更频率 | 玩家编辑时 | **每 tick 都可能变** |
| 存哪 | 女仆 NBT / 模组配置 | **不存**，`ActionProvider` 现算 |
| 例 | 禁用某女仆的枪械类（不想让她打枪） | 背包里现在有没有枪 |

⇒ **可用层 = 配置层 ∩ 持有物 ∩ 状态 ∩ 互斥 ∩ 冷却**。
**M2 只做后面的动态部分；配置层留作后续可选（原 Q15 的选项 C）。**

#### 4.6.2 换武器：**执行器的前置步骤，不是动作**（Q8 决策的落地）

**Q8 已定**：「换武器直接体现在使用武器上（即执行对应物品对应的动作时，若不是该物品则切换为该物品）」。

⇒ **清单里不存在「换武器」条目**。它落在 **§4.5.4 流水线的第 4 行**：

```
if 女仆主手 != item:  切换到 item      ← 换武器发生在这里
```

| 设计点 | 说明 |
|---|---|
| **为什么不做成动作** | 玩家也不会"先切换再攻击"；把它做成动作会让决策层去选"换武器"这个**没有战术价值**的动作，污染评分空间 |
| **代价** | 切换有一次 `switch` 的开销（≈ 数 tick）；⇒ **`u_x` 应包含一个小的 `MOBILITY`/时间代价**（M4 调参时定） |
| **★ 由此产生的硬要求** | **每个动作必须能解析出"它需要的物品"** —— 否则执行器不知道要不要换手。这正是 §4.5.4 `pool` 的用途 |

#### 4.6.3 无载体动作（`maid:body`）

Q8 新增的走位与撤退动作**不需要物品**：

| 动作 | carrier | 在流水线里的行为 |
|---|---|---|
| `maid:retreat`（后撤） | `maid:body` | 命中**无物品规则** ⇒ **永远可用** |
| `maid:charge`（突进） | `maid:body` | 同上 |
| `maid:disengage`（撤退&脱战） | `maid:body` | 同上 |

⇒ **它们是"永远可用的兜底"的自然候选**，也是 `A = ∅` 时的回退动作来源（§4.4）。
**空手女仆不会无事可做。**

## 5. 决策循环

### 5.1 完整伪码

```
每 tick（服务端）：
  ── 0. 承诺门控 ──────────────────────────────────────
  if committed:
      tickCommit()
      if interrupted:  refund(remainingRatio)          // §5.3
      return                                            // ★ 不重选

  ── 1. 决策周期节流 ──────────────────────────────────
  if now - lastDecision < decisionInterval: return

  ── 2. 态势基线偏置（⑥，思维层未做时的主力）──────────
  b ← biasFromContext(maid)                             // §5.2
  b += biasFromThinkingLayer(maid)                      // ← 预留接口，当前恒 0

  ── 3. 弹簧受迫位移 ──────────────────────────────────
  p ← p + b
  p ← clamp(p, 0, P_MAX)

  ── 4. 忘却 + 规整（③）────────────────────────────────
  p ← p ⊙ (1 − λ)
  p ← normalize(p)                                      // 非负 / 上限 / 死区

  ── 5. 死区判定（②）──────────────────────────────────
  if ‖p‖ < ε:
      choose from DEFAULT_ACTIONS                       // 接近 / 警戒 / 待机
      return

  ── 6. 载体解析（§4）──────────────────────────────────
  A ← resolveAvailableActions(maid)
  if A == ∅:  choose FALLBACK_ACTION; return

  ── 7. 最近邻选解（含平局处理 ⑦）────────────────────
  x* ← argmin_{x ∈ A} d(p, u_x) + recencyPenalty(x) + jitter(x)

  ── 8. 提交执行 ───────────────────────────────────────
  commit(x*)                                            // 锁定 duration
  execute(x*)                                           // ③ 执行层（N2/N3）
  p ← p − u_{x*}                                        // ★ 立即扣减（不是等结束）
  p ← normalize(p)
  markUsed(x*)
```

### 5.2 态势基线偏置 `biasFromContext`（修正 ⑥ 的核心）

**这是"思维层"的规则版替身**，也是它在未实现前唯一让弹簧动起来的机制：

| 条件 | 偏置 |
|---|---|
| 有攻击目标且在其射程内 | `SINGLE_DAMAGE +0.3` |
| 附近敌人 ≥ 3 | `AREA_DAMAGE +0.4` |
| 附近敌人 ≥ 6 | `AREA_DAMAGE +0.8`（**替代**上一档，不叠加） |
| 自身血量 < 40% | `SELF_SURVIVAL +0.6` |
| 主人血量 < 50% | `ALLY_CARE +0.5` |
| 自身血量 < 15% | `SELF_SURVIVAL +1.0`、`SINGLE_DAMAGE −0.5`（**替代**上一档） |
| 距离目标 > 8 格 | `MOBILITY +0.3` |
| 附近无敌人 | 全 0（⇒ 死区 ⇒ 默认动作） |

> ★ **分档规则不叠加**：同一轴上的分档（`附近敌人`、`自身血量`）取**最高命中档**，
> 不同轴之间才累加。否则"敌人多 + 血少"会瞬间把 `p` 顶到上限，弹簧失去分辨率。

> ★ **设计要点**：`b_context` **每个决策周期重新计算并累加**，
> 在**上限之下**稳态满足 `p ≈ b/λ`（一个**比例控制器**）。
> ⇒ 偏置越强 ⇒ 稳态需求越大 ⇒ 越可能选到"更狠"的动作。**这正是我们要的"强度可调"。**
>
> ⚠️ **但 `max` 钳制会先接管**：本场景 `b/λ = 0.8/0.04 = 20`，远超 `AREA` 的上限 `1.0`，
> 实际 `p[群伤]` 稳定贴在 `1.000`（见 §5.6 第 3 步）。
> ⇒ **不要靠"加偏置"来提升动作强度**，那是无效的；要提升强度得**换更大的 `v_x`**。参 §5.6 读法 3。

### 5.3 承诺与退还（修正 ④）

| 情况 | 处理 |
|---|---|
| 动作是 `INSTANT` | 立即扣减 `p` |
| 动作是 `COMMIT(n)` / `CHANNEL` | **开始时**就扣减（承诺语义：我准备付这个代价了）；期间**不重选** |
| 被打断（受伤/目标消失/命令切换） | `p ← p + u_x · (剩余tick / 总tick)` ⇒ **按比例退还**，避免"没放出来却被扣了" |
| 正常结束 | 不退还 |

### 5.4 平局与抖动（修正 ⑦）

```
recencyPenalty(x) = ρ · exp(−(now − lastUsed(x)) / τ)      // 刚用过的轻微惩罚
jitter(x)         = U(0, δ)                                 // δ 很小（默认 0.01）
```
`τ` 默认 100 tick。**注意 `ρ` 要小**（默认 0.05）—— 它只是打破平局，
**主力的轮换效果本来就来自 `p` 的位移**，不靠惩罚。

### 5.5 参数总表（全部走配置）

| 参数 | 默认 | 作用 | 调大的后果 |
|---|---|---|---|
| `λ_d` 忘却率 | 生存/护友 `0.01`，其余 `0.04` | 需求回归速度 | ↑ = 更快忘记、更短视、更易重复 |
| `ε_d` 死区 | `0.02` | 极近即原点 | ↑ = 更常进入默认动作 |
| `P_MAX_d` | `1.0`（生存/护友 `2.0`） | 需求上限 | ↑ = 允许积累更极端的倾向 |
| `w_d` 权重 | 生存/护友 `2.0`，其余 `1.0` | 距离加权 | ↑ = 更保守 |
| `τ` 平局窗口 | `0.05` | 视为平局的距离带 | ↑ = 更常按 recency 打破 |
| `decisionInterval` | `5` tick | 决策周期 | ↑ = 更迟钝但更省 |
| `δ` 抖动 | `0.01` | 随机微扰 | ↑ = 更随机（不建议超 0.05） |

### 5.6 用你的例子跑一遍（验证设计确实能产生你描述的行为）

> ⚠️ **本节数字全部来自实跑，不是手算。**
> 复现：`java -cp build\classes\java\main com.touhoulittlemad.fightlikeplayer.decision.SpringSelfTest`
> （见 [`SpringSelfTest.java`](../src/main/java/com/touhoulittlemad/fightlikeplayer/decision/SpringSelfTest.java) 测试 1 与测试 8）
>
> 📌 **一次自我纠正**：本表初版是手算的，偏置取成了 `AREA +0.4`，于是想当然写了"第 1 步选吟唱 AoE"。
> 实跑后**第 1 步其实是「近战连击」**（0.6502 < 0.8798）—— 因为需求小时，
> AoE 那 `−0.5` 的自保代价在加权距离里不划算。这不是 bug，而是"**需求小就该用轻手段**"的正确行为。
> 教训：**设计文档里的数字必须来自可执行的自测。**

**场景**：群怪环境（附近敌人 ≥ 6），女仆满血，主人满血 ⇒ `b = SINGLE +0.3, AREA +0.8`

动作表（`v_x`，写死在清单里）：

| 动作 | SINGLE | AREA | SURV | CTRL | MOB | REINF | ALLY |
|---|---|---|---|---|---|---|---|
| 吟唱 AoE | 0.2 | **0.9** | −0.5 | 0 | 0 | 0 | 0 |
| 壁垒聚晶 | 0 | 0 | **0.8** | 0 | 0 | 0 | 0.1 |
| 近战连击 | **0.8** | 0.1 | −0.2 | 0 | 0 | 0 | 0 |
| 突进 | 0.4 | 0 | −0.3 | 0 | **0.8** | 0 | 0 |

`p` 的演化（已含偏置与忘却）与**全部候选距离**（加权欧氏；`w`：单点/群伤/位移 = 1，**自保/护友 = 2**）：

| 周期 | `p`（单点, 群伤, 自保） | 群攻 | 近战连击 | 突进 | 壁垒聚晶 | 选中 | 扣减后 `p` |
|---|---|---|---|---|---|---|---|
| 1 | (0.288, 0.768, 0) | **0.7247** ← | 0.8879 | 1.1926 | 1.4046 | **吟唱 AoE** | (0.088, 0, **0.500**) |
| 2 | (0.372, 0.768, 0.495) | 1.4238 | 1.2630 | 1.5794 | **0.9668** ← | **壁垒聚晶** | (0.372, 0.768, 0) |
| 3 | (0.646, **1.000**, 0) | **0.8417** ← | 0.9560 | 1.3712 | 1.6483 | **吟唱 AoE** | (0.446, 0.100, **0.500**) |
| 4 | (0.716, 0.864, 0.495) | 1.4991 | **1.2477** ← | 1.6584 | 1.2103 | **近战连击**（平局） | (0, 0.764, 0.695) |

**这张表能读出四件事**：

1. **第 1→2 步就是你要的机制**：AoE 的 `SURV −0.5` 让 `p[自保]` 从 0 跳到 **0.500**，
   第 2 步最近邻于是自然变成"壁垒聚晶"。
2. **自保权重 2.0 是决定性的**：第 2 步壁垒聚晶 `0.9668` 领先近战连击 `1.2630`；
   若把自保权重降到 1.0，这个差距会被抹平，节奏随即被输出动作淹没。
3. **`max` 上限是节奏的另一半**：第 3 步 `p[群伤]` 实算 `1.505`，被上限钳到 `1.000`。
   **没有这个钳制，`p` 会朝 `b/λ = 20` 一路漂移，AoE 之后就再也选不出别的动作。**
   （⇒ §5.2 那句"稳态 `p ≈ b/λ`"只在**上限之下**成立；本场景实际是钳制主导。）
4. **第 4 步不是壁垒聚晶，而是近战连击** —— 这是**平局带**在工作：
   `d(壁垒)=1.2103` 与 `d(近战)=1.2477` 只差 `0.0374 < τ(0.05)`，落入平局带后由 LRU 打破，
   而近战连击**从未用过**。⇒ 循环是 `群攻→自保→群攻→近战`，**不是死板的两动作对拍**。
   实测对照（自测 9）：`τ=0` 确实退化成 `群攻↔自保` 死循环，`τ=0.05` 出现第三种动作。

> ✅ **结果与你的描述一致**：群攻 → 因为生存为负 → 生存端需求上升 → 检索生存端动作（壁垒聚晶）→ 执行 → 生存需求被满足。
> **而且这个循环不需要任何一条"打完 AoE 就防御"的规则 —— 它是几何的必然结果。**
> **这就是你设计的价值。**
>
> **结论**：在**恒定的环境输入**下，系统自发产生了**有变化的多动作循环**，
> 循环的"形状"完全由 `v_x`（作者写的战术价值）、`w`（性格权重）与 `λ`（记性）三者决定 ——
> **不需要状态机、优先级表或冷却规则**。
> 调这三样就能调出"保守 / 激进 / 多变 / 专一"的性格，这正是"可便捷搭建"的含义。

### 5.7 ★★ 弹簧空间：以「发布影响器」代替「直接改点」（委托方要求）

**原来**：执行动作时直接 `p ← p − u`。**问题有三个**：

| # | 问题 |
|---|---|
| 1 | **两个循环互相看不见** —— 主循环与副手循环共用一个空间，副手直接改 `p`，主循环无从知道自己错过了什么 |
| 2 | **顺序不确定** —— 同一 tick 里主循环动作、副手动作、态势偏置、思维层都想影响 `p`，**谁的先？** 直接赋值时这个顺序是隐式的、依赖调用点 |
| 3 | **思维层没有位置** —— 思维层要"推一把"弹簧，却只能去改 `p` 本身，绕过规整 |

**现在**：任何来源都**发布**一个 {@code NeedVector → NeedVector} 的纯函数，由
`SpringSpace.drain()` **按发布顺序逐个执行**：

```
publish(影响器1); publish(影响器2); publish(影响器3);
drain() ⇒ p ← 影响器3(影响器2(影响器1(p)))         // ★ 顺序即语义
```

| 收益 | 说明 |
|---|---|
| **顺序显式** | 由"发布顺序"决定，不再依赖调用点 —— **可复现、可断言** |
| **两循环天然合流** | 副手循环发布的影响，主循环下一次 `tick` 开头就能读到 |
| **思维层与动作层同构** | 思维层就是"再发布一个影响器"，**接口完全相同** |
| **易于测试** | 每个影响器是纯函数，可以单独断言 |

**现成的影响器工厂**（`SpringImpact`）：

| 工厂 | 语义 | 谁会用 |
|---|---|---|
| `subtract(u, …)` | **动作扣减** `p ← p − u` | 执行动作时 |
| `refund(u, ratio, …)` | **打断退还** `p ← p + u·ratio` | 被打断时（§5.3 修正 ④） |
| `bias(b, …)` | **偏置** `p ← p + b` | 态势基线 / **思维层** |
| `decay(cfg, …)` | **忘却** `p ← p·(1−λ)` | 每决策周期；思维层也可显式"催忘" |
| `reset(…)` | **强制置零** | 脱战 |

> ⚠️ **规整只在整批 `drain` 结束时做一次**（不是每个影响器各做一次）。
> 否则中间那次非负钳制会**把负值提前吃掉**，代价语义失效。
> ⇒ 实现上是"影响器只做纯向量变换，规整统一收口在 `drain` 末尾"。
>
> ★ 这次重构是**行为等价**的：`bias → decay → 规整` 一次 drain，
> 与原来的 `p.plus(b).decayed().normalize()` **数学上完全相同** ——
> 因此 §5.6 那张手工验证过的演算表与 τ 对照测试**全部原样通过**（24 项断言）。

### 5.8 ★★ 双循环架构：主循环 / 副手循环共用弹簧空间（委托方要求）

```
       ┌──────────────── SpringSpace（唯一）────────────────┐
       │   point: NeedVector       ← 两循环共同读写          │
       │   pending: [影响器…]      ← 按【发布顺序】逐个执行   │
       └───────▲───────────────────────────────▲───────────┘
               │ publish                       │ publish
     ┌─────────┴─────────┐         ┌───────────┴───────────┐
     │ 主循环「main」     │         │ 副手循环「offhand」     │
     │ 物品：主手 + 盔甲   │         │ 物品：【仅副手槽】      │
     │  + 背包 + 女仆背包  │         │ 盾 / 烈风之伞 / 灭火器  │
     │  + Curios          │         │                        │
     └───────────────────┘         └───────────────────────┘
```

| 规则 | 实现 | 自测 |
|---|---|---|
| **共用一个弹簧空间** | 两个 `DecisionCycle` 构造时**传入同一个 `SpringSpace` 实例** | ✅ 已断言 `main.space() == off.space()` |
| **动作层隔离** | `LoopSplit` 按槽位切开持有物：`OFFHAND` 归副手循环，其余归主循环 | ✅ 已断言两集合槽位不相交 |
| **不会抢同一个物品** | 结构上保证 —— 副手槽只有一个，且只归副手循环 | ✅ `isIsolated()` 不变量 |
| **上一个动作执行完毕才能开下一个** | `inFlight` 门控 + **执行器回报** `notifyCompleted()` | ✅ 已断言 |

> ★ **副手循环的动作天然是"持续型"**（持盾格挡、撑伞、喷灭火器）⇒
> 多为 `CHANNEL` / 长 `COMMIT`，与主循环"打一套"的节奏**天然错开**。
> 这正是"盾在手上就一直挡着"的玩家观感。

#### ★ 执行门控：为什么"完成"必须由执行器回报

委托方要求「上一次的执行完毕了才能开启下一次循环」。实现上有**两个结束途径**：

| 途径 | 说明 |
|---|---|
| ★ **执行器回报** `notifyCompleted()` | **权威来源** —— "一梭子打完了""这轮三连发结束""法术结算完毕"**只有执行器知道** |
| 承诺 tick 数走完 | **兜底** —— 防止执行器漏报导致循环永久卡死 |

⇒ 静态 tick 数只是**估计**（弹匣大小、连发长度都是物品数据决定的），
所以门控**以执行器回报为准**，tick 数只做保险。

## 7. 稳定性与调优

| 问题 | 条件 | 对策 |
|---|---|---|
| **发散**（偏置累积到上限、永远选同一个轴） | `b` 持续同向且 `λ` 过小 | `P_MAX` 钳制 + `λ` 不低于 `b/(P_MAX)` 的量级 |
| **振荡**（两动作交替） | `v_A ≈ −v_B` 且 `ε` 太小 | `τ` 平局窗口 + recency 惩罚 |
| **呆滞**（总在死区） | `b` 太小或 `ε` 太大 | 态势基线偏置按"是否在战斗"整体缩放 |
| **暴走**（长引导频繁被打断） | `decisionInterval` 太小 + 无承诺门控 | §5.3 承诺门控（**已内建**） |

**调优顺序建议**：先定 `w_d`（决定性格保守/激进）→ 再调 `λ`（节奏快慢）→ 最后 `ε`/`P_MAX`（敏感度/上限）。

>
> ⇒ 这样 `heal` 终于走到 `HEAL_SURVIVAL`，不再和 `fireball` 同分。
> ⇒ 3 个类别里 2 个是**闭包推导**，**新增法术不需要改清单**。

### 8.0f ★★ 一次自我检查（委托方质疑触发）：层账记错了

> 委托方问：「我们明明还没做思维&决策层，为什么做了 M4 进游戏就能看到变化？」
> ⇒ **这个问题是对的，我的层账记错了。**

**审计方法与结果**（在**生产代码**里找实现类，不看自测）：

| 检查项 | 结果 |
|---|---|
| `DecisionCycle` 的构造点 | **只在 5 处自测里** —— **没有任何生产调用** |
| `CarrierResolver` 的消费方 | **只有 `CatalogHolder`（它自己也还没被读）与自测** |
| **`biasFromContext` 的生产实现** | **0 个**（只有自测里塞的 lambda） |
| **契合度乘数 `m_x` 的生产实现** | **0 个**（`withFactors` 存在但无人调用） |

**⇒ 我此前说的"③ 决策层 骨架已通"严重低估了缺口。** 真实缺口不是"没接线"，而是：

> **弹簧的机械造好了，但让它动起来的两个实质内容 ——
> `biasFromContext`（态势偏置）与 `m_x`（契合度乘数）—— 一行都没写。**

**没有它们会怎样**：`b = 0` ⇒ `p` 永远停在原点 ⇒ **命中死区** ⇒
**永远只走"默认动作"** ⇒ 整个决策层**什么都不会做**。
⇒ **M4 单独做出来，游戏里看不到任何变化** —— 我之前的说法是错的。

**本轮已补齐（纯 JVM + 断言）**：

| 补齐项 | 类 | 说明 |
|---|---|---|
| ★★ **态势偏置规则表** | `ContextBias` | docs/09 §5.2 的 8 条规则，**分档不叠加**；已适配 8 轴模型（低血 ⇒ `MITIGATION_SURVIVAL`，**不是** `HEAL_SURVIVAL`）与有向 `MOBILITY` |
| ★★ **契合度乘数** | `FitnessCalculator` | docs/09 §3.5 的逐轴乘数：`rangeFit` / `clusterFit` / `deficitFit` / `threatFit` / `gapFit` |
| ★ 接入解析流水线 | `CarrierResolver` | 候选动作的有效向量现在 = `v_x ⊙ m_x`（此前 `u = v`，**等于没有契合度**） |
| ★★ **端到端链路自测** | `PipelineSelfTest` | **不再自己塞偏置**，走真实的 `ContextBias` 规则 —— **只有这种测试才暴露得出"实现为 0"这类缺口** |

**★ 端到端实测出的行为（最有说服力的一条）**：

| 情境 | 选中 |
|---|---|
| 满血 100%、1 敌、4 格 | `slashblade:slash_art`（攻击） |
| **残血 12%**、1 敌、4 格 | ★★ **`fight_like_player:disengage`（撤退 & 脱战）** |

> **没有任何一条"血少了就逃跑"的规则** —— 它是
> `自血 < 15% ⇒ MITIGATION_SURVIVAL +1.0` 偏置 ×
> `disengage` 的 `免伤 0.8 + 位移 −0.9` 向量 的必然结果。
> **这正是委托方 Q8 要的"残血时撤"，端到端跑通。**

**修正后的层记法（避免再记错）**：

| 层 | 内容 | 状态 |
|---|---|---|
| ① 动作层 | 清单数据（**当时** 78 条 / 67 可评分；现为 77 / 54） | ✅ 完成 |
| **② 执行器层** | **把动作在服务端做出来** | ⚠️ **只有 1 条**（TLM 原本的通用近战） |
| **③ 决策层 · 机械** | 弹簧、选解、承诺、双循环、清单加载 | ✅ M1/M2/M3 + 弹簧空间 |
| **③ 决策层 · 实质** | **态势偏置 + 契合度乘数** | ✅ **本轮补齐**（此前为 0） |
| **③ 决策层 · 接线** | 把真实世界喂进去、把动作做出去 | ❌ **未做 = M4** |
| **④ 思维层** | 推理 + 直接指令表 | ❌ 未做（延后，**不是 M4 的前置**） |

> ★ **关键结论（回答委托方）**：
> **可见变化 = ③机械 × ③实质 × ②执行器数量 × ③接线。**
> 思维层**不是**前置 —— 规则版偏置已经能产生"攻击 ↔ 自保"的节奏。
> **但若 ② 只有 1 个执行器，则无论 ③ 多聪明都看不见变化**（一个动作没有可选项）。
> ⇒ **真正决定"能不能看到变化"的是 ②，不是 ③。** M4 的可见效果**取决于它实现了几个执行器**。

#### ★★ M4 用源码纠正的建模错误（原题：第 11 条自我纠正；编号体例见 [13 §1.1](13-更正记录与教训.md)）

读 `EntityMaid#doHurtTarget`（:914-946）发现一次调用**同时**做三件事：

```java
926:  boolean result = super.doHurtTarget(target);   // ① 近战
929:  this.doSweepHurt(target);                      // ② 横扫（TLM 内部自判 SWORD_SWEEP + 横扫附魔）
941:  if (task instanceof IAttackTask at && at.hasExtraAttack(this, target))
943:      return result && at.doExtraAttack(this, target);   // ③ 灭火器附伤
```

⇒ **三者不可分开选择** —— 女仆无法"只横扫不近战"。
★ 而**玩家侧也一样**：横扫是左键命中时的**被动效果**，不是独立操作。

⇒ 清单修正：`sweep` 与 `extinguisher_extra` 标为 **`role = passive`**（引擎自动附带），
近战向量**吸收横扫的群伤价值**（`AREA_DAMAGE 0.25`）。可评分动作 67 → **65**。

> **教训（第 11 条）：执行器实现是"建模真相"的最后一道检验。**
> 前 10 条纠正都来自读文档/字节码；**这一条只有在真正去写"怎么执行"时才暴露**
> —— 因为只有那时才会读 `doHurtTarget` 的实现体。
> ⇒ **"能不能执行"必须与"能不能选择"一起设计**，而不是先列动作、再想执行。

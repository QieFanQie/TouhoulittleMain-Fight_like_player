> **本文回答什么问题**：女仆**能做什么** —— 一条操作记录该有哪些字段、怎么给一个新模组编清单、各载体的清单本体。
> **什么时候读**：查"某个模组到底有多少操作、每条什么作用"时；**给新载体编清单**时读 §1+§2。

> **上半部分是「怎么编制」（元模型 + 方法 + 判定规则），下半部分是「编制结果」（各载体的清单）**。
> 上半部分是可复用的规范；下半部分是可增补的数据。

## 1. 清单元模型

### 1.1 记录层级

```
OperationCatalog
└── Carrier（载体：主手物品 / 副手物品 / 饰品 / 已激活模式）
    └── ActionFamily（动作族：共享执行骨架，仅参数不同）
        └── ActionInstance（动作实例：参数绑定后的具体动作）
```

**族 vs 实例的判定**：见 [00](00-需求专业化重述.md) §4.3 的 Q1–Q5。
一句话——**效果实质不同 → 两条；只是程度不同 → 一条 + 参数**。

### 1.2 字段规范

| 字段 | 类型 | 必填 | 说明 | 空缺时怎么办 |
|---|---|---|---|---|
| `id` | `ResourceLocation` | ✅ | 稳定标识，决策层用它点名 | — |
| `carrier` | `ResourceLocation` | ✅ | 载体（物品 ID / 模式 UID） | — |
| `sourceMod` | `string` | ✅ | 提供方 modid；用于清单剪枝 | — |
| `family` | `bool` | ✅ | 是族（true）还是实例（false） | — |
| `params` | `map<string,domain>` | 族必填 | 参数名 → 取值域（可枚举或范围） | 若无法枚举，标 `open` |
| `preconditions` | `list<Predicate>` | ✅ | **服务端可判定**的可用性谓词 | 缺 = 该动作随时可用（危险，需复核） |
| `stateReq` | `list<enum>` | ✅ | 所需实体/世界状态 | 从触发语法抽取；抽取不到标 `unknown` |
| `cost` | `list<Cost>` | ✅ | 代价：耐久/资源/弹药/召唤位/饥饿/经验/冷却 | 标 `none` 或 `unknown` |
| `duration` | `enum` + `int` | ✅ | `INSTANT` / `COMMIT(n ticks)` / `CHANNEL`(可延续) | — |
| `interruptible` | `bool` + 窗口 | ✅ | 能否被打断、何时可取消 | — |
| `comboDeps` | `list<id>` + 窗口 | 组合动作必填 | 前置动作 + 时序窗口 | — |
| `effects` | `list<Effect>` | ✅ | 可观测效果（**与战报项目对接**） | — |
| **`exclusivity`** | `list<Group>` | 条件必填 | ★ **互斥占用组**：该动作执行期间/持有期间**独占**哪些资源槽位。例：铁魔法"法术书同类互斥"（默认只能装 1 本 ⇒ 同时只有 5~12 个法术可用）、召唤位、主手法杖 | 若该族存在"同时只能用 N 个"的限制则**必须填**，否则决策层会选中互斥的动作组合 |
| `reach` | `RA` / `RB` / `RC` | ✅ | 服务端可达性分级 | — |
| `evidence` | `list<Cite>` | ✅ | `【已查证】`/`【推断】`/`【待验证】` + 出处 | — |
| `existingImpl` | `string?` | 可选 | 已知的既有实现（如万法皆通的枚举名） | 无则留空 |

### 1.3 `stateReq` 取值域（从实测的触发语法归纳）

| 值 | 含义 | 实测来源 |
|---|---|---|
| `GROUND` | 在地面 | 拔刀剑"连击A：指令 地面" |
| `AERIAL` | 滞空 | 拔刀剑"御空刀舞：指令 滞空" |
| `MOVING` | 正在移动 | 拔刀剑"瞬步回避：在移动中" |
| `NEAR_ENEMY` | 靠近敌人 | 拔刀剑"借力跳：滞空靠近敌人时" |
| `NEAR_WALL` | 靠近墙壁 | 拔刀剑"踢跃：滞空靠近墙壁时" |
| `HAS_TARGET` | 有当前目标 | 通用 |
| `TARGET_IN_VIEW` | 注视目标 | 拔刀剑"隔空瞬步：向注视中的敌人" |
| `SNEAKING` | 潜行中 | Goety"施法者潜行…" |
| `NOT_WALKING` | 非行走状态 | 拔刀剑"防御：'行走'中无法发动" |
| `SHEATHED` | 纳刀状态 | 拔刀剑"迅速蓄力：在纳刀的瞬间" |
| `AFTER(action_id)` | 某动作之后 | 拔刀剑"跃升斩：上斩后" |
| `TIMING_WINDOW(evt, n)` | 事件触发的时机窗口 | 拔刀剑"格挡：在受到攻击时" |
| `BUFF(效果)` | 需要某效果 | 拔刀剑"连击A绝：在力量或饥饿效果时" |
| `SERVANT_SELECTED` | 已选中仆从 | Goety"没有被选中的仆从" |

### 1.4 `cost` 取值域

`DURABILITY(n)` / `RESOURCE(耀魂值/Soul/n)` / `AMMO(item)` / `SUMMON_SLOT(n)` / `HUNGER` / `XP(n)` / `COOLDOWN(ticks)` / `CHARGE_TIME(ticks)` / `MANA(n)`

### 1.5 `reach` 分级（服务端可达性）

| 级 | 定义 | 判定方法 | 处理 |
|---|---|---|---|
| **R-A** | 模组提供**服务端公开入口**（public 静态方法/API） | `javap` 看到 public 方法且签名不含 client 类 | 首选做 |
| **R-B** | 无公开入口，但可**组合底层调用**复现（生成实体、写 capability、拼时序） | 需要"自己实现效果" | 做，但要估工作量 |
| **R-C** | 效果**本质依赖客户端/UI/玩家身份** | 引用了 `net.minecraft.client.*` 或纯 GUI 流程 | **不进清单** |

## 2. 编制方法（给新模组的 5 步流程）

这套流程已经在拔刀剑/Goety 上跑通过，可直接复用。

| 步 | 动作 | 拔刀剑的实例 | Goety 的实例 |
|---|---|---|---|
| **1** | **从模组自身找"操作清单"** —— 很多模组已经把操作写进了成就/指南/提示文本 | `adv.slashblade.*` 的 **22 条成就描述就是官方操作手册**，含键位与指令序列 | 聚晶的 `*.info` tooltip 直接写了变体规则 |
| **2** | **枚举载体** —— 哪些物品/系统是"操作来源" | `ItemSlashBlade` 及其 SA | 法杖 + 聚晶 + 聚晶包 + 魔法书 |
| **3** | **抽取触发语法** —— 把"键位+状态+时序"翻译成 `stateReq` / `comboDeps` | ♠/ᐃ/ᐁ/⚪/□ → `GROUND`/`AERIAL`/`SNEAKING`/… | 右键/潜行右键/左键点仆从 → `SNEAKING`/`SERVANT_SELECTED` |
| **4** | **查服务端可达性** —— `javap` 找公开入口；找不到就下潜到实体/能力层 | 命中 `AttackManager.doSlash(...)` → R-A；后处理 `EntitySlashEffect` → R-B | 命中 `Goety.api.magic.ISpell` / `IChargingSpell` → R-A |
| **5** | **与既有实现对账** —— 查万法皆通等既有模组是否已实现，避免重复造轮子 | 已有 31 个 `DirectSkill` | 已有 `GoetyProvider` + `MaidGoetySpellData` |

> 📌 **第 1 步是最容易被忽略、但性价比最高的一步。** 拔刀剑把自己的完整操作手册做成了 22 条成就，
> 只要把 `lang/zh_cn.json` 里的 `adv.slashblade.*` 读出来，就能得到一份官方权威的操作表——
> 比读反编译代码快一个数量级。

> ⚠️ **但第 1 步有一个陷阱（本轮踩到了）**：**一个模组的操作清单往往分散在多处。**
> 拔刀剑的 22 条成就只覆盖了"**剑技系统**"（左键派生），而"**SA 刀技系统**"（**右键蓄力**）**完全不在其中**——
> 它藏在 `ItemSlashBlade.onUseTick` + `SlashArtsRegistry` 里。
> 只读成就文本会得出"拔刀剑没有右键操作"的**错误结论**（我最初就写错了，见 §9.1）。
>
> ⇒ **规则：第 1 步产出的清单必须用"载体 × 注册表"做交叉验证**——
> 凡是模组里有 `DeferredRegister` / `Registry` 的（如 `SlashArtsRegistry` 的 9 个 SA），
> 都要逐个对账："这个注册项对应哪个玩家操作？"对不上的就是漏掉的操作。

**证据等级：全表 【已查证】**——来源为拔刀剑重锋 1.8.60 自带的成就文本

两个自定义按键（`key.slashblade.*`）：
- `special_move` —— **特殊移动**（在输入命令位里映射为 `SPRINT`）
- `summon_blade` —— **召唤幻影剑**（映射为 `M_DOWN`）

> ✅ **对你原话的确认**：你说拔刀剑有"**左键 / 右键 / 长按右键 / shift+…**"等操作——**这是正确的**。
> 实测拔刀剑有**两套并存的系统**：
>
> | 系统 | 触发 | 覆盖 | 载体 |
> |---|---|---|---|
> | **剑技系统**（Resharped 新增） | **左键 或 右键**（+潜行/前进/后退/跳跃/特殊行动键派生） | §3.1–§3.6 的全部 28 条 | `ComboStateRegistry` + `ComboCommands` + `InputCommand` |
> | **SA 刀技系统**（拔刀剑原有） | **右键按住蓄力，松手时结算** | §3.7 | `ItemSlashBlade.releaseUsing` → `ISlashBladeState.doChargeAction` → `SlashArts.doArts` |
>
> 即：**左键/右键 = 剑技，长按右键 = SA**。两套系统独立并存，且**都有"次元斩"**（剑技蓄力版与 SA 版）。

### 3.4.1 ★★ 可达性专项：为什么这 6+2 条是"最难"而不是"最容易"

> **这一节推翻了我在 §8.2 里的初始优先级判断，请以本节为准。**

【已查证，基于反编译源码】拔刀剑的"能力"系统由 `InputCommandEvent` 驱动，而该事件的载荷类型
**写死为 `ServerPlayer`**：

```java
// _research/javap/mods.flammpfeil.slashblade.event.handler.InputCommandEvent.txt
public class InputCommandEvent extends Event {
    net.minecraft.server.level.ServerPlayer player;          // ← 写死 ServerPlayer
    public net.minecraft.server.level.ServerPlayer getEntity();
    public static InputCommandEvent onInputChange(net.minecraft.server.level.ServerPlayer, ...);
}
```

⇒ **女仆永远收不到这个事件。** 受影响的处理器（全部写作 `ServerPlayer sender = event.getEntity();`）：

| 处理器 | 覆盖的操作 | 关键证据 |
|---|---|---|
| `EnemyStep.onInputChange` | 借力跳 | `EnemyStep.java:69-72`；另用 `sender.f_8906_.m_9829_(...)` **发包给玩家连接**（`:90`） |
| `KickJump.onInputChange` | 踢跃 | `KickJump.java:76-79`；并挂在 `TickEvent.PlayerTickEvent`（`:117`） |
| `SlayerStyleArts.onInputChange` | **全部 4 条瞬步** | `SlayerStyleArts.java:106-107`；其全部执行方法签名都是 `ServerPlayer`（`:123,138,153,164,190,195,201,206,214,223`） |
| `SuperSlashArts.onInputChange` | SA·Super | `SuperSlashArts.onInputChange` + `releaseSSA(ServerPlayer)` |
| `MoveInputHandler.onPlayerPostTick` | 输入状态采集 | 挂在 `TickEvent.ClientTickEvent` ⇒ **纯客户端** |

#### 但有两个好消息

**好消息 ①：`防御 / 格挡` 是唯一对 `LivingEntity` 通用的一条。**

【已查证】`Guard.java` 不是输入驱动，而是**事件驱动**：它挂在 `LivingAttackEvent` 上，
并且从 **`victim`（类型是 `LivingEntity`）** 上取能力：

```java
// Guard.java:75,91,96-100
LivingEntity victim = event.getEntity();                     // ← LivingEntity，不是 Player
LazyOptional input = victim.getCapability(CapabilityInputState.INPUT_STATE);
InputCommand targetCommand = InputCommand.SNEAK;
boolean handleCommand = input.filter(i ->
        i.getCommands().contains(targetCommand) &&
        i.getCommands().stream().noneMatch(move::contains)).isPresent();
```

里面唯一与玩家绑定的只有**播声音**（`:161 if (victim instanceof Player)`）和成就授予——**都不影响功能**。

⇒ **`防御 / 格挡` ＝ R-B，而且是本清单里最有希望的一条**：
只要往女仆的 `IInputState` capability 里**写入 `InputCommand.SNEAK`**，`Guard` 就会替女仆工作。
**这是"类玩家"在拔刀剑上唯一一处可以复用官方状态机的缝隙。**

**好消息 ②：瞬步的"位置计算与传送数学"是可复用的。**

【已查证】`SlayerStyleArts` 里这几个方法参数是 **`Entity` / `LivingEntity`，不是 `ServerPlayer`**：

```java
public static void  doTeleport(Entity entityIn, LivingEntity target);
public static void  executeTeleport(Entity entityIn, LivingEntity target);
public static Vec3  calculateTeleportPosition(Entity entityIn, LivingEntity target);
public static boolean isValidTeleportPosition(Vec3 teleportPos);

public static void  handleEntityTeleportation(Entity entityIn, ServerLevel, double, double, double, float, float);
```

⇒ 只有"输入派发"和"给玩家发包"是不可达的，**核心数学可以直接调用**。
⇒ 4 条瞬步属于 **R-C 但可 R-B 重写**。

**好消息 ③：`Guard` 的时机窗口是明文常量。**

【已查证】`Guard.java:112-117`：
```java
int soulSpeedLevel = EnchantmentHelper.getEnchantmentLevel(Enchantments.SOUL_SPEED, victim);
int justAcceptancePeriod = 5 + soulSpeedLevel;                 // ← 完美格挡窗口 = 5 + 灵魂疾行等级
```

⇒ 这正好解释了 §3.8 里"灵魂疾行每 1 级延长格挡输入窗口 1 tick"的说法，**清单可填精确数值**。

**好消息 ④（最重要）：`IInputState` 是"服务端可写"的 ⇒ 原版连击/SA 状态机对女仆可复用。**

【已查证】
- `CapabilityAttachHandler.java:30-37`：`slashblade:inputstate` 被挂到**每一个 `LivingEntity`** 上，
  **没有任何 `instanceof Player` 检查**。
- `IInputState` 内部是**可变的 `EnumSet` / `EnumMap`**，服务端可写。
- `IInputState#getCommands(LivingEntity)` 会自动补 `ON_GROUND` / `ON_AIR`
  ⇒ 女仆**不需要自己判定地面/滞空**，写进去即可。

配套的 `LivingEntity` 型入口（**全部可直接调用**）：

```java
// 状态机推进
ISlashBladeState#doChargeAction(LivingEntity, int elapsed)        // ★ SA 入口
ISlashBladeState#progressCombo(LivingEntity[, boolean isVirtual])
ISlashBladeState#updateComboSeq(LivingEntity, ResourceLocation)
ISlashBladeState#resolvCurrentComboStateTicks(LivingEntity)

// 攻击

  doSlash ×7 重载 | areaAttack ×7 | doVoidSlashAttack | newVoidSlashEffect
  doManagedAttack | doAttackWith | doMeleeAttack ×2 | isPowered
  playQuickSheathSoundAction | playPiercingSoundAction | genRushOffset | getSlashBladeDamageScale
```
> ⚠️ 注意：**不存在** `doJudgementCut` / `doSummonedSword` / `doChargeAttack` 这类方法（曾猜测有，实测没有）。
> SA 的入口是 `doChargeAction`。

⇒ **结论：走 `IInputState` + `progressCombo`/`doChargeAction` 这条路，唐刀剑整套连击与 SA 状态机都能为女仆复用。**
**唯一要彻底避开的是 `InputCommandEvent`**（它承载 `ServerPlayer`）。

**唯一协议通道（解释了一切）**【已查证】：
客户端→服务端**只有 1 个包**：`MoveCommandMessage`（id 0，**单个 `int` 位掩码** = `EnumSetConverter.convertToInt(EnumSet<InputCommand>)`），
由 `MoveInputHandler#onPlayerPostTick` 在**掩码变化时**发送。
（id 1/2 的 `RankSyncMessage` / `MotionBroadcastMessage` 是 S→C。）
⇒ **这就是"客户端驱动的操作到不了女仆"的根本原因**：那条通道的发送者是玩家客户端。

#### ⚠️ 最大未验证风险（必须做冒烟测试）

【已查证】许多 `ComboState.tickAction` 引用了 **`event.client.UserPoseOverrider`**（`setRot`/`resetRot`）
与 **`event.client.SneakingMotionCanceller`** —— 这些是**客户端侧类**。

⇒ **在专用服务器上运行这些 `tickAction` 是否抛 `NoClassDefFoundError`，尚未验证。**
**这是"复用原版状态机"这条路线成败的头号风险**，必须在动手前用一个最小服务端测试确认。

### 3.7 刀技 SA（`SlashArts`）—— **右键蓄力释放**，且有**三档评价**

**这一节是本轮勘测的关键补齐**：SA 的触发方式不在 22 条成就里，通过字节码勘测确定。

#### 3.7.1 触发机制【已查证】

> ⚠️ **一个重要更正**：我最初根据 `ItemSlashBlade.onUseTick` 里出现 `getSlashArts()` 就断定"SA 由 `onUseTick` 驱动"。
> **这是错的。** 反编译验证后的真实调用链是：

```
右键按住  → getUseDuration() = 72000（ItemSlashBlade.java:212-214）
         → onUseTick()  只做 ComboState.holdAction + 蓄力粒子（:400-416）  ← 不触发 SA
         → 松手：releaseUsing(ItemStack, Level, LivingEntity, int timeLeft)
                 → elapsed = 72000 - timeLeft
                 → state.doChargeAction(entityLiving, elapsed)        ← ★ SA 在这里结算
                     → getSlashArts().doArts(ArtsType, user) → 返回新的 ComboState id
```
（`ItemSlashBlade.java:371-398`）

⇒ **SA 在"松手那一帧"结算，不是在持续按住时。** 这个区别直接决定实现方式
（女仆要模拟的是"一次带时长的使用动作 + 释放"，而不是持续 tick）。

| 证据 | 内容 |
|---|---|
| `ItemSlashBlade.getUseDuration()` = **72000** | 原版"使用中"时长的最大值 ⇒ **"按住"是靠原版 `startUsingItem` 实现的** |
| `ItemSlashBlade.releaseUsing(...)` → `doChargeAction(LE, elapsed)` | ★ **SA 的唯一触发点** |
| `ISlashBladeState.doChargeAction(LivingEntity, int)` | ★ **参数是 `LivingEntity`** ⇒ **女仆可以直接调，不必模拟右键** |
| `SlashArts.ChargeTicks` = **9**、`ChargeJustTicks` = 3、`ChargeJustTicksMax` = 5 | `public static final int`；实际生效的是 `getFullChargeTicks()`（硬编码 9） |
| `SlashArts.getJustReceptionSpan(LE)` = `min(5, 3 + 灵魂疾行等级)` | 完美释放窗口；注意 `ChargeJustTicks`/`ChargeJustTicksMax` 是**死代码**（无引用） |
| `SlashArts.doArts(ArtsType, LivingEntity) -> ResourceLocation` | 执行刀技，返回新的连击状态 |
| `SlashArts.getProudSoulCost()` / `setProudSoulCost(int)` | **消耗耀魂值（默认 20）**；不足则改为扣 **1 点耐久**；**每把刀可不同** |
| `SlashArtsRegistry`（Forge `DeferredRegister`） | SA 是**可注册对象**：`NONE` / `JUDGEMENT_CUT` / `SAKURA_END` / `VOID_SLASH` / `CIRCLE_SLASH` / `DRIVE_VERTICAL` / `DRIVE_HORIZONTAL` / `WAVE_EDGE` / `PIERCING`（9 个，与 `lang` 完全对应） |

#### 3.7.2 ★ 核心发现：`ArtsType` 是**四档评价** ⇒ SA 是一个**动作族**

【已查证】`SlashArts$ArtsType` 枚举常量：

```
Fail | Success | Jackpot | Super
```

⇒ **"长按右键"不是一个操作，而是一个动作族，参数是「释放时机质量」**：
`elapsed = 72000 - timeLeft`（即按住的实际 tick 数），

| # | 操作名 | 玩家输入 | `elapsed` 区间 | `ArtsType` | 状态载体 | reach |
|---|---|---|---|---|---|---|
| 29 | **SA（刀技）** | 右键按住 → 松手 | `>= 9 + justSpan` | `Success` | `getComboState(LE)` | **R-A** |
| 30 | **SA·完美（绝）** | 右键按住 → 在完美窗口松手 | `[9, 9 + justSpan)` | `Jackpot` | `getComboStateJust(LE)` | **R-A** |
| 31 | **SSA（超级刀技）** | **地面按住特殊行动键 20 tick** | — | `Super` | `getComboStateSuper()` | ⚠️ **R-C** |
| — | 蓄力不足 ⇒ 无 SA | 松手过快 | `< 9` | `Fail` | — | — |

其中 `justSpan = SlashArts.getJustReceptionSpan(LE) = min(5, 3 + 灵魂疾行等级)`。
**成本**：`getProudSoulCost()`（默认 **20** 耀魂值）；耀魂值不足时改为**扣 1 点耐久**。

> ⚠️ **`Super` 档是 R-C，且有额外前置**：【已查证】
> ① 执行入口 `SuperSlashArts.releaseSSA(net.minecraft.server.level.ServerPlayer)` —— **参数类型写死为 `ServerPlayer`**；
> ② 触发方式不是"释放 SA"，而是**在地面按住 `special_move` 键 20 tick**；
> ③ 还要求刀为 **BEWITCHED**（妖刀）且带 **FIERCEREDGE** 附魔、**击杀数 ≥ 1000**；
> ④ 消耗**最大耐久的一半**。
> ⇒ 服务端 mob（女仆）无法直接调用。要支持它必须走 R-B（自己重写 SSA 效果）或放弃。

### 4.2 ★ 聚晶的"变体规则" —— 从**源码**还原的完整语法

> 本节结论来自 **Goety 源码** `D:\tiaolvshi\Goety-2-1.20\src\main\java\com\Polarice3\Goety\`

#### 4.2.1 变体判定的唯一入口

【已查证】`common/magic/Spell.java:71-73`：

```java
public boolean isShifting(LivingEntity caster){
    return (caster.isCrouching() || caster.isShiftKeyDown()) && !WandUtil.findWand(caster).isEmpty();
}
```

⇒ **两个关键含义**：
1. **潜行变体的总开关就是这一个布尔**（没有 `CastType` 枚举——**别去发明它**）。
2. ⚠️ **必须有法杖**：只拿聚晶、不拿法杖时，潜行变体**不触发**（`!WandUtil.findWand(caster).isEmpty()` 为假）。
   ⇒ 清单里"潜行变体"的 `preconditions` 必须包含**持法杖**。

#### 4.2.2 八类变体规则（一般化，非逐个聚晶）

#### 4.2.4 施法形态（第三个变体维度）——由**基类**决定，不是枚举

【已查证】Goety **没有** `CastType` 枚举。施法形态由**基类 + 两个谓词**决定：

| 形态 | 判定 | 基类 / 接口 | 法术数 |
|---|---|---|---|
| 瞬发（对空右键） | `!isNotInstant(...) && notTouch(...)` | `Spell`（直接继承） | **75** |
| 蓄力/前摇 | `spell.castDuration(caster, staff) > 0` | `ChargingSpell`（直接） | **2** |
| 持续引导（按住不放） | `defaultCastDuration() == 72000` | `EverChargeSpell` | **14** |
| 连发无冷却 | `everCharge() == true` | （同上，标记） | — |
| 吐息锥 | `instanceof IBreathingSpell` | `BreathingSpell` | **3** |
| 触碰实体 | `instanceof ITouchSpell` ⇒ `notTouch` 为假 | `TouchSpell` | **2** |
| 对块施法 | `instanceof IBlockSpell` ⇒ `notTouch` 为假 | `BlockSpell` | **4** |
| 召唤 | 有仆从上限与召唤惩罚 | `SummonSpell` | **25** |
| **合计** | | | **125** |

**一个法术对象的五个阶段钩子**【已查证，`api/magic/ISpell.java`】：

```
startSpell(起手) → useSpell(每 tick 引导) → stopSpell(松手) → SpellResult(结算载荷)
                   useParticle(每 tick 表现)
```
瞬发法术直接跳到 `SpellResult`。

⇒ **这对清单的意义**：`duration` 字段有现成的 7 种取值，且 `interruptibility` 有现成的判定
（是否 `isNotInstant`、是否 `everCharge`）。

#### 4.2.5 变体维度总结

| 维度 | 取值 | 判定来源 |
|---|---|---|
| `sneaking` | true / false | `Spell.isShifting(caster)`（**且需持法杖**） |
| `aim` | `TARGET` / `BLOCK` | `getTarget(caster)` 是否为 null |

> 📐 **结论（重要）**：**聚晶不是 120 条操作，也不是"1 族 + 6 维度"。**
> 它是 **1 个动作族「施法」 × 5 个变体维度 × 125 个法术参数 × 11 个学派**。
>
> 而且——**变体维度是"代码里的 8 类语义"，不是"每个聚晶一套规则"**。
> 这让"类玩家"的实现变得非常可行：女仆只需要理解那 **5 个维度**，
> 就能覆盖 125 个法术的绝大部分行为空间；只有 B/E 两组（共 4 个法术）需要逐个特判。

| # | 原因 | 证据 |
|---|---|---|
| 1 | `MagicData(true)` → `new PlayerRecasts()` **无参构造** → `serverPlayer == null` → `tick()` 恒假 | `PlayerRecasts.tick(int)` 里 `if (serverPlayer != null && …)`；且 `MagicManager.tick:57` **只遍历 `level.players()`** ⇒ **永不超时、永不完成** |
| 2 | 万法皆通**从不调 `castSpell`**，只调 `onCast` | ⇒ recast 计数**永不递减** |
| 3 | `onRecastFinished` 的形参是 `ServerPlayer` | 硬调必 NPE（覆写体第一句 `entity.level()`；基类走 `addCooldown(null,…)` ⇒ `getEffectiveSpellCooldown((Player)null)`） |

**recast 法术数取决于 Iron's 版本**：**3.4.0.9 只有 4 个**（`wall_of_fire` / `flaming_barrage` / `eldritch_blast` / `portal`）；
**3.16.3 已扩到 11 个**（再加 `raise_dead` / `summon_swords` / `summon_horse` / `summon_vex` / `summon_polar_bear` / `thunder_step` / `raise_hell`）。
⇒ 这直接影响了 [06](06-验收实例模组清单.md) §2.3 的版本选择。

**⭐ 重大发现：万法皆通 1.8.2 已经自己实现了 recast**（`MaidIronsSpellData$MaidRecastSession`，间隔 10 tick），
用**反射 `getDeclaredField("recastLookup")`** 绕过 `onRecastFinished`，并**逐法术手写收尾**（`finishMaidWallOfFire` / `finishMaidThunderStep`）。
⇒ **证明 recast 对 mob 明确是 R-B**，且给出可参考成品与两条硬约束（别指望 `PlayerRecasts.tick`；别调 `onRecastFinished`）。

> **推荐的实现（比 1.8.2 更稳）**：
> ① 用 **`spell.getRecastCount(level, maid) > 0`** 判「是不是 recast 法术」（public 且吃 `LivingEntity` ⇒ **R-A**）；
> ② 用 **`spell.getEmptyCastData()` 的类型**做收尾分发（对齐 ISS 自己的多态做法）
> ⇒ **不写死 spellId，3.16.x 新增的 recast 法术自动覆盖**（这正是 §4.2.4.1 那条"用接口闭包代替手写清单"的原则）。
> ⚠️ **不要用反射删 `recastLookup`**，改用 Mixin `@Accessor` —— 字段改名时**编译期失败**，好过**静默卡死**。

#### ③ 同类法术书互斥 = **万法皆通自己的设计，不是 Iron's 的限制** ⇒ 我们应当解除

【已查证】`canAddSpellBook` 判的是 `k.isAssignableFrom(c) || c.isAssignableFrom(k)`（比物品**类**的继承关系）；
铁魔法 14 本书全在 `SpellBook` 树上 ⇒ 互相冲突 ⇒ 默认只能装 1 本 ⇒ **同时只有 5~12 个法术可用**。
**反证**：玩家的 `SpellSelectionManager` 收 Curios 法术书槽 + 主/副手 + 4 件护甲，**不比较类**。

⚠️ **还查出一处万法皆通自身的不一致**：互斥**只对主手/副手/背包生效**；
**Curios 槽里的法术书不受互斥限制、全部可施放**。

⇒ **本位就是 schema 里 `exclusivity` 字段的现实来源**（见 [07](07-清单数据格式.md) §4.2）。

#### ④ 支援/治疗法术被**无条件短路**成"打敌人" ⇒ 22 个法术白放

【已查证】`mixin/iss/UtilsMixin#beforePreCastTargetHelper`：条件 `caster instanceof EntityMaid && additionalCastData instanceof TargetEntityCastData`
→ HEAD `setReturnValue(true)` ⇒ **`filter` 与 `aimAssist` 一并失效**。

**更好的做法**：不注入（或注入但**恢复 `filter` 与距离判据**）。
因为女仆施法前已被 `forceLookAtTarget` 用 `lookAt(EYES, …)` 设好 `yRot` + pitch ⇒ **原生射线路径大概率能命中**。
更进一步："法术意图（攻击/支援）→ 打谁"应当**提升为调度器的一等概念**，而不是塞进名叫「法术白名单」的 `blue_note` 里（那个命名本身就在误导）。

#### ⑤ 无 PvP：**硬门但可覆写**（R-A）

【已查证】`api/task/IAttackTask.canAttack` 是 **`default` 方法**，判 `target instanceof Player → false`；
而 `EntityMaid.canAttack`（`EntityMaid.java:1225-1228`）**委托给当前任务**
⇒ **只需在自己实现的任务里覆写 `canAttack` 就能解锁**。

⚠️⚠️ **一个安全认知陷阱**：万法皆通的 `AllianceManager` 调了 `setAllowFriendlyFire(false)`，
但它**只影响 Player 打 Player，不阻止法术伤害** ⇒ **别把"同队"当安全保证**。

建议：**默认关 + 主人永久豁免 + 队伍/好友系统介入**。（1.8.2 已按法术粒度部分解除 ⇒ 上游认可这个方向。）

#### ★★ 两个必须单独讲的发现

**① 持枪的女仆贴身时完全没有任何输出（真实战力空档）**

【已查证】`AbstractGunItem#onEntitySwing` **返回 `true`** ⇒ **持 TaCZ 枪时原版挥击被取消**。
而 TLM 从未调用 `operator.melee()` ⇒ **女仆持枪贴身时，既没有枪托近战，也没有普通 `mobAttack`**。

枪托近战在 TaCZ 里是**独立路径**（不是 `mobAttack`）：
`IGunOperator.melee()` → `LivingEntityMelee` → prepTime 倒数 → `ModernKineticGunItem.melee()`
→ **MUZZLE 附件 → STOCK 附件 → 枪默认 `GunMeleeData`**，按 `distance` / `rangeAngle` 结算伤害 + 击退。

⇒ **补这一条不是"多一个动作"，而是修一个战斗能力黑洞。** P0。

**② 手雷/榴弹：**★ **TaCZ 侧根本不存在，不是 TLM 的遗漏**

【已查证】TaCZ 1.1.7-hotfix2 的 **816 个 class** 搜 `Grenade|grenade|Throw` **零实体命中**；
三个附属（`taczaddon` 73 / `taczlabs` 22 / `FCE` 8 class）也零命中；只剩
`ModSyncedEntityData.THROWABLE_USE_TICK`（无读写方）与 `ThrowableAnimationStateContext`（空类）—— **废弃脚手架**。
而 `TacCompat.isGrenade` 硬编码 `false` 在全仓**无任何调用点**（孤立 TODO）⇒ **它是正确实现**。

> 📌 **这条纠正了一个流传的说法**：不要再把手雷列为"TLM 未实现的功能"。
> RPG 类的"榴弹"是**普通枪 + 爆炸弹药**，走 `shoot()`，女仆**已经能打**。
